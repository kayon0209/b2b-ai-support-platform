## 0. 先说结论

**三个界面都在，但不成形；闭环缺最后一公里。**

| 目标 | 现状 | 结论 |
|---|---|---|
| 客户侧对话窗（对话 + 数据卡片） | `/support` 有，且**真的渲染结构化卡片**（时间轴/节点，不是文字） | ✅ 成形 |
| 坐席工作台（会话 + AI 话术 + 已查数据 + 相似工单） | `/workbench` 数据齐（单个 bundle 端点一次取全），但**已查数据是文字不是卡片** | 🟡 数据齐、呈现缺 |
| 运营后台（自动化率 / 漏点分析 / 知识库维护） | `/quality` + `/gaps` + `/knowledge` 三页齐全，含 `automation_candidates` | ✅ 成形 |
| **一个闭环**（漏点 → 标记可自动化 → 上线 → 自动化率上升） | 前 3 段有，**最后一段"标记后可自动化上线"没有机制** | ❌ 断在最后一公里 |
| 界面数量 | **实际 4 个**：多了内部验证面 `/chat` | 🟡 需收敛 |

**最值钱的那张表已经存在**（`/quality` 的"Where handoffs come from"，带 `automation_candidates` 与 `sample_questions`），
但它现在只**告诉你**下一步该自动化什么，**不能让你真的去自动化**。这是 §4 排第一的缺口。

## 1. 目标形态：三个界面 + 一个闭环

### 界面一 · 客户侧对话窗

- **谁用**：客户。
- **看到什么**：对话 + **数据卡片**（订单状态、物流节点可视化，不是一段文字）。
- **关键约束**：卡片里的数据必须**属于这个客户**——身份没通过之前，任何业务数据都不该出现。

### 界面二 · 坐席工作台

- **谁用**：客服。
- **看到什么**：会话 + AI 建议话术 + **已查数据** + 相似工单。
- **关键约束**：**不用切系统**。切一次系统就丢一次上下文，丢一次上下文客户就要重说一遍。

### 界面三 · 运营后台

- **谁用**：主管 / 总经办。
- **看到什么**：自动化率、**漏点分析**（哪些问题还在转人工）、知识库维护。
- **为什么它最被低估**：**"哪些问题还在漏"是这套系统最值钱的一张表**，它直接告诉你下一步该自动化什么。

### 一个闭环

```
线上会话 → 漏点（转人工的原因 + 问法样本）
        → 运营看到"这一类 100% 转人工" → 标记为可自动化候选
        → 补齐知识/规则 → 上线自动应答
        → 该类目自动化率 0% → 62%
        → 线上数据继续回流（人工修正、满意度、拦截日志）
```

闭环的价值不在任何单点，而在**"漏点能变成已自动化"这条路径是通的**。任何一段断开，产品就退化成静态报表。

## 2. 一天的时间线：逐环节对照实现

| 时刻 | 期望发生什么 | 现状 | 缺口 |
|---|---|---|---|
| **凌晨 2:14** 工程师问"我昨天下的单能加急吗" | ①身份通过 ②查到订单 ③识别为"改价类" ④风控拦截（AI 不许定价） ⑤回复"已记录，9:30 前专员联系您" ⑥工单生成并带全部上下文 | ①`POST /v1/support/verify`（单号+手机尾号）✅ ②Tool Gateway 查订单 → 卡片 ✅ ③意图+业务线（PCB/元器件/SMT/DFM）+改价类识别 ✅ ④`redline_violations` 把 price/lead time 列为模型禁言项，出站拦截 ✅ ⑤非工作时间 `offline_notice` 明确给出下次服务时间 ✅ ⑥案例+会话+AI 方案+引用+账户联系人 ✅ | **几乎全通**。唯一缺：④之后"改价类"这个**业务线级分类**没有进入漏点统计的维度（见 §4-3） |
| **早上 9:05** 坐席打开工单，不用再问一遍 | AI 副驾给出：加急费参考 ¥XX（依据：价目表 v3.2 + 同类工单 3 条） | `/v1/cases/{id}/workbench` 一次返回：案例 + 会话 + `ai_suggestion` + 来源 + `related_cases` + 账户联系人 ✅。报价走 `pricing/engine.py`（确定性规则表 + `QuoteBand` 区间 + `basis` 说明依据哪条规则 + 价目表版本）✅ | **两处**：①工作台把"已查数据"渲染成**文字/徽章**，不是客户侧那种卡片（`ToolCard` 只被 `/support` 用）；②`QuoteBand` 的价目表默认是**空的**——不配置就没有数字（见 §4-2） |
| **下午 3:00** 主管看后台：本周"加急咨询"47 次，100% 转人工 | 标记为"可自动化候选" | `/quality` 有自动化率、转人工来源表、`automation_candidates` + `sample_questions` ✅ | **"标记"这个动作没有落点**：候选是**算出来的**，不是**可操作的**。没有"标记 → 进入待办 → 指派"的机制 |
| **一周后** 加急咨询上线自动应答，该类目自动化率 0% → 62% | 补齐知识/规则 → 上线 → 率上升 | 知识侧有完整链路：`gap_service`（缺口）→ 草稿 → 审核 → 发布（`/gaps` 页面全流程）✅；人工修正回流 `answer_corrections` ✅ | **断在这里**：从"这个类目该自动化了"到"它真的自动化了"之间，**没有任何机制**。运营只能自己在别处改词表/改规则，然后**无法验证**该类目的率是否真的变了 |

**这条时间线的判定：前 3 段通，第 4 段断。** 断点就是"一个闭环"缺的那一公里。

## 3. 逐界面差距

### 3.1 客户侧对话窗（`/support`）

**已具备**
- 访客会话身份（ADR 0011），不是操作员令牌。
- 身份三步：`POST /v1/support/verify`（单号 + 手机尾号）→ 重签带 `account` 的访客令牌 → **fail-closed**。
- 归属校验两道门：匿名访客在**任何连接器调用之前**拦截；回执里的 `account` 与已验证账户比对。**三态而非布尔**：`None`=操作员运行（不过闸）、`""`=匿名（过闸）、`"acme"`=已验证。
- 结构化卡片：`tool_card.py` → `timeline[].card` → `ToolCard.tsx`（订单时间轴/节点）。卡片带 `fetched_at`（ISO 8601）+ `provenance`。
- 查不到就明说，不出卡片、不编造（`found:false`）。

**差距**
| # | 差距 | 影响 |
|---|---|---|
| C1 | **卡片是只读的** | 演示故事里"客户确认 → 系统改单"这一步，卡片上**没有确认入口**。确认只能靠文字往返 |
| C2 | **匿名开销只受配额约束** | ADR 0011 已记录：公开的 `/support` 接受匿名模型开销，只由月度配额与队列深度兜底。ADR 0012 之后没有第二个渠道可退，这个决策从"建议"变成"必须" |
| C3 | **一个客户只有一个身份入口** | 2.1 身份归一（淘宝 ID ↔ 商城账号 ↔ 来电号码 ↔ 微信 openid）只做到"账户"一层；没有跨渠道显式映射表 |
| C4 | **语音进不来**（1.4 ASR） | 电话渠道的语音消息无法进入流程 |

### 3.2 坐席工作台（`/workbench`）

**已具备**
- 单端点聚合：`GET /v1/cases/{id}/workbench` → 案例、`account_contacts`、会话、`ai_suggestion` + 来源、`related_cases`。
- 与客户侧**同一套**权限与脱敏（返回引用而非正文）。
- 一键升单：业务语义 → 真实 `Department.slug`；目标组不存在**拒绝且不写入**（避免工单进没人看的队列）。

**差距**
| # | 差距 | 影响 |
|---|---|---|
| W1 | **已查数据不是卡片** | 目标说"已查数据"，客户侧看到的是时间轴卡片，坐席看到的是一段文字/徽章。同一个事实两种呈现，坐席要自己脑补节点顺序 |
| W2 | **两个卡片组件并存** | `ToolCard.tsx`（客户侧，API 已解析）+ `DataCard.tsx`（旧 `/chat` 页，自己解析 JSON）。`ToolCard` 的 docstring 声称自己是"唯一渲染器"，而 `DataCard` 仍在跑 |
| W3 | **相似工单相关性是语言相关的** | 复用词项重叠（pg_trgm 对中文 `similarity()=0.000`），短中文问答对上只有 Dice=0.222。**排序必须保持语言无关**，否则中文短问法永远排不到一起 |
| W4 | **内部协作 @（7.9）没有** | P2，跨部门确认只能出系统 |
| W5 | **工作台只能从案例进** | `/workbench/:caseId`。没有"未指派队列"视图——坐席得先知道案例号 |

### 3.3 运营后台（`/quality` + `/gaps` + `/knowledge`）

**已具备**
- 自动化率、正确解决率、意图分布与趋势（`aggregate_intent_distribution`，scene/kind/business_line 三个维度 + 时间分桶）。
- **漏点来源表**（转人工原因 + 自动化候选 + 样本问法）——就是"最值钱的那张表"。
- 缺口队列 → 草稿 → 审核 → 发布；知识库文档列表 + 上传 + 术语/别名 CRUD。
- 全链路回放 `/conversations`：决策按 `turn.text_hash == run.input_hash` 关联到轮次（**不按时间猜**），未能归因的 run 单独列出而非丢弃。
- 人工抽检：分层抽样（弃权/转人工/失败/低置信优先），seed 决定论可复现。

**差距**
| # | 差距 | 影响 |
|---|---|---|
| O1 | **"可自动化候选"只读不可操作** | 表告诉你该做什么，但点不动。这是闭环的断点（§4-1） |
| O2 | **没有"类目"这一层对象** | 统计维度有 business_line / scene，但**没有"问题类目"实体**可以挂"已自动化 / 待自动化"状态。所以无法回答"加急咨询这个类目现在自动化了吗" |
| O3 | **改动与指标之间没有回链** | 发布了一份知识 / 改了一条规则，**无法看到**该类目的自动化率随之变化。9.4 回归测试存在，但它测的是"没变差"，不是"这次改动带来了什么" |
| O4 | **A/B（8.6）与灰度（9.3）有机制无运营入口** | `evaluation/ab.py` 有稳定分桶、flag 有租户级 rollout，但后台没有"跑一个实验并看结果"的页面 |
| O5 | **界面数量是 4 不是 3** | `/chat` 是内部验证面（ADR 0010 保留），页面文案**仍写着"客户渠道是 Chatwoot"**——这句现在是错的 |

## 4. 必须补齐的部分（按风险与价值排序）

### 第一优先：闭环的最后一公里（O1 + O2 + O3）

**问题**：漏点分析现在只输出"观察"，不输出"动作"。

**最小可行修法**（不新建架构组件）：
1. 引入**问题类目（IssueCategory）**这一层：由 `intent.scene` + `business_line` + 关键实体派生，确定性、可版本化。
2. 每个类目带状态：`observed`（只在漏）→ `candidate`（已标记）→ `automating`（在补知识/规则）→ `automated`。
3. 类目状态**进入 AgentRun 快照**，于是"该类目自动化率"变成一次按类目分组统计——不需要新的埋点。
4. `/quality` 的候选行加一个动作：标记为候选 → 生成一张待办（复用缺口队列的既有形态）。
5. 上线后，同一张表显示"标记前 0% → 标记后 62%"，**改动与指标的回链就闭合了**。

**为什么这是第一优先**：它把三界面里最值钱的那张表从"报表"变成"工具"，且不引入新的基础设施组件。

### 第二优先：工作台看到客户看到的东西（W1 + W2）

- 让 `/workbench` 用**同一个** `ToolCard` 渲染 `ai_suggestion` 里的已查数据；删除 `DataCard.tsx` 与 `styles.css` 里 `.cw-*` / `.data-card` 的旧块。
- **为什么重要**：坐席与客户看到同一张卡片，才能"不用再问一遍"。

### 第三优先：报价的"依据"要真的有依据（4B.2）

- `pricing/capability.py` 的制程能力矩阵**默认空**，且**部分未知绝不判 feasible**——这是对的纪律。但空矩阵意味着**任何报价都转人工**。
- 演示故事里的"加急费参考 ¥XX（依据：价目表 v3.2）"要成立，必须**灌入真实的价目表版本与能力矩阵**。这是**数据配置任务，不是代码任务**。
- 同样地，`QuoteBand` 的价目表来源（PCBSync）需要一条真实的来源记录。

### 第四优先：收敛到三个界面（O5 + C2）

- `/chat` 要么合并进 `/workbench` 的调试抽屉，要么明确标注为"仅内部验证"并**修正它页面里那句错的文案**（现在仍说客户渠道是 Chatwoot）。
- 公开的 `/support` 的匿名开销必须做一个**按环境的显式决策**（ADR 0011 要求、ADR 0012 之后变成必须）。

### 第五优先：剩下的 P1/P2（清单口径）

| 项 | 内容 | 依赖 |
|---|---|---|
| 1.1 | 淘宝/天猫、电话、QQ 群适配器 | 各渠道签名与协议；`channels/base.py` 已是扩展点，加渠道=一行适配器+一行注册 |
| 1.4 | 语音转写 ASR | **外部模型服务** |
| 3.7 | 多语言（出海 180+ 国） | 已有跨语言检索修复（rerank 信号替代词面门限）；缺的是话术本地化 |
| 4B.6 | 替代料参数匹配 | 参数化匹配（**不是语义检索**），需要料号参数库 |
| 7.9 | 内部协作 @ | P2 |
| 10.1 | 真实 ERP / MES 适配器 | 现在只有 `demo_erp.py`；连接器 SDK 已就绪，按此即插 |
| 8.6/9.3 | A/B 与灰度的运营入口 | 机制已有，缺页面 |
