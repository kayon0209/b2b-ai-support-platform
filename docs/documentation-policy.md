# 文档维护规范

## 分层与权威入口

- README 面向产品使用者，描述当前能力和安装入口，不充当开发交接日志。
- `docs/README.md` 为文档首页；能力在 `capabilities.md`，部署要求与限制在 `production-readiness.md`。
- 接口、架构、安全、运行手册持续更新；验证报告始终绑定提交、环境和日期。
- 历史评估、阶段清单和原始交付记录归档，或在保留兼容路径时明确标注历史范围。

## 完成事项与表述

1. 完成的开发事项写入发布记录，不继续挂在当前产品文档中。
2. 被后续实现取代的缺口说明更新或归档；不能一边实现认领、一边保留“没有认领”的当前说明。
3. 企业凭据、身份源、数据库、模型、监控等写为接入/部署要求；需要实际验证的部分仍列明验证条件。
4. 当前版本不包含的能力明确写“不支持”，不要把未来愿望混进当前承诺。
5. 删除过时的“本次增加”“交给某 Agent”“完成后再唤醒”等工作现场措辞；历史报告保留原文，不改写证据。
6. 不机械删除正常产品状态，如审批待办、等待客户、待收集字段；它们不是未完成开发声明。
7. 代码合入、CI 通过、合成验证、真实企业验证与生产发布分别记录。没有证据不能把失败/未执行替换为通过。

## 删除与链接

删文件前查找代码、测试、文档和发布脚本引用。ADR、安全说明和测试证据不得为了营销观感删除。移动资料时修复相对链接，必要时保留兼容入口；发布前检查 Markdown 本地链接和 `git diff --check`。

## 版本交付

产品文档、部署指南、能力矩阵、已知限制和验证报告随版本一起维护。完成后清除当前文档中过时的“待办/待验收”状态，但不消除真实限制或篡改历史。
