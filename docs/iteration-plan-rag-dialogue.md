## 1. 终局状态（North Star）

### 1.1 一句话目标

> **把当前"安全治理达标、智能能力 Demo 级"的平台，做成一个在质量、延迟、成本、
> 可靠性四个维度上都能拿出企业级数字、并且每个数字都有可复现证据的 AI 客服系统。**

"企业级"在这里不是形容词，是一组**可测量、可复现、可回归**的门槛（第 2 节）。
本项目是个人项目，没有真实客服流量，因此证据形态是**替代品**而不是**降级品**——
替代规则见第 3 节。

### 1.2 成熟度阶梯

每一维度都按四级判定。**目标是把全部维度推到 L3，把安全与容量推到 L4。**

| 级别 | 名称 | 判据 |
|---|---|---|
| **L1** | 可演示 | 能跑通 happy path；参数写死在代码里；无指标；失败无区分 |
| **L2** | 可测量 | 有指标与评测；参数可配置；能回答"现在是多少" |
| **L3** | 可运营 | 有 SLO 与门禁；行为变更可灰度可回滚；有 runbook；回归可拦截 |
| **L4** | 可规模化 | 有容量规划与成本预算；多租户隔离经负向验证；做过故障演练 |

### 1.3 能力矩阵：现状 → 目标

| 能力维度 | 现状 | 目标 | 主要差距 |
|---|---|---|---|
| 租户隔离 / 权限 | **L4** | L4（保持） | — |
| 审计 / 引用溯源 | **L4** | L4（保持） | — |
| 工具网关安全 | **L4** | L4（保持） | — |
| 转人工 / 人机竞态 | **L3** | L4 | 缺故障演练；交接不带证据 |
| 超时重试 / 熔断 | **L3** | L4 | 退避无抖动；无并发上限；无降级链 |
| 可观测性 | **L3** | L4 | 缺上下文/成本/首字延迟指标 |
| 幻觉抑制 | **L2** | L3 | 引用只验存在不验支持；guard 未落地 |
| RAG 检索 | **L1→L2** | L3 | 参数全硬编码、无 overlap、无 metadata 过滤、无召回指标 |
| 数据处理 | **L1** | L3 | 无清洗、无标签、表格被拉平 |
| 知识生命周期 | **L2** | L3 | 无 owner、无权威度、无复审、无冲突裁定 |
| 评测体系 | **L2** | L3 | 只有布尔结果，**无归因**；无 judge；无人工评测 |
| 意图识别 | **L1→L2** | L3 | 审计前是二分类；本轮补了体系但未接线 |
| 多轮 / 记忆 | **L0→L1** | L3 | 审计前不存在；本轮补了模块但无持久化、无历史拉取 |
| Agent 工具编排 | **L2** | L3 | 无选择逻辑；无读工具；工具回执不进答案 |
| 成本 / 延迟治理 | **L1** | L3 | 无预算闸门、无缓存、无流式、无模型路由 |
| 并发 / 容量 | **L2** | L4 | 无并发上限、无背压、无压测报告 |

## 2. 企业对标基线与本项目目标

### 2.1 质量

| 指标 | 行业基线（来源见下） | 本项目目标 | 测量方式 |
|---|---|---|---|
| 自动解决率 / containment | Tier-1 agentic AI **60–90%**；实现良好的客服机器人 **70–90%**；电商典型 **70–80%**、领先 **89–92%**；Intercom Fin 规模化下 **76%** | **固定语料 ≥70%** | `scripts/run_eval.py` + `supported_resolution_rate` |
| 弃权正确率 | 无公开基线，按"宁可弃权不可错答"自定 | **≥90%** | 已有门禁 `min_abstention_correct_rate` |
| 引用覆盖率 | — | **≥95%** | 已有门禁 `max_citation_violation_rate` |
| 禁止声明率 | — | **≤2%**，启用 guard 后 **≤0.5%** | 已有门禁 `max_forbidden_claim_rate` |
| 重开率（一次修复率） | 行业共识：解决率**必须**与 CSAT、重开率配对解读 | **≤5%** | `wrong_resolution_rate` |
| 检索召回 | 主流做法：retrieve top-20 → rerank → 送 top-5 给模型；faithfulness 与 context recall 是最高信号指标 | **recall@10 ≥0.90** | 新增门禁 `min_retrieval_recall_at_k` |
| 上下文精确率 | — | **≥0.70** | 新增 |

> 关于绝对阈值的重要立场：主流 RAG 评测实践（RAGAS 方法论文档）**明确不推荐追逐
> 固定阈值**，而是要求"以自身基线做相对对比，并当作 CI 回归门禁来用"。本项目的
> `release_check` + `pytest_plugins_release` 派生门禁**正是这个模式**——这是既有资产，
> 不需要改，只需要把新指标接进去。上表的数字是**方向性标尺**，不是别人家的 KPI。

### 2.2 延迟

| 指标 | 行业基线 | 本项目目标 | 说明 |
|---|---|---|---|
| TTFT p50 | **< 500 ms** | Phase 5 前：不适用 | 当前 provider 非流式，**无首字可测**（`generator.py` 已记录该限制） |
| TTFT p95 | **< 1.5 s**（持续超 1.5s 即告警） | 流式落地后 **< 1.5 s** | 需先做 5.2 |
| TTFT p99 | **< 3 s** | < 3 s | |
| 总延迟 p95 | 流式下数秒可接受；**15–20 s 为硬上限** | **< 8 s**，backstop 20 s | 现有 `run_latency_seconds` 已有基础 |
| 感知阈值 | <200 ms 瞬时；<500 ms 灵敏；>1 s 感知到卡 | — | 用于解释为什么必须做流式 |

**p95 必须按模型、按租户、按"首轮 vs 后续轮"分别切分**——聚合 p95 会掩盖区域性
或版本级劣化。这是行业明确的告警实践，也是多轮上线后必须补的切分维度。

### 2.3 成本

| 指标 | 行业基线 | 本项目目标 |
|---|---|---|
| 简单 FAQ 会话 | **0.2–0.5 美分/会话** | **p50 ≤1 美分** |
| 复杂多工具会话 | **3–15 美分/会话** | **p95 ≤5 美分** |
| 人工坐席对照 | **约 $7/会话** | 用于论证 ROI（AI 成本应低于人工 1–2 个数量级） |
| 缓存折扣 | 缓存 token 通常**便宜约 50%** | 用于 5.1 的 prompt 缓存收益核算 |

**必须统计 p95 成本**：最贵的会话通常是重试循环或多轮调试，只报均值会把
成本失控藏在平均值里。行业实践还要求设**硬限制**——每会话最大 LLM 调用数
（建议 10）、每调用最大 token、每会话成本上限；触限时**优雅转人工并记录事件**，
而不是静默失败。

### 2.4 可靠性

| 指标 | 行业基线 | 本项目目标 |
|---|---|---|
| 可用性 | 99.9% = 每月约 **43.2 分钟**不可用 | 定义 SLO 并在压测下验证，不口头声称 |
| 零容忍不变量 | — | 跨租户 **0**、越权写 **0**、重复回复 **0**（已有门禁） |
| 读工具成功率 | 排除第三方故障 **≥99%** | 已有门禁，自动覆盖新增读工具 |
| 故障演练 | 企业必做 | 备份恢复演练（已有 `backup_restore_drill.py`）+ 新增模型宕机与降级演练 |

## 3. 个人项目如何证明达到企业标准

这是本计划最重要的一节。企业标准里有一部分**无法通过写代码获得**——真实流量、
真实客服团队、7×24 值班、数据科学家团队。诚实做法是**明确替代规则**，而不是假装拥有。

| 企业靠什么 | 本项目用什么替代 | 为什么这不算降级 |
|---|---|---|
| 真实客服流量（百万级会话） | **固定评测语料**（`tests/evals/dataset.py`）+ 合成压测 | 真实流量不可复现；固定语料让回归**可 diff**。评测读活数据等于放弃复现能力 |
| 真实客户数据 | **合成语料 + 脱敏策略** | `docs/security.md` 已规定原文不入库；合成语料是唯一合规且可公开的做法 |
| 人工坐席标注 | **人工标注子集 + judge 一致性验证（Cohen's kappa）** | 企业同样需要先验证 judge 才能信它；这里只是样本量小，方法论一致 |
| A/B 实验分流 | **门禁回归 + 版本对比报告** | 行业评测实践本身就要求"以相对对比 + CI 回归门禁"替代绝对阈值 |
| 7×24 值班 | **runbook + 桌面演练记录** | 演练能证明流程可执行；不能证明有人值夜班，如实标注 |
| 容量规划（按增长曲线） | **压测曲线（并发 → 吞吐/延迟/错误率）** | 压测能给出拐点与上限；不能给出增长预测，如实标注 |
| 多租户规模化运营 | **跨租户负向测试套件** | 这是比"生产跑过"更强的证据：它主动尝试越界 |

**因此本计划的验收标准分两类**：
- **可量化达标**（质量/延迟/成本/安全）——必须有数字与产出物。
- **可复现证明**（替代项）——必须说明"用什么替代了什么"，并如实标注不可替代的部分。

## Phase 1 — 检索链路与数据处理

覆盖主题：检索链路（RAG 检索、query 重写、chunk 切分与 overlap、chunk size、
多路召回、rerank、top-k）、数据处理（清洗、结构化、切片、标签）、
体验优化（口语化与模糊表达召回）。

### 目标

把检索从"能跑通"（L1）变成"可调、可测、可解释"（L3）。当前所有参数都是常量
（`MAX_CHUNK_CHARS=1200`、候选 40/40、RRF k=60），无 overlap，无 query 重写接线，
无 metadata 过滤，无召回指标。

### 量化目标

| 指标 | 基线 | 目标 |
|---|---|---|
| recall@10 | 未测量 | **≥0.90** |
| 上下文精确率 | 未测量 | **≥0.70** |
| 硬编码检索参数个数 | 5（chunk/候选/RRF/top-k/rerank 阈值） | **0** |
| 每路召回的独立贡献 | 不可测 | 每路可单独关闭并测出指标变化 |
| 型号不匹配时的弃权率 | 不适用 | **100%**（用错方案比答不出更贵） |
| citation / forbidden 门禁 | 现状值 | **不回归** |

### 工作项

#### 1.1 切片参数化 + chunk overlap

- **现状**：`knowledge/ingest.py::chunk_sections` 按段落边界切，`MAX_CHUNK_CHARS` 是
  模块常量，**无 overlap**。段落级切割会切断跨段落论证。
- **方案**：
  - `ChunkingConfig`（`max_chars` / `min_chars` / `overlap_chars` / `split_granularity`），
    默认值由 1.2 的实验决定，不拍脑袋。
  - overlap 在**段落级**：上块尾段拼入下块头部；`overlap_chars` 是上限而非精确值
    （精确到字符会切碎句子）。行业推荐实验集为 **256 / 512 / 1024 token**，
    本项目按字符等价换算后纳入扫描网格。
  - 生效配置与 `PIPELINE_VERSION` 一起写入 `document_versions.metadata`（列已存在）。
    切片参数一变 `pipeline_version` 变，既有幂等键自动触发重切，**无需新机制**。
  - 边界：`overlap_chars >= max_chars` 必须**报错**；单段超长按句号再切，仍超则原样
    成块并标 `oversized=true`。
- **交付物**：`ChunkingConfig` + overlap + `pipeline_version` 记录。
- **验收标准**：单测覆盖零 overlap、上限、单段超长、`overlap >= max` 报错、空文档、
  纯表格；同文档两组配置产出**不同且可复现**的 chunk 集；重切幂等。

#### 1.2 chunk size / overlap 调优实验

- **方案**：`scripts/tune_chunking.py` 在固定语料上扫 `(max_chars, overlap_chars)` 网格，
  测 **recall@5 / recall@10 / MRR / 平均 chunk 数 / 摄取耗时**，产出
  `tests/artifacts/chunking_tuning.json`。用固定语料——评测读活租户数据不可复现。
- **交付物**：脚本 + 报告 + 由报告确定的默认值。
- **验收标准**：报告含每配置完整指标与推荐理由；默认值可追溯到报告中一行；
  换默认值必须同时更新报告。

#### 1.3 多路召回扩展（含 typo 容错）

- **现状**：两路（FTS `websearch_to_tsquery('simple')` + pgvector）。纯词法匹配对
  型号、故障码、拼写错误无能为力。
- **方案**（保持 RRF 融合，逐路独立开关以便归因）：
  - **第三路 trigram**（`pg_trgm`，Postgres 内建，**已确认全仓库未使用**）+
    `gin_trgm_ops` 索引。解决 typo 与型号/故障码这类精确 token。
  - **第四路术语/别名扩展**：新增 `knowledge_aliases`（tenant, term, alias, weight）。
  - 每路候选数与权重进 `config.py`，不再写死 40。
  - **检索深度对齐行业实践**：retrieve top-20 → rerank → 送 top-5。
- **交付物**：两路新召回 + 索引迁移（`0033`）+ 别名表与维护入口。
- **验收标准**：typo 与型号类用例 recall 提升且门禁不回归；**每路单独关闭后指标
  变化可测**（证明每路都在起作用）；跨租户负向测试覆盖别名表与 trigram 路。

#### 1.4 query 重写的生产接线与扩展

- **现状**：`conversation.rewrite_query` 已实现（指代消解 + 省略补全，确定性、可审计），
  改写结果已落 `retrieval_config.rewritten_query`，但入口没有真实历史。
- **方案**（仍不引入 LLM 改写，理由：路由决策不能非确定，且改写必须可复现）：
  - **口语归一化词典**与 1.3 的别名表**共用同一份数据**，避免两套词表漂移。
  - **实体保护**：型号、故障码、订单号在改写时**逐字符保留**，不参与词干化与停用词
    过滤。这是改写最大风险面——把 `EC-504` 改写掉就再也召不回。
- **交付物**：归一化 + 实体保护 + 单一数据源。
- **验收标准**：型号/故障码改写前后**逐字符相同**（单测）；口语 query recall 提升；
  改写关闭时行为与开启前一致。

#### 1.5 metadata 过滤接线

- **现状**：`documents.metadata` 与 `chunks.metadata` 是 JSONB，**迁移已做、字段已存在、
  检索期完全不用**——审计点名的"有字段无消费方"。
- **方案**：
  - `MetadataFilter` 值对象 → `hybrid_search` 生成 JSONB 包含谓词（`metadata @> :filter`），
    全部绑定参数。
  - 维度：产品线、设备型号、硬件版本、固件版本、地区、语言、文档类型、敏感级、
    生效日期区间。
  - 来源：① 摄取时从 front-matter 抽取；② 运行时由 `intent.IntentDetection` 识别实体。
  - **关键取舍**：识别不到实体时不加过滤（宽召回）；**但**问题明确指向某型号而证据
    来自另一型号时必须弃权。
- **交付物**：`MetadataFilter` + 抽取器 + 与意图对接。
- **验收标准**：型号不匹配时**弃权**（新增 eval 用例）；跨租户与跨型号双重负向测试；
  过滤开/关指标对比报告。

#### 1.6 非纯文本知识（表格优先，图片仅评估）

- **现状**：PDF（`pypdf`）与 DOCX（`python-docx`）**只抽纯文本**。表格被拉平，行列表头
  关系丢失；图片不处理。
- **方案**：
  - **表格**：识别 DOCX 表格与 PDF 表格块，转 markdown 表格并**整表作为单个 chunk**
    （禁止跨行切分，否则"第 3 行的保修期"无从对应）；`chunk.metadata.content_kind="table"`。
  - **图片**：**本阶段只出评估结论，不实现**。OCR 需新依赖（违反约束 1）且质量与成本
    需先论证。产出图片在真实语料中的占比、必要性、可行方案与代价，作为独立 ADR 输入。
- **交付物**：表格解析 + `content_kind` 标记 + 图片评估结论。
- **验收标准**：表格类问题答案正确且引用指向表格 chunk；表格 chunk 不被 overlap 拆散。

#### 1.7 top-k 与 rerank 策略化

- **现状**：`top_k` 已可配；rerank 有 deadline 与降级。
- **方案**：
  - **按 Scene 的 top-k 档位**：政策类要广（证据分散），故障码类要窄（精度敏感）。
  - **rerank 后相对阈值裁剪**：低于阈值不送模型。阈值必须**相对**
    （`score / top_score`）——RRF 分数绝对值极小，绝对阈值必然失效（审计已记录该坑）。
  - **只对 top-N 做 rerank**（N ≤ 2×top_k）。
- **交付物**：Scene 档位 + 相对阈值 + rerank 候选上限。
- **验收标准**：token 消耗下降且 `citation_coverage` 不回归；阈值开/关对比报告；
  不同 Scene 的 top_k 可独立配置且被 `retrieval_config` 记录。

#### 1.8 口语化与模糊表达召回（体验优化主题）

- 由 1.3（trigram）+ 1.4（口语归一 + 实体保护）+ Phase 2（澄清）共同承担，不新增机制。
- **关键原则**：模糊 query 宁可**澄清**也不要乱召回——错误召回产出自信的错答案，
  澄清只多一轮。
- **交付物**：三类模糊输入（typo / 口语 / 指代省略）对照报告。
- **验收标准**：每类有 recall 或澄清率数据；**无新增"高置信度错答"**。

### Exit gate

- 检索参数**零硬编码**（grep 常量字面量为 0）。
- 召回质量可测量：`tune_chunking.py` 报告 + 每路开/关对比。
- `recall@10 ≥0.90`、上下文精确率 `≥0.70` 达标并成为门禁。
- metadata 过滤上线，型号不匹配弃权。
- 新行为全部 flag 门控，关闭时指标与 Phase 0 基线一致。

## Phase 2 — 记忆与上下文

覆盖主题：对话交互（多轮对话、短期/长期 memory、主动追问时机、对话总结、
历史与当前冲突以谁为准）、上下文管理（记忆、上下文压缩）。

### 目标

把平台从无状态问答（L0）变成"记得住、会追问、不丢承诺"（L3）。
审计确认多轮此前**完全不存在**，根因是 `ChatwootClient` 没有拉取会话历史的方法。

### 量化目标

| 指标 | 基线 | 目标 |
|---|---|---|
| 指代消解成功率（第二轮命中正确政策） | 不适用（无多轮） | **≥90%**（固定用例集） |
| 跨会话记忆命中率 | 不适用 | **100%**（客户属性在后续会话可用） |
| 凭据/PII/助手声称入库条数 | 不适用 | **0**（三条负向测试） |
| 上下文渲染大小上界 | 无上界 | 100 轮对话下有**明确上界** |
| 丢弃钉住项次数 | 不适用 | **0**（超限即告警） |
| 澄清后转人工率 | 不适用 | 连续追问达上限后 100% 转人工 |

### 工作项

#### 2.1 对话轮次持久化

- **方案**：新表 `conversation_turns`（`tenant_id` / `conversation_ref_id` / `role` /
  `text_redacted` / `text_hash` / `ts` / `ref`）。迁移 `0034`，FORCE RLS + 策略 + GRANT。
- **关键取舍**：存**脱敏文本**而非原文。原文只在 Chatwoot（`docs/security.md`）；
  但记忆若只存哈希就无法用于指代消解。折中即"入库前过
  `evaluation/pii.redact_text`"，并加入 `evaluation/pii.py::RetentionPolicy`。
- **交付物**：迁移 + ORM + 读写服务 + `RetentionPolicy` 登记。
- **验收标准**：`downgrade base && upgrade head` 通过；`EXPECTED_MIGRATIONS` bump 到 34；
  跨租户隔离测试；保留期清扫覆盖新表；凭据/PII 不落库（负向测试）。

#### 2.2 Chatwoot 历史拉取

- **方案**：`support_bridge/chatwoot_client.py` 新增
  `list_messages(account_id, conversation_id, limit)`，走已文档化的 REST API，
  复用 `integrations/resilience` 的断路器与退避。
- **降级契约**：拉取失败**不阻断**本轮，退化为单轮并在 trace 标
  `context.history_unavailable=true`。多轮是增强，不是依赖。
- **交付物**：客户端方法 + 契约测试（payload fixture）+ 降级路径。
- **验收标准**：契约测试覆盖正常/空/畸形 payload；拉取超时时单轮回答仍成功且有标记。

#### 2.3 历史注入 orchestrator

- **方案**：`inbox_consumer` 新增 `load_history(event, deps) -> list[Turn]`，合并本地表与
  Chatwoot 实时拉取（本地优先，用于补齐 Chatwoot 已过期的窗口），传入
  `orchestrator.run(history=...)`。
- **交付物**：历史加载 + 接线。
- **验收标准**：**集成测试证明第二轮能解析指代**——先问年付退款窗口，再问"那月付呢"，
  第二轮必须命中月度政策且 `retrieval_config.query_rewritten=true`。

#### 2.4 短期 memory 参数化与可观测

- **现状**：`ConversationMemory`（预算化压缩、钉住义务项、确定性摘要）已实现，参数是
  类默认值；指标已在 0.3 补。
- **方案**：预算 / `recent_turns` / `max_turns` 进 `config.py`；`context_pins_evicted`
  超阈值 WARN + 告警——**钉住的义务被挤掉意味着平台丢了一个承诺**，这是必须告警的事件。
- **交付物**：配置项 + 告警阈值。
- **验收标准**：超长对话下钉住项仍在（单测）；挤掉时产生指标与 WARN。

#### 2.5 长期 memory 持久化

- **现状**：`DurableFact` 提取与"永不入库清单"已实现，**但只在内存里**。
- **方案**：新表 `contact_facts`（`tenant_id` / `contact_ref` / `key` / `value` /
  `source_turn_id` / `confidence` / `updated_at` / `expires_at`）。迁移 `0035`。
  - **写**：run 结束时落 `extract_durable_facts` 结果。
  - **读**：run 开始时加载并合并进 `CompactedContext.durable_facts`。
  - **冲突规则**：**当前表达覆盖历史**（`ON CONFLICT (tenant, contact_ref, key) DO UPDATE`）。
    客户改口是常态，"以最新陈述为准"是唯一不需要额外仲裁的规则。
  - **只读客户轮次**：助手自己的声称不得成为记忆来源（防模型自反馈）。
- **交付物**：迁移 + 模型 + 读写 + 双向接线。
- **验收标准**：跨会话记住 plan；改口后以新值为准；凭据/PII/助手声称**永不入库**
  （三条负向测试）；跨租户隔离。

#### 2.6 对话总结强化

- **现状**：`_summarize` 是确定性首行抽取（刻意不用 LLM，保证可 diff、可回归）。
- **方案**：改为**滚动摘要**——每次压缩把"旧摘要 + 本次被丢弃轮次"合并重排，仍不调模型。
  钉住项走独立通道，不进摘要（避免重复计费与语义稀释）。
- **交付物**：滚动摘要 + 大小上界。
- **验收标准**：100 轮对话上下文渲染大小有明确上界（单测）；同输入两次摘要**逐字节一致**；
  钉住项不在摘要中重复。

#### 2.7 上下文与证据的预算分配

- **方案**：当前证据与上下文各有字符预算但**互不感知**。改为显式分配：**证据优先**，
  上下文用剩余额度，冲突时证据优先并记 `context.budget_reduced_for_evidence=true`。
- **理由**：回答必须由证据支撑；上下文丢了会退化但不出错，证据丢了会直接弃权或幻觉。
- **验收标准**：超长对话 + 大量证据时证据不被截断（单测）；预算不足时有指标与标记。

#### 2.8 主动追问时机策略化

- **现状**：`needs_clarification`（4 种原因码）+ `_finish_clarify`（**不释放租约**——
  澄清等回复，转人工结束参与，两者必须区分）已实现。
- **方案**：追问策略按 Scene 分化——订单类缺订单号必问；政策类除非完全无主题否则不问。
  加**追问次数上限**（连续 N 次未澄清转人工），避免追问死循环。
- **验收标准**：连续追问达上限后转人工（有测试）；澄清**不进入**转人工率指标
  （已在 `_finish_clarify` 中按 `abstained` 而非 `handed_off` 计数）。

### Exit gate

- 第二轮能解析指代，有集成测试。
- 跨会话记住客户属性，改口以最新为准。
- 凭据/PII/助手声称**永不入库**，有负向测试。
- 上下文有上界、可审计（`model_config.conversation` 快照）、可降级（历史不可用退单轮）。

## Phase 3 — Agent 与工具调用

覆盖主题：实时与集成（查订单/物流、CRM/订单/工具集成、业务工具生态）、
Agent 能力（如何判断调哪个 tool、multi-agent、共享 context）。

### 目标

把工具层从"4 个写工具、无选择逻辑"（L2）变成"有读工具、能选择、能合成答案"（L3）。
审计确认 `registry.py` 只注册 `jira.create_issue`、`linear.create_issue`、
`crm.update_account`、`im.send_notification`——**没有任何读类业务工具**，且
`tool_gateway/router.py` 由调用方显式指定 `tool_name`，**没有选择逻辑**。

### 量化目标

| 指标 | 基线 | 目标 |
|---|---|---|
| 读类业务工具数 | **0** | **≥4** |
| 工具选择确定性 | 不适用 | 同输入同输出，**100% 可审计** |
| 无候选时的行为 | 不适用 | **100% 转人工**，0 次编造 |
| 读工具成功率 | 门禁已存在（≥99%） | 新工具**自动纳入**同一门禁 |
| 实时数据走工具的比例 | 不适用 | **100%**（不进 RAG） |
| 工具回执可引用 | 不可 | 引用来源可区分 `document` / `tool` |

### 工作项

#### 3.1 工具选择

- **方案**：新增 `tool_gateway/selector.py`。
  - **候选集**：`registry.TOOL_CAPABILITY` 中能力已被租户连接器满足的工具
    （未连接的能力直接出局，不是运行时报错）。
  - **打分**：意图（`intent.IntentKind`）× 工具声明（`input_schema` 必填项是否可由
    已知实体满足）× 场景匹配。
  - **铁律**：选择器只产出**候选与参数**。授权仍由 policy 决定，写操作仍需确认。
    `docs/agent.md` 的"LLM 可提议、不可绕过授权/确认/幂等/后置校验"不得松动。
  - **无候选时**：转人工并说明原因，**不得**编造或降级成知识问答。
- **交付物**：选择器 + 与 intent 对接 + 决策审计事件。
- **验收标准**：给定（意图，连接器集合）结果**确定且可审计**；无候选时转人工（有测试）；
  越权提议被 policy 拒绝（负向测试）。

#### 3.2 业务读工具生态

- **方案**：新增读类工具，risk=`read`，走既有注册表 + 适配器模式：
  `order.get_status`、`shipment.track`、`billing.get_invoice`、`case.read`
  （`case.read` 已在 `tests/evals/dataset.py` 的 `allowed_tools` 声明却从未注册，本次落地）。
- **交付物**：4 个读工具适配器 + 注册表条目 + 契约测试。
- **验收标准**：每个工具有契约测试；自动被既有 `aggregate_read_tool_outcomes` 的
  ≥99% 门禁覆盖；第三方故障与自身故障被正确区分。

#### 3.3 实时数据不进 RAG（ADR）

- **方案**：ADR 明确"订单状态、物流轨迹、账户余额等**易变事实**走 Tool，RAG 只承载
  稳定知识"。理由：进了索引即过期，且过期数据会被自信引用。
- **验收标准**：ADR 合入；eval 新增"实时数据必须走工具"用例——未接工具时**必须弃权**
  （当前行为），接工具后返回真实值且引用类型为 `tool`。

#### 3.4 工具结果回填与答案合成

- **现状**：QA 路径**只从文档证据生成**，工具回执不进生成。
- **方案**：
  - 读工具回执作为**第二类证据**进入生成，引用来源区分 `document` / `tool`。
  - `Citation` 需表达工具回执：`source_uri` 承载回执引用，`excerpt_hash` 承载回执哈希；
    `document_version_id` 对工具来源置空需迁移允许 NULL（迁移 `0036`）。
  - **失败即弃权**：工具超时/返回歧义 → 弃权转人工，绝不猜测。网关的 `UNKNOWN` 语义
    已保证这点，此处只需不吞掉。
- **交付物**：工具证据通道 + 引用类型 + 迁移。
- **验收标准**：订单状态类问题能回答且引用指向工具回执；工具失败时弃权（有测试）；
  引用来源在审计中可区分。

#### 3.5 multi-agent 与共享 context 的决策

- **决策**：**不实现通用 multi-agent**。当前单 Agent 确定性流水线在授权、幂等、审计三处
  都依赖"单一决策点"，拆成多 Agent 会把这三处变成分布式一致性问题；收益是并行度，
  而当前瓶颈是检索与模型延迟，不是编排。
- **替代方案**：按 Scene 做**子流程分派**（同进程、共享 Case 与控制租约、共享
  `ConversationMemory`，**不共享对话原文**——原文按需从 Chatwoot 取，避免多份副本各自脱敏）。
- **触发条件**（写进 ADR）：出现独立的审批型 Agent、或单一 Scene 的编排复杂度超过
  可维护阈值时，重新评估。
- **验收标准**：ADR 合入；**跨 Scene 切换集成测试**——同一 conversation 从 BILLING 切到
  TECHNICAL_SUPPORT，上下文与 Case 不丢、控制租约不冲突。

#### 3.6 CRM / 工单集成深化

- **方案**：补齐入站方向（提供方 webhook → 更新本地资源映射）与同步游标消费方，
  使 `SyncCursor` / `DeadLetterItem` 不再是"有表无消费者"。
- **验收标准**：双向同步集成测试；死信可列出并可重放（有测试）。

### Exit gate

- ≥4 个读工具上线，工具成功率门禁自动覆盖。
- 工具选择确定、可审计，无候选时转人工。
- 工具回执能进答案且有引用类型区分。
- multi-agent 有决策记录与触发条件，跨 Scene 切换有测试。

## Phase 4 — 质量、可信与评测

覆盖主题：质量与可信（幻觉抑制、知识生命周期、评测体系、LLM-as-a-judge）、
数据处理（清洗、标签的治理侧）。

### 目标

让"好不好"变成可测量的数，而不是可争论的观点。审计确认当前评测只能给出一个
`passed` 布尔，**无法区分"检索错"与"生成错"**——这是评测体系最大的洞。

### 量化目标

| 指标 | 基线 | 目标 |
|---|---|---|
| 评测归因能力 | **0**（只有布尔） | 每用例带归因标签（4 类） |
| 归因准确率（人工抽检） | 不适用 | **≥90%** |
| judge 与人工一致性（Cohen's kappa） | 不适用 | **≥0.6**（低于则 judge 不上线） |
| 引用支持性 guard 误报率 | 未测量 | **0**（误报才可转 guard） |
| 数据集规模 | 23 用例 / **11 类** | **≥100 用例**，每类 ≥5 |
| 清洗去重率 | 不适用 | 有报告；误删率抽检 **≤1%** |
| 标签覆盖率 | **0%** | **≥80%** 的 chunk 带结构化标签 |
| 人工评测闭环 | 无 | 抽样 → 标注 → 一致性统计可走通 |

> **顺带修正一处文档与代码的不一致**：`tests/evals/dataset.py` 的模块注释说
> "twelve documented categories"，而 `EvalCategory` 实际只有 **11** 个成员
> （`CATEGORY_CASES` 也恰好填满 11 个，无遗漏）。扩数据集时一并把注释改成 11，
> 或补上第 12 类——**不要让注释描述一个不存在的东西**，这正是本次审计反复命中的
> 缺陷形状。

### 工作项

#### 4.1 检索 / 生成归因（最高优先）

- **方案**：
  - `EvalCase` 增 `expected_version_keys`（该问题**应该**命中哪些语料）。
  - `evaluation/runner.py` 计算 `recall@k` / `MRR`，给出归因枚举：
    `PASS` / `RETRIEVAL_MISS` / `GENERATION_ERROR` / `ABSTENTION_ERROR`。
  - 新增门禁 `min_retrieval_recall_at_k` 进 `evaluate_release_gates`。
- **为什么一次命中多条**：这一项同时解决"分别评估检索与生成"、"判断检索正确但生成错误"、
  "Bad Case 归因"、"修复后证明解决"四个问题——它们是同一能力的四种问法。
- **交付物**：`EvalCase` 扩展 + runner 归因 + 新门禁 + 报告字段。
- **验收标准**：报告含每用例归因标签；≥3 条用例演示不同归因；`release_check` 输出新门禁；
  归因结果**自动写入 `gap_service` 队列**（打通数据飞轮）。

#### 4.2 引用支持性校验（幻觉抑制最后一环）

- **现状**：`validate_citations` 只校验引用**存在**，不校验声明**被支持**。
  `claim_contradiction_candidates` 已实现矛盾检测但**刻意只作 metric 不作 guard**
  （注释记录：6 对样本 1 个误报，误报会把正确答案变弃权）。
- **方案**：① 全量数据集测精度/召回并出报告 → ② 精度达标后作为 **flag 门控 guard**，
  默认关闭 → ③ 灰度期对比 `forbidden_claim_rate` 与 answerable 回归，达标才全量。
- **铁律**：**误报为 0** 才可转 guard。误报把正确答案变弃权，比漏检更差。
- **验收标准**：报告含精度/召回与样本量；flag 关闭时行为与现状**逐字节一致**；
  开启后 `forbidden_claims` 改善**且 answerable 零回归**。

#### 4.3 LLM-as-a-Judge

- **方案**：`evaluation/judge.py` 复用现有 `ChatProvider`，对
  **correctness / relevance / faithfulness** 三维打 rubric 分。
  - **judge 必须先被验证**：在人工标注子集上算与人工的一致率（**Cohen's kappa ≥0.6**）。
    不达标不上线——未验证的 judge 是给评测体系加噪声。
  - **成本控制**：只对 deterministic 判定为 `PASS` 的用例抽样送 judge（确定性判定已能
    抓的错误不必花模型钱）；抽样比例可配。这也符合成本基线里"p95 成本"的关注点。
  - **judge 结果只作 metric 不作门禁**，直到一致性达标且有稳定性证据（同输入多次运行
    分数方差可控）。
- **交付物**：judge + 一致性报告 + 抽样配置。
- **验收标准**：报告含样本量与 kappa；judge 不可用时评测**降级为 deterministic 结果
  而非失败**；重复运行方差有报告。

#### 4.4 人工评测流程

- **方案**：`evaluation/review.py`（抽样、标注、一致性统计）+ admin-web 新增"评测复核"页
  （复用 `useAsync` / `useAction` / `ActionFeedback`，不用 `alert()`）。
- **验收标准**：抽样 → 标注 → 一致性统计闭环可走通；标注落库且有审计；
  前端 `tsc` + `vite build` 通过。

#### 4.5 知识生命周期补强

- **方案**：
  - **owner 字段**：每条知识有责任人。
  - **可信度/权威度分级**：官方文档 / 内部 wiki / 客户提供；冲突时高权威优先——当前
    `_sources_compete` 只能发现冲突后转人工，有分级才能**裁定**。
  - **定期复审**：按 `expires_at` 与 `last_reviewed_at` 生成复审任务，复用
    `gap_service` 的 draft/review/publish 模式与 `sla_consumer` 的扫描模式。
  - **冲突裁定工作流**：把 `CONFLICTING_SOURCES` 弃权事件升级成待裁定条目。
- **验收标准**：临近过期产生复审任务（有测试）；冲突可裁定且留痕；权威度影响检索排序
  且可配置。

#### 4.6 数据清洗与标签体系
- **方案**：
  - **清洗**（插进 `ingest` 状态机，不新建流水线）：内容哈希去重、空白/编码规范化、
    页眉页脚与页码噪声移除、语言识别。每步可开关，前后留存对比。
  - **标签体系**：与 1.5 的 metadata 过滤**共用同一套键**（产品/型号/硬件版本/固件版本/
    地区/语言/文档类型/敏感级），摄取时抽取 + 人工校正入口。
- **验收标准**：清洗前后对比报告（去重率、噪声移除量、误删率抽检 ≤1%）；标签覆盖率
  ≥80%；标签驱动检索命中（与 1.5 联动）；清洗可关闭且关闭时行为不变。

#### 4.7 上线验收清单与 incident runbook

- **方案**：文档化"AI 客服上线验收标准"（安全/质量/成本/延迟/回滚五维阈值，与
  `release_check` 门禁对齐）+ incident runbook（错误回答激增时：kill switch →
  prompt 回滚 → 租户级停用 → 复盘）。
- **验收标准**：清单每条阈值都有对应门禁或指标；runbook **桌面演练走通且记录在案**。

### Exit gate

- 评测能给出**归因**，不再只有一个布尔。
- `retrieval_recall_at_k` 门禁生效；judge 有验证报告且 kappa ≥0.6。
- 清洗与标签进入摄取流水线且有覆盖率指标。
- 幻觉 guard 有精度证据，默认关闭可灰度。
- 数据集扩到 ≥100 用例。

## Phase 5 — 工程治理与体验（达标 L3/L4）

覆盖主题：工程治理（成本与延迟治理、高并发、兜底策略与转人工）、
体验优化（首字延迟、单位成本）。

### 目标

把成本、延迟、并发从"没出事"变成"有预算、有上限、有降级"，并把质量/延迟/成本
三条曲线同时钉在企业基线上。

### 量化目标

| 指标 | 基线 | 目标 |
|---|---|---|
| 单位会话成本 p50 | 未测量 | **≤1 美分** |
| 单位会话成本 p95 | 未测量 | **≤5 美分** |
| 每会话 LLM 调用数上限 | 无 | **≤10**，触限优雅转人工并记事件 |
| 总延迟 p95 | 未测量（已有 histogram） | **< 8 s**；backstop **20 s** |
| TTFT p95（流式后） | 不适用 | **< 1.5 s**；p99 **< 3 s** |
| p95 切分维度 | 无 | 按模型 / 租户 / **首轮 vs 后续轮** |
| 并发上限 | 无 | 有信号量 + 背压；超限 **429** 而非堆积 |
| 压测报告 | 无 | 并发 → 吞吐/延迟/错误率曲线，标出拐点 |
| 退避抖动 | **无** | `jitter_ratio` 默认 0.3，重试峰值下降有数据 |
| 转人工携带证据 | 无 | **100%** 含 `reason_code` + 证据引用 |
| 模型降级链 | 无 | 主 → 备 → 弃权，降级事件有指标 |

### 工作项

#### 5.1 成本治理

- **方案**：
  - **token 预算闸门**：每 run / 每租户 / 每窗口三级上限，超限**降级**（缩短证据、
    降 top-k）而非直接失败。复用 `identity/usage.py` 配额模式与 `billing` 账本。
  - **硬限制**（对齐行业实践）：每会话最大 LLM 调用数 10、每调用最大 token、
    每会话成本上限；触限**优雅转人工并记录事件**（用于判断是限制太紧还是 agent 卡住）。
  - **小模型路由**：分类、query 改写、judge 等**非客户可见**调用走轻量模型，生成走主模型。
  - **prompt 缓存**：相同证据哈希 + 相同 prompt 版本可复用（仅 temperature=0 场景）；
    按行业基线，缓存 token 约便宜 50%，收益需核算。
  - **成本面板**：p50 / p95 / 按模型分布——**p95 必看**，最贵会话通常是重试循环。
- **验收标准**：单位会话成本 p50/p95 有 dashboard；预算超限时降级而非 5xx；
  触限事件可查；门禁不回归。

#### 5.2 延迟治理

- **方案**：
  - **先并行化，再流式**。可并行的先并行（意图分类与检索预处理、别名扩展与 FTS）。
  - **流式输出**：当前 `ChatProvider.complete` 非流式，首字延迟无法优化
    （`generator.py` 注释已记录该限制）。引入流式需改 provider 表面 + 发送路径
    （先发首段再补全）。**这是较大改动，需单独评估后定**。
  - **rerank 只对 top-N**（Phase 1.7 已含）。
  - **p95 按模型/租户/轮次切分**，避免聚合掩盖劣化。
- **验收标准**：并行化后总延迟 p95 有前后对比；流式落地后 TTFT p50 <500ms、
  p95 <1.5s、p99 <3s 有指标；总延迟 backstop 20s 告警生效。

#### 5.3 高并发

- **方案**：
  - **并发上限**：模型调用与检索加信号量，防止打爆下游。
  - **背压**：队列深度超阈值拒绝新入队（429，与现有配额拒绝同语义），不无界堆积。
  - **优先级队列**：临近 SLA 的 Case 优先。注意审计已记录
    "priority-queue admission 有实现无消费方"——本次**要么接线要么删除**，不留半成品。
  - **退避抖动**：`resilience.retry_delays` 当前**无抖动**，高并发下所有调用方同节奏
    重试形成同步峰值。加 `jitter_ratio`（默认 0.3）。
- **验收标准**：压测报告（并发 → 吞吐/延迟/错误率，标出拐点）；抖动开启后重试峰值下降；
  优先级队列有真实消费方。

#### 5.4 兜底策略与转人工强化

- **现状**：已达 L3（弃权必发通知、发送前租约复检、转人工释放租约）。**不重复实现**，
  只补两处：
  - **按 Scene 的兜底话术**：故障类与投诉类用不同措辞。
  - **转人工携带证据与失败原因**：`docs/agent.md` 要求"preserve the evidence and failure
    reason for the receiving agent"，当前 `_finish_abstain` 只写审计，未把证据摘要交给
    接收坐席。
- **验收标准**：转人工消息含 `reason_code` + 证据引用；坐席侧可见（集成测试）。

#### 5.5 模型降级链

- **方案**：主模型 → 备用模型 → 弃权转人工。flag 门控，降级事件有指标。复用
  `CircuitBreaker` 既有语义。
- **验收标准**：主模型故障时降级成功且 `model_fallback_total` 可观测；全链不可用时弃权
  （有测试）；**做一次模型宕机演练并记录**。

### Exit gate

- 成本、延迟、并发各有指标与上限，超限走降级而非故障。
- 退避有抖动，优先级队列有消费方。
- 转人工携带证据与原因。
- 模型有降级链且做过演练。
- 第 2 节全部量化目标有实测数字。

## 7. 风险与取舍

| 风险 | 影响 | 缓解 |
|---|---|---|
| 流式改造面大 | 5.2 可能拖累整阶段 | 先做并行化（低风险高收益），流式单独评估后再定 |
| OCR 引入新依赖 | 违反约束 1 | 1.6 只出评估结论，由 ADR 决定 |
| 多轮引入新攻击面 | 对话内容是比问题更长的不可信输入 | Prompt v3 规则 7 已声明对话为不可信数据；对话内容与证据同等脱敏 |
| 长期记忆存错东西 | 合规风险 | 三层防线：提取白名单 + `_NEVER_DURABLE` 拒绝清单 + PII 形态拒绝；三条负向测试 |
| 引用支持性 guard 误报 | 把正确答案变弃权 | 严格"误报为 0 才转 guard"，flag 默认关闭 |
| judge 不可靠 | 给评测加噪声 | kappa ≥0.6 才上线；先只作 metric |
| 迁移与门禁失配 | CI 红 | 每个迁移同步 bump `EXPECTED_MIGRATIONS`；`downgrade base && upgrade head` 必跑 |
| 评测读活数据不可复现 | 回归无法复现 | 沿用固定语料；真实链路报告只用于门禁 |
| 个人项目无真实流量 | 数字代表性受限 | 按第 3 节替代规则执行，并**如实标注**不可替代的部分 |

## 9. 对标数据来源

第 2 节的行业数字来自公开基准与厂商数据，用于**确定量级与方向**，不作为承诺：

- **containment / 自动解决率**：Teneo《Containment Rate Call Centre Benchmarks》、
  Alhena《AI Chatbot Containment vs Deflection Rate》、Talkative《Chatbot Containment
  Rate》汇总（经 simpli.support 归一）；Intercom Fin 规模化部署 76% 自主解决；
  MyAskAI 对 195 个真实部署的横断面（区间 15%–98.3%，强调"标题数字掩盖一切"）。
- **配对解读原则**："contained 也计入放弃与死路，必须与 CSAT、重开率配对"——
  来自 simpli.support 与 MyAskAI 的一致结论。
- **TTFT / 延迟**：chatzybot《Chatbot Response Time Targets》给出的 p50/p95/p99
  阈值与告警实践（含"按模型/区域/首轮-后续轮切分 p95"）。
- **成本**：CallSphere《Cost-Per-Conversation Tracking》给出的会话成本区间、
  人工对照（约 $7/会话）、缓存折扣（约 50%）与"必须设硬限制并记录触限事件"。
- **RAG 评测方法**：RAGAS 方法论文档——**不推荐绝对阈值**，要求以自身基线做相对对比
  并当作 CI 回归门禁；faithfulness 与 context recall 为最高信号指标；
  chunk size 实验集 256/512/1024 token；检索深度 retrieve top-20 → rerank → top-5。
