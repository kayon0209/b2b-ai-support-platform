# 最终外形与最后一公里（设计决策）

> 本文保留早期产品形态决策。当前坐席工作台的执行规格、参考图与状态请以 [工作台改版规格](workbench-redesign-spec.md) 为准。

> 依据：已上线产品的实测做法（Intercom Fin、Zendesk AI agents、Dynamics 365 Copilot、Decagon/Sierra，
> 以及国内合力亿捷的 62%→19% 改造实录）+ 本仓库现状（`docs/product-gap-analysis.md`）。
> 结论性文档：§2 定外形，§3 定最后一公里。**§4 起是可直接施工的设计。**

---

## 1. 参考对象：什么是共识、什么是差异、什么是陷阱

### 1.1 共识（做不做都要有，缺了会被认为"不完整"）

| 共识 | 谁在做 | 对我们的含义 |
|---|---|---|
| **三个数，不是一墙图**：自动化率 + 解决率 + 参与率 | Intercom Performance dashboard（Fin 的 automation / resolution / involvement rate 一屏） | 我们的 `/quality` 现在分散在多个卡片里，应收敛成三个数 + 趋势 |
| **会话自动聚成"类目"**，不靠人工打标 | Intercom Topics Explorer（自动 topic/subtopic）；Zendesk Intents | 我们有 `scene`/`business_line`/实体，但**没有"类目"这一层对象**——这是 §3 的核心 |
| **一张"接下来补什么"的清单**，按影响排序 | Intercom Recommendations；Zendesk automation potential report | 我们的 `/quality` 有 `automation_candidates`，但**只读** |
| **清单每一项带"缺的是什么"**，且**不同缺法对应不同动作** | Intercom Query type 四桶：Informational→补内容；Personalized→接数据连接器；Action-based→建动作；Investigative→转专家 | **这是最关键的一条**，直接决定 §3 的设计 |
| **一键修**，不是"给你个报告自己想办法" | Intercom 明说 "in clicks, not hours" | 我们的缺口→草稿→发布链路已有，缺的是从类目直接进去 |
| **每周趋势用大白话讲"什么变了、为什么"** | Intercom Trends | 我们有意图分布趋势，缺"变化 + 归因"的叙述 |
| **转人工必须带全上下文** | 国内案例把它列为**改造第一优先级** | 我们刚修完这条（弃权通知此前在渠道上根本没送达） |
| **每个答复可解释** | Decagon 的 message analysis（可追问"为什么给这个订单选了 Track Order 动作"） | 我们的 `/conversations` 回放已有，按哈希关联轮次 |

### 1.2 差异（选型差异，不是对错）

| 差异 | 代表 | 我们的取舍 |
|---|---|---|
| **"按解决收费"** | Sierra / Decagon 的 outcome pricing（billed per fix） | **采纳其纪律，不采纳其计费**：它逼出一件事——"解决"必须**严格定义**。AI 说了一句话 ≠ 解决。见 §3.4 |
| **Agent as code**（声明式、可版本化） | Sierra Agent SDK | 我们已有 prompt 发布 + feature flag 版本化。自然延伸是**类目级自动化配置可版本化、可回滚** |
| **原生工具执行**（自己发起退款、改单） | Decagon（Stripe 退款、建 Salesforce 工单） | 我们的 Tool Gateway 已有授权/确认/幂等/后验。**但卡片上没有确认入口**（gap doc C1）——这是要补的 |
| 要不要多 Agent | Intercom/Zendesk 都是**单 Agent + 工具**，不做多 Agent 分发 | 与 ADR 0007 一致，**不改** |

### 1.3 陷阱（别人踩过，我们正在踩或容易踩）

| 陷阱 | 出处 | 我们的状态 |
|---|---|---|
| **追 100% 自助解决率** | 国内案例列为陷阱一；正确配比是 AI 接 70–80% 标准化、人工 20–30% 复杂 | 我们的清单里 `8.5` 指标看板没有目标值概念，容易变成"越高越好" |
| **知识库建好就完事** | 陷阱二：上线 3 个月后转人工率反弹 | 我们**没有运营节奏**（新政策 48h 内更新 / 新问题出现 3 次即评估 / 每月复盘盲区） |
| **忽视转人工体验** | 陷阱三，且**改造优先级明确：先修转人工平滑通道，再提升 AI 能力** | 我们刚补上通知送达，但"不重复描述"还依赖坐席自己看 |
| **"AI 能回答 ≠ AI 能解决"** | 国内案例核心判断 | 我们的 `route` 已经区分了知识问答/业务读/业务写，方向对 |
| **知识库"假性覆盖"** | 检索得到片段，但片段答不了这个问题 | 我们的 `decide_abstention` + 引用校验已经在防，但**没进运营视野**（假性覆盖应是一类独立缺口） |

## 2. 最终外形：三个界面 + 一个闭环

### 2.0 一个前提：我们不是电商

华秋的客户是**工程师和采购**，不是消费者。问题域是订单/交期、库存/料号、工艺能力、报价、品质异常。
所以：**不要抄电商的营销话术和"猜你喜欢"**。清单自己也写了"工程师对浮夸话术反感"。
我们要抄的是**结构**（三界面、一闭环、卡片、清单），不是**语气**。

### 2.1 界面一 · 客户侧对话窗（`/support`）

一页，三段：

```
┌────────────────────────────────────────────┐
│ 对话流（AI / 人 / 系统事件 同一条时间线）        │
│                                              │
│  客户：我昨天下的单能加急吗                      │
│  ┌──────────────────────────────┐            │
│  │ 数据卡片：订单 SO-9001          │  ← 一等公民 │
│  │  节点时间轴：已下单→已审核→…    │            │
│  │  数据更新于 3 分钟前 · 来源 ERP  │            │
│  └──────────────────────────────┘            │
│  AI：加急属改价类，已记录，9:30 前专员联系您      │
│  ┌──────────────────────────────┐            │
│  │ 动作卡片：确认申请加急（¥XX）    │  ← 新增     │
│  │  [ 确认 ]  [ 先不改 ]           │            │
│  └──────────────────────────────┘            │
└────────────────────────────────────────────┘
```

**要改的两处**
1. **卡片从只读变可动作**。目标形态里"客户确认 → 系统改单"这一步，现在只能靠文字往返。
   动作卡片走既有 Tool Gateway：授权 → 确认 → 幂等 → 后验，**不新开一条写路径**。
2. **身份闸门的前置形态**。未验证时不出现任何业务数据卡，只出现一张"验证身份"表单卡
   （单号 + 手机尾号）——把 2.2 从"接口"变成"界面上的一个卡"。

**不做的**：猜你喜欢、营销浮层、会话中途的满意度弹窗（满意度放在会话结束后，7.10）。

### 2.2 界面二 · 坐席工作台（`/workbench`）

三栏：

```
┌──────────┬────────────────────────┬──────────────────┐
│ 队列      │ 会话流                  │ AI 副驾            │
│ 未指派     │  ┌──────────────┐      │ 建议话术（可编辑后发） │
│ 我的       │  │ 同一套数据卡片 │ ← 同  │ 已查数据 + 引用来源   │
│ 等待中     │  └──────────────┘      │ 相似工单            │
│          │  客户原话 / AI 草稿 / 人的 │ 该类目历史状态：      │
│          │                        │  「PCB·交期」上周      │
│          │                        │   自动化率 0%，在补   │
└──────────┴────────────────────────┴──────────────────┘
```

**要改的三处**
1. **卡片组件与客户侧是同一个**。现在客户看到时间轴卡片、坐席看到一段文字，同一个事实两种呈现。
   这是"不用切系统"的物理前提。（删 `DataCard.tsx`，统一到 `ToolCard`。）
2. **左栏加"未指派队列"**。现在 `/workbench/:caseId` 只能从案例进，坐席得先知道案例号。
3. **右栏加"该类目历史状态"**——这是闭环回流到坐席的那一半（§3.3 协同）。
   坐席能说"这一类我们正在补，目前 X%"，而不是每次从零开始。

### 2.3 界面三 · 运营后台：三页一条主线

现状是 `/quality` + `/gaps` + `/knowledge` 三个平级页面，**没有主线**。参考对象都收敛成一条：
**表现 → 该补什么 → 知识**。

```
① 表现 Performance         ② 该补什么 Recommendations        ③ 知识 Knowledge
   自动化率 / 解决率 / 转人工率   按影响排序的类目清单，每行：      语料 · 缺口 · 修正回流
   + 趋势（按业务线/类目拆）       类目 · 量 · 自动化率 · 缺什么 · [动作]
```

**② 就是最后一公里的家。** 现在它叫"自动化候选"，只读；要变成可操作。

### 2.4 一个闭环：四个动作的落点

| 环节 | 落点 | 现状 |
|---|---|---|
| 识别 | ② 的清单自动算出"哪些类目在漏、漏多少" | 有表，无类目层 |
| 拦截 | ② 每行可**标记为候选** → 进入待办 | ❌ 无动作 |
| 协同 | 类目状态进 AgentRun 快照 → 坐席右栏可见 | ❌ 无 |
| 闭环 | 上线后显示**标记前 vs 标记后**自动化率 | ❌ 无回链 |

### 2.5 界面数量：4 → 3

`/chat` 是内部验证面（ADR 0010）。要么并进工作台的调试抽屉，要么明确标注仅内部。
用户要的是三个界面，这一步要做，但不阻塞闭环。

## 3. 最后一公里：机制设计

### 3.1 核心判断

**"该自动化什么"不能只按量排序，要按"缺什么"分流。**

Intercom 的 Query type 四桶是这条的最强证据：同一句"我的订单到哪了"和"帮我改一下收货地址"，
量可能一样，但前者要补内容、后者要接动作——**修法完全不同，混在一张榜上就没法行动**。

我们比 Intercom 有利：**需要的信号已经在库里了**，只是没有汇总成类目维度。

### 3.2 类目与"缺什么"：从已有信号映射，不新增埋点

```
IssueCategory（确定性派生，可版本化）
  = business_line × scene × 关键实体槽位
  例: pcb × order_status × {has_order_ref}
  例: components × stock_query × {has_part_no}
  例: pcb × expedite_request × {has_order_ref}   ← 演示故事里的那一类
```

派生**只用 AgentRun 已有字段**（`intent` 快照 + `route` + `abstain_reason` + 拦截原因），
所以**统计不需要迁移**——和 8.7 意图分布同一个做法。

`fix_type` 从已有信号映射：

| fix_type | 触发信号（已有） | 一键动作 |
|---|---|---|
| `content` | 无依据拒答 / 检索为空 / 引用不足 / 假性覆盖 | → 缺口队列 → 起草知识 |
| `data` | 工具未配置 / 连接器不可用 / `found:false` | → 连接器配置页 |
| `action` | 需要写但被拦（红线 / 未挂审批） | → 工具与审批配置 |
| `routing` | 高危 / 情绪 / 显式要人 / 重复失败 | → 技能组路由规则（**这类本就不该自动化**，清单 6.4/7.1 明确） |
| `policy` | 业务规则（非标、议价、赔付） | → 标记为"人工专属"，**从自动化候选里移除** |

**`routing` 与 `policy` 两桶必须能"关掉"**——否则清单会一直推荐自动化那些本来就不该自动化的类目，
这正是"追 100% 自助解决率"这个陷阱的入口。

### 3.3 状态机与四个动作

```
observed ──标记──> candidate ──开始补──> automating ──上线──> automated
   │                                                          │
   └────────────── policy/routing：直接 → human_only ──────────┘
```

1. **识别**：清单 = 按 `量 × (1 − 自动化率)` 排序的类目，带 `fix_type` 与样本问法。
2. **拦截**：每行可标记 → `candidate`（记谁标的、什么时候）。
3. **协同**：类目状态随 AgentRun 快照走 → 坐席工作台右栏显示"这一类在补，当前 X%"。
4. **闭环**：`automated` 后显示 **标记前 vs 标记后** 的自动化率。**这是"改动与指标的回链"**，
   也是现在完全缺失的一环。

### 3.4 "自动化"的严格定义（采纳 outcome pricing 的纪律）

**不算自动化**：
- AI 答了但客户紧接着追问同一件事
- AI 答了但同一会话内转人工
- AI 答了但触发红线拦截 / 引用校验失败
- 弃权、澄清（这两种是"AI 承认答不了"，不是解决）

**算自动化**：该类目的会话**由 AI 收尾，且客户未再追问、未转人工、未触发拦截**。

分母是**该类目的会话数**，不是全部会话。**空类目返回 `None` 而不是 `0.0`**——
"没人问过"和"问了全转人工"含义相反（本仓库已有的纪律，继续遵守）。

### 3.5 三个自动触发器（借国内案例的"越挫越勇"机制）

| 触发器 | 条件 | 动作 |
|---|---|---|
| 连续失败 | 同一类目**连续 3 次**弃权/转人工 | 自动进清单，标 `repeated_failure` |
| 量超阈值 | 类目 7 日量 ≥ 阈值且自动化率 < 目标 | 自动进清单，按影响排序 |
| 新类目 | 首次出现的类目 | 标 `new`，观察，不急着自动化 |

### 3.6 运营节奏（把"知识库不是一次性工程"变成制度）

- 新政策上线 **48 小时内**更新对应知识 → 触发方式：类目状态 `automating` 的到期提醒
- 新问题出现 **3 次**即评估 → 就是触发器①
- **每月**复盘漏点原因、补盲区 → 清单的月度快照

## 4. 施工设计

> **状态（2026-09-22）**：§4.1–§4.3 的**后端已实现并测试通过**——迁移 0046、
> `evaluation/{categories,category_models,category_service}.py`、两个接口
> （`GET /v1/quality/categories`、`POST /v1/quality/categories/state`）、
> 36 个单测 + 6 个集成测试（含 RLS 与 0%→100% 的闭环数值）。
> **未做**：§2 的前端三处改动与 §4.2 的 `Recommendations.tsx` 页面。
> 后端先行是因为外形可以再调，但"该不该自动化某一类"这件事必须先有对象才能讨论。

### 4.1 数据模型（1 个迁移）

统计**不落表**（从 `agent_runs` 读），只落**运营状态**——它是人拥有的数据，必须持久化。

```
issue_categories
  id, tenant_id, category_key (业务线×场景×槽位，确定性字符串)
  state: observed|candidate|automating|automated|human_only
  fix_type: content|data|action|routing|policy      -- 最后一次人工确认的缺法
  note, marked_by, marked_at, automated_at
  UNIQUE (tenant_id, category_key)   + RLS FORCE + tenant_id
```

### 4.2 模块落点

| 层 | 文件 | 职责 |
|---|---|---|
| 派生 | `evaluation/categories.py` | `derive_category(run) -> str`（确定性、纯函数、可单测） |
| 归因 | `evaluation/categories.py` | `fix_type_for(run) -> str`（从已有信号映射） |
| 统计 | `evaluation/categories.py` | `category_report(session, tenant, window)` → 量/自动化率/缺口分布 |
| 状态 | `evaluation/category_models.py` + `category_service.py` | 状态机 + 标记 |
| 接口 | `evaluation/category_router.py` | `GET /v1/quality/categories`、`POST /v1/quality/categories/{key}/state` |
| 界面 | `apps/admin-web/src/pages/Recommendations.tsx` | ② 该补什么 |

### 4.3 验收标准

- 单测：派生确定性（同 run 同结果）、`fix_type` 映射覆盖每个信号、空类目返回 `None`、
  状态机非法转移被拒、`human_only` 类目不出现在候选清单里。
- 集成：跨租户不可见（RLS）、标记后 `marked_at/marked_by` 落库、标记前 vs 标记后自动化率可算。
- 端到端：演示故事的那一类（`pcb × expedite_request`）能从"0% 全转人工"走到 `candidate`，
  并在后台看到 0% → X% 的对比。

### 4.4 不做

- **不做多 Agent 分发**（ADR 0007）。
- **不做"猜你喜欢"式推荐**（B2B 工程师场景反效果）。
- **不自动改知识库**——清单可以一键跳到起草，但发布必须人点（6.5/7.8 的纪律）。
- **不做 100% 自动化目标**：`routing`/`policy` 两桶的归宿就是 `human_only`。
