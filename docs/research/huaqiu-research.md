## 执行摘要

1. 华秋不是单点制造商，而是**"工业软件 + 工程师社区流量 + 自有柔性制造"三段闭环**的平台型公司。这决定了它的客服不是"售后"，而是**贯穿设计→采购→生产→交付全链路的过程咨询**。
2. 咨询密度最高的不是"买不买"，而是**"我的板子/物料现在怎么样了"**——状态查询与工程确认（EQ）是绝对主力，且**直接决定交期**。
3. **EQ（工程确认）是华秋最具行业特性的流程**：工程发现文件矛盾后反馈客户，客户不确认则不投产，**交期自 EQ 确认后起算**。这是 AI 客服最高价值的切入点，也是唯一必须做对的人机权责边界。
4. 人工客服时间为**周一至周六 9:00–18:30**，而工程师调板、赶项目集中在夜间与周日——**夜间空窗是 AI 最直接的价值主张**。
5. 术语密集且高度口语化（绿油=阻焊、半孔、沉金=化金、飞针测试、阻抗、TGZ/Gerber），**别名表与工艺能力结构化是知识库的第一道门槛**。
6. 落地最大风险不是模型能力，而是**实时数据（库存、货期、订单进度、价格）被错误地放进 RAG**。存量事实走检索，**实时事实必须走工具**，这是本平台 ADR 0006 已定的硬约束。
7. 大客户（30 万企业客户中的头部）存在专属服务预期，**AI 不能成为大客户专属通道的降级替代**——需按 `EnterpriseAccount.tier` 分流。
8. 建议**单租户起步、多租户架构不动**：Pilot 只做"问得到就答、查得到就查"（纯检索 + 只读工具），写操作与 EQ 流转放第二阶段。

## 1.3 在产业链中的位置

华秋占据的是**电子硬件创新的"中段基础设施"**：上游连原厂与元器件供应链，中游是自己可控的柔性制造，下游是硬件研发企业与工程师。

```text
工程师社区(流量) → EDA/DFM 设计工具(入口) → 元器件采购/BOM配单(供给)
                                                    ↓
                                         PCB 制造 → PCBA 装联 → 交付/物流
                                                    ↓
                                          售后 · 质量 · 对账 · 开票
```

**这个位置对客服的直接影响**：

- 客户在**同一家公司**内跨 3–4 个业务系统下单，但**客服视角必须统一**——"我那单 PCBA 的料齐了没"横跨商城与 PCBA 两套数据。
- 华秋既是**平台方**也是**制造方**，质量争议时它同时是裁判与当事人——赔付边界天然敏感。
- 交付周期缩短 50%+ 是核心卖点，**交期承诺本身就是产品**——任何答错的交期都是直接的品牌损伤。

### 1.5.1 岗位地图（部分由公开招聘岗位职责实证）

### 1.5.2 工程岗（CAM / QAE 工程师 + EQ 组）——**本调研最有价值的一手证据**

> 来源：华秋 2026 年公开招聘中 "CAM/QAE 工程师" 岗位职责原文要素

- 依据客户要求、公司工艺能力、工程制作规范与预审指示，**制作工程 TGZ 文件**，**编制 ERP MI 流程和工序参数**，提供生产所需的制作工具与图纸资料；
- **在制作过程中检查客户文件与 ERP 系统中的参数，对矛盾的信息和无法满足的要求，将信息反馈给客户或 EQ 组**；
- 对客户提出的修改、生产过程中出现错误的文件和 ERP 进行修正；跟进自己订单与返修确认回复订单的处理及下线。

同批招聘的 **HDI 工艺工程师**职责中明确包含：**"协助生产处理 HDI 产品的客诉问题调查及改善"**；**工艺总监**职责包含"解决新产品开发关键技术问题""流程品质问题的解决"。

**这段描述直接暴露了客服的工程侧结构**：

| 结论 | 对产品设计的意义 |
|---|---|
| 存在一个专职的 **EQ 组** | EQ 是**独立职能**，不是客服附属动作；AI 只能"转述 + 收集确认"，不能代替放行 |
| 工程侧以 **ERP MI + 客户文件**双源比对发现矛盾 | 矛盾检测本身是**可结构化**的（参数 vs 能力表），AI 可做前置预检（DFM 已做了一部分） |
| 客诉调查由**工艺工程师**承担 | 质量投诉的答案权威在工艺/品质部，**不在知识库**；AI 必须走转人工并携带证据 |
| 工程与客户之间存在**多轮往返**（反馈→客户修改→再修正） | 需要**多轮会话状态**（本平台 `agent_runtime/conversation.py` 已具备）与 Case 的 `WAITING_CUSTOMER` 暂停时钟 |

```text
①设计(EDA/DFM) → ②在线智能计价 → ③上传文件 → ④CAM预审/EQ → ⑤投产(MES)
   → ⑥PCBA/物料齐套 → ⑦发货 → ⑧物流 → ⑨对账开票 → ⑩售后/质量
     ↑          ↑            ↑          ↑           ↑          ↑
   工具使用   报价规则     文件格式    交期起算点   进度/单号   发票/赔付
```

**★ 关键洞察：交期自 EQ 确认后起算**——EQ 是全链路唯一一个"客户动作直接决定交付承诺"的环节，也是 AI 唯一能产生**可量化业务价值**（缩短 EQ 停留时长 = 缩短实际交期）的地方。

# 第二部分 · 客服场景与落地挑战

## 2.1 咨询场景全景（按 AI 可控性分层）

| 层级 | 场景 | 答案性质 | AI 策略 |
|---|---|---|---|
| **L1 静态规则** | 工艺能力参数、文件格式要求、下单规则、赔付政策、退换货规则、开票流程 | 稳定、有权威文档 | **检索 + 引用**，可直接回答 |
| **L2 实时状态** | 订单进度、发货、物流、库存、货期、BOM 配单进度 | **实时、每分变化** | **必须走只读工具**（ADR 0006 禁止入 RAG） |
| **L3 条件变体** | "4 层板 1.6mm 绿油最快几天"（打样/批量、加急/常规不同）、"退货运费谁出"（归责 × 是否用券） | 答案随条件分叉 | 检索 + **变体条件弃答**（答错变体比答不出更贵） |
| **L4 受控写操作** | 申请开票、修改地址、修改发票抬头 | 需授权 + 后置校验 | `confirmed_write`：`propose → 人工/客户确认 → 执行 → 后置校验` |
| **L5 专业判断** | 缺料替代、阻抗叠层设计建议、工艺可行性例外审批 | 需工程师判断 | **转人工**，携带上下文与证据 |
| **L6 争议归责** | 质量投诉、赔付、责任划分 | 权威判定 + 情绪 | **转人工 + 证据收集**，AI 不得做归责表态 |

**这个分层本身就是路由设计**：L1/L3 → `KNOWLEDGE_QA`；L2 → `BUSINESS_READ`；L4 → `BUSINESS_WRITE`；L5/L6 → 弃权转人工。本平台 `agent_runtime/intent.py` 的路由枚举已覆盖这些类别。

## 2.2 六大典型场景详解

### 场景 A：报价与下单

- **典型问法**："4 层板 1.6mm 绿油沉金 100 片多少钱""这个 BOM 整套配下来多少""有没有免费打样活动"
- **难点**：报价是**多参数函数**（层数/板厚/铜厚/工艺/数量/交期），属**非标准化询盘**；PCB 有在线智能计价工具，PCBA/元器件 BOM 需人工报价（BOM 整单最快 4 小时）。
- **AI 定位**：**不做报价**。应引导至在线计价/上传 BOM，并收集必要参数（层数、尺寸、数量、工艺、目标交期）生成结构化询价单转销售。**承诺价格是本项目的红线**——模型输出的价格无权威来源即构成无据声明。

### 场景 B：交期与物流查询

- **典型问法**："我的订单到哪一步了""什么时候发货""快递单号多少""为什么还没到"
- **性质**：**最高频 + 最适合自动化**。华秋官网已提供"生产全工序进度实时可查、物流全程可追溯"，数据源存在。
- **AI 定位**：**只读工具全自动**。`order.get_status` / `shipment.track` 已是本平台注册工具，只需写华秋侧适配器。
- **陷阱**：**必须给出数据时间戳**。缓存的进度等于过期承诺。

### 场景 C：工艺与文件要求

- **典型问法**："半孔怎么做""最小线宽能做多少""阻抗公差多少""Gerber 要哪些层""为什么我的文件解析失败"
- **可核实的权威内容**（hqpcb 帮助中心）：最小线宽/线距 6mil(0.153mm)、常规 10mil；最小过孔 0.3mm(12mil)、焊盘单边 ≥6mil（建议 >8mil）；PTH 焊盘外环单边 ≥0.15mm；SMD 防焊开窗单边 ≥0.076mm(3mil)；字符字宽 ≥0.153mm、字高 ≥0.8mm；非金属化槽孔最小间距 ≥1.6mm；有间隙拼版间隙 ≥1.6mm、V-cut 板一般 ≥80×80mm、工艺边 ≥5mm；铜到外形线 0.508mm(20mil)。
- **难点**：①**参数有变体**（"参数多针对普通单双面板，多层板和盲埋孔板适当放宽"）；②**术语口语化**（绿油=阻焊、沉金=化金）；③**单位混用**（mil/mm）。
- **AI 定位**：检索 + 别名表 + **变体弃答**。**工艺参数是"表格型知识"**，需按原子 chunk 切分，避免参数与适用条件被切开。

### 场景 D：质量投诉与售后

- **典型问法**："板子短路了""开短路不良我要索赔""这批货有虚焊"
- **可核实的政策要点**：全测板承诺开短路直通率 100%；"坏一片赔十片"（有赔偿上限）；除板费外不承担其他经济损失（如 PCBA 停工损失）——**赔付边界是高频争议点**。
- **AI 定位**：**L6，必须转人工**。AI 只做三件事：①识别 `COMPLAINT` 意图；②**收集结构化证据**（订单号、批次、不良数量、照片→MinIO 预签名上传）；③生成带证据与原因码的**内部便签**给品质/工艺。**AI 绝不可做归责表态或赔付承诺**。
- **原理**：赔付判定是**权威判定**，不是知识检索；且涉及金额，属本平台定义的不可逆/高风险动作。

### 场景 E：账号、对账与开票

- **可核实的流程要点**：元器件**普票出库自动开具**；PCB/PCBA 及**专票需发货后手动申请**（用户中心 → 发票管理 → 我要开票）。
- **AI 定位**：流程性答案走检索；"帮我申请开票"走 `billing.get_invoice` + 受控写工具，**并做后置校验（是否已发货）**。修改发票抬头/地址属低风险写操作，绑 `action_hash` 确认。
- **陷阱**：对账涉及**金额与客户账本**，任何数字必须有工具来源，不得由模型推算。

### 场景 F：元器件与 BOM 配单

- **典型问法**："这颗料有货吗""货期几天""有没有替代料""我的 BOM 配到哪一步了"
- **性质**：**纯实时数据**。库存与货期入 RAG 是**明确禁止**的（ADR 0006）。
- **AI 定位**：需新增 `inventory.check_stock` 读工具（**当前平台尚未提供**）；替代料建议转采购人工。

## 2.3 场景 → 平台能力映射（已逐项核对源码）

| 华秋场景 | 平台机制 | 状态 |

## 2.4 落地难点（五项，每项给出根因与应对）

### 难点 1 · 专业术语密集，且口语名与文档名不一致

- **表现**：客户说"绿油"，文档写"阻焊"；说"沉金"，文档写"化学沉镍金"；说"半孔"，文档写"半孔径/邮票孔"。检索直接失效。
- **根因**：PCB 行业术语存在**大量同义词与俗称**，且**单位混用**（mil/mm），**参数随板型分叉**。
- **应对**：
  1. 建**术语别名表**（`knowledge_aliases`），涵盖俗称 ↔ 标准名、中英文、缩写（HDI/PTH/VIA/DFM/EQ/MI/TGZ）；
  2. 别名替换已实现**整词匹配**（避免 "ec" 命中 "ec-504"）与 CJK 子串匹配——**录入时无需担心误伤**；
  3. 工艺参数以**表格原子 chunk** 存储，保证"参数值 + 适用条件 + 单位"不被切开；
  4. **数字类答案要求引用**：任何具体数值回答必须携带 chunk 引用，否则弃权。

### 难点 2 · 非标准化询盘（报价、可行性、替代料）

- **表现**：客户一句"这个能做吗多少钱"包含未言明的层数、材质、数量、交期、认证要求。
- **根因**：B2B 制造业询盘**本质是参数收集过程**，不是问答过程。
- **应对**：
  1. 识别为 `BUSINESS_WRITE`/销售类意图后**不做回答，改做参数收集表单**（多轮 `conversation`）；
  2. 收集齐后生成**结构化询价单**进 Case 转销售；
  3. **明确禁止模型推算价格、交期、库存**——这三类无据声明是本平台 `forbidden_claim` 门禁的打击对象。

### 难点 3 · 多系统数据打通

- **表现**：PCB（MES）、PCBA（MES）、商城（库存/订单）、财务（发票）、DFM/EDA（工具侧）各自为政，客服需在多系统间切换。
- **根因**：业务是"三段闭环"收购与自建并存的结果，数据天然分散。
- **应对**：
  1. **统一走 Connector Adapter**，禁止直连任何业务库（本平台架构红线）；
  2. **严格分层**：静态规则入 RAG，**订单/库存/物流/价格一律走工具**（ADR 0006）；
  3. 每个工具定义**超时、重试、幂等、熔断、后置校验**；适配器对未知枚举**报错而非静默映射**；
  4. **先只读、后写入**：Pilot 阶段只开读工具，写操作逐工具评审后再开。

### 难点 4 · 人机转接与权责划分（**最关键**）

- **表现**：
  - 客户在对话里说"确认，按建议生产"——**这不等于工厂放行**；
  - 客服已介入后 AI 又发消息——**人机抢答**；
  - AI 对质量问题表态"这是我们的责任"——**越权归责**。
- **根因**：B2B 场景中 AI 的一句话可能构成**商业承诺**，而承诺主体是公司不是模型。
- **应对（平台已有机制，逐项对应）**：
  1. **控制租约**（`ConversationControlLease`）：面向客户的 AI 发送必须在派发前对 `lease_version` 做 CAS 复检——**人工接管立即压过 AI**；
  2. **风险分级**（`LOW_WRITE` / `CONFIRMED_WRITE` / `HUMAN_APPROVAL`）：EQ 放行、赔付、退款一律 `HUMAN_APPROVAL`；
  3. **弃权必须出声**：弃权路径必须发送"我无法核实，可转人工"的安全通知——本平台已修复"弃权即沉默"缺陷，这是 B2B 场景的底线；
  4. **转接携带上下文**：转人工必带订单号、历史、已收集证据与原因码，避免客户重复陈述；
  5. **红线清单**：价格承诺、交期承诺、质量归责、赔付金额、合同变更——**五类一律禁止 AI 表态**。

### 难点 5 · 大客户专属服务流程

- **表现**：头部客户有专属对接人、协议价、优先排产、账期；AI 用标准答案回应大客户，等于**服务降级**。
- **根因**：`EnterpriseAccount.tier` 与 SLA 策略是**合同属性**，不是知识库内容。
- **应对**：
  1. 用 `EnterpriseAccount.tier`（闭集：`strategic`/`enterprise`/`standard`/`basic`）驱动**SLA 策略与转人工优先级**；
  2. 大客户命中 `COMPLAINT` / 交期风险意图时**一律直转专属人工**，AI 只做登记与摘要；
  3. 知识库按 ACL 隔离：大客户专属政策文档仅对相应 `enterprise_account` 主体可见（`KnowledgeAcl.principal_type` 已支持该主体类型）。
- 【待核实】华秋实际的客户分层名称与权益细则。

# 第三部分 · 业务上线路径

## 3.1 部署形态：多租户架构，单租户起步

| 选项 | 说明 | 结论 |
|---|---|---|
| A. 华秋自用（单租户） | 华秋 = 平台一个租户，内部按业务线分 Department 与 KnowledgeSpace | 上手最快 |
| B. SaaS 卖给同行（多租户） | 本平台原生多租户（RLS FORCE + `platform_app` NOBYPASSRLS + 跨租户负向测试），每租户独立连接器/知识库/配额/账本 | 商业化路径 |

**推荐：按 B 的架构、A 的节奏上线**——代码不动，先以单租户运行，隔离与计费能力天然在位。

- 租户 `huaqiu`，`data_region` 设为境内（数据不出境）；
- 按业务线建 **Department**（PCB / PCBA / 商城 / 工程）与 **KnowledgeSpace**（工艺能力 / 交易政策 / 元器件 / DFM-EDA / 大客户专属）；
- `EnterpriseAccount` 导入大客户名单并标注 tier。

## 3.2 知识库来源与构建方式（四层分离）

| 层 | 内容 | 来源 | 构建方式 | 入 RAG？ |
|---|---|---|---|---|
| **L1 政策规则层** | 赔付政策、退换货规则、开票流程、账号/认证规则、服务承诺 | 官网帮助中心、用户中心说明、客服话术库 | 文档上传 + front-matter 标注 `doc_type`/生效期/权威等级 | ✅ 是 |
| **L2 工艺能力层** | 工艺参数表、文件格式要求、DFM 报错释义、材料与表面处理说明 | hqpcb 帮助中心、工程部 MI 规范、工艺能力表 | **表格→原子 chunk**；附别名表；标明适用条件（单双面/多层/HDI） | ✅ 是 |
| **L3 产品目录层** | 元器件型号、封装、替代关系、品牌选型 | 商城商品数据 | 量大且变化频繁——**建议走工具查询而非全量入 RAG**；仅静态选型指南入 RAG | ⚠️ 部分 |
| **L4 实时数据层** | 订单进度、库存、货期、物流、价格、BOM 配单进度 | ERP/MES/商城/物流 | **只读工具**（ADR 0006） | ❌ **禁止** |

**构建要点**：

1. **先建权威分层**：赔付/交期/价格类文档标记为"高权威"，冲突时由裁定工作流处理，而非让模型自行选择——**答错变体比答不出更贵**。
2. **生效期管理**：`DocumentVersion.effective_at` / `expires_at` 必须填。工艺能力与活动政策都有时效，过期文档被检索到等于错误答案。
3. **别名表优先于语料扩充**：术语问题先录别名，比堆文档更省事且更可控。
4. **缺口即飞轮**：弃权生成的缺口队列由工程师补答 → 审核 → 发布为新文档。华秋有 850 万工程师社区沉淀，这是**天然的高质量语料供给**。

## 3.3 与现有系统的对接优先级

按 `docs/integrations.md` 的既定顺序裁剪（Chatwoot → 身份 → CRM → 工单 → IM → 受控写 → 更多渠道）：

| 优先级 | 系统 | 能力 | 理由 |
|---|---|---|---|
| **P0** | Chatwoot（客服内核） | 渠道接入、会话、webhook HMAC、去重 | 平台内核，必备 |
| **P0** | 华秋 ERP/MES 只读网关 | `order.get_status`、`shipment.track` | **覆盖最高频场景**（进度/物流），价值密度最高 |
| **P0** | 知识库（帮助中心语料） | 检索 | L1 场景基础 |
| **P1** | OIDC / Keycloak | 企业客户身份、SSO | 大客户登录与身份绑定 |
| **P1** | 财务/发票系统只读 | `billing.get_invoice` | 对账开票高频 |
| **P2** | 商城库存系统 | `inventory.check_stock`（工具已注册，按 part_number 查询） | 元器件货期/库存 |
| **P2** | CRM | 客户/合同/权益查询、`crm.update_account` 受控写 | 大客户分层与权益 |
| **P2** | 工单系统（Jira/Linear 或自建） | Case → 工程/品质工单 | 客诉与 EQ 内部流转 |
| **P3** | 企业 IM（企微/飞书） | 通知与审批；**企微/微信渠道** | 华秋客户主渠道之一，**当前平台缺口** |
| **P3** | EQ 系统 | EQ 状态读写 | 特有流程，价值高但需业务建模 |

**注意**：所有凭据走 `credential_ref` 密管引用（Pilot 支持 `env://`，生产替换为密管客户端），**绝不落库明文**。

## 3.4 适合先行试点的场景与范围

**选择原则**：高频 × 低风险 × 有权威数据源 × 答案可验证。

| 试点场景 | 选择理由 |
|---|---|
| ✅ **订单进度 / 发货 / 物流查询** | 最高频、纯只读、数据源存在、答案可客观验证 |
| ✅ **工艺能力与文件要求问答**（L1/L3） | 语料现成（帮助中心）、术语可控、夜间价值最大 |
| ✅ **开票 / 退换货 / 赔付流程说明** | 规则明确、有权威文档、减少重复人工 |
| ⛔ **报价** | 非标准化、无权威实时来源、承诺风险 |
| ⛔ **EQ 放行** | 直接决定交期与生产，必须人工 |
| ⛔ **质量归责与赔付判定** | 权威判定 + 金额风险 |

**试点范围**：官网帮助中心 + 用户中心（登录态）两个入口；**不覆盖**微信/企微（缺口）、不覆盖电话渠道。登录态优先——登录后可绑定 `EnterpriseAccount`，实现分层服务。

## 3.5 分阶段上线节奏

### 阶段 0 · 准备（1–2 周）

- 租户初始化：租户 `huaqiu`、境内数据区、部门与知识空间划分；
- 导入 `EnterpriseAccount` 名单与 tier；
- 术语别名表初版（PCB/PCBA/元器件三套）；
- **红线清单与话术基线**评审（价格/交期/归责/赔付/合同五类禁止表态）。

### 阶段 1 · Pilot 只读（4–6 周）

- 语料：工艺能力表（表格原子切分）、发票/赔付/退换政策（标注生效期与权威等级）；
- 工具：`order.get_status` + `shipment.track` 适配器（华秋 ERP/MES 只读网关）；
- 渠道：Chatwoot 网站构件挂官网帮助中心与用户中心；webhook HMAC 与去重验证；
- 开关：`agent.business_read_enabled` 对该租户开启；`agent.rerank_enabled` 小比例放量；
- **验收门禁**：
  - 真实评估脚本 `scripts/run_eval.py` 扩充华秋语料用例（EQ/发票/赔付变体）；
  - **变体条件类题目 100% 变体正确率**（答错变体比答不出更贵）；
  - `citation_coverage`、`abstention_correct_rate`、`forbidden_claims` 三道 P0 门禁（由 `release_check --evidence-only` 计算，非手写）；
  - **重复投递验收**：同一 webhook 投递两次只产生一条客户回复（已有 e2e 脚本可复用）。

### 阶段 2 · 受控写与 EQ 流转（+4 周）

- 写工具：`address.update`（`LOW_WRITE`）、`invoice.apply`（`CONFIRMED_WRITE`，发货后后置校验）；
- **EQ 流转**：AI 只做"转述 EQ 内容 + 收集客户确认"，**确认动作走 `HUMAN_APPROVAL`**——客户在对话中的确认不能直接等于工厂放行；
- Case 进入 `WAITING_CUSTOMER` 时 SLA 时钟暂停，需与华秋"交期自 EQ 确认后起算"口径对齐；
- 企微/微信渠道适配器（走 `integrations` 框架，当前缺口）。

### 阶段 3 · 深化（+6–8 周）

- `inventory.check_stock` 实时库存工具（需平台新增）；
- BOM 配单进度查询；

## 3.6 效果评估指标

### 业务指标（对华秋的价值）

| 指标 | 定义 | 目标（Pilot 基线后设定） |
|---|---|---|
| **EQ 平均停留时长** | 工程发出 EQ → 客户确认的时长 | **核心指标**：直接决定实际交期 |

| 客户满意度 / 投诉率 | 会话评价与投诉量 | 不劣化（**红线**） |

### 系统指标（平台可观测性）

| 指标 | 说明 |
|---|---|
| read-tool 成功率 | `release_check` 已可读取真实 `tool_executions` 流量计算 |
| 引用覆盖率 `citation_coverage` | 有据声明比例，P0 门禁 |

### 质量红线（任一突破即暂停放量）

1. `forbidden_claims > 0`（出现无据的价格/交期/库存/赔付承诺）；
2. 变体条件类问题答错变体（如把大批量交期答给打样客户）；
3. 跨租户数据泄漏（零容忍测试）；
4. 重复投递产生重复客户回复；
5. **弃权却无回复**（客户沉默等待）——本项目已修，需回归覆盖。

## 3.7 主要风险与应对

| # | 风险 | 影响 | 应对 |
|---|---|---|---|
| 1 | **实时数据被误入 RAG**（库存/价格/进度） | 客户拿到过期承诺，直接商业损失 | ADR 0006 硬约束：实时数据只走工具；答案必带时间戳 |
| 2 | **AI 做出商业承诺**（价格/交期/赔付） | 法律与商誉风险 | 红线清单 + `forbidden_claim` 门禁 + 高权威文档裁定流 |
| 3 | **EQ 被误放行** | 错误投产，物料与产能损失 | `HUMAN_APPROVAL` 风险级；客户确认 ≠ 工厂放行 |
| 4 | **人机抢答** | 客户收到矛盾信息 | 控制租约 CAS 复检；人工接管即压过 AI |
| 5 | **术语/变体答错** | 工程返工 | 别名表 + 变体弃答 + 表格原子切分 |
| 6 | **Gerber/图纸属客户 IP** | 知识产权与合规风险 | 平台已"不落原文"（webhook 最小化 + 哈希）；法务确认个保法与保密条款 |
| 7 | **微信/企微渠道缺口** | 覆盖不到主渠道 | 走 `integrations` 框架开发适配器（已识别为待建） |
| 8 | **PDF 工艺表抽取失真** | 参数错切导致错误答案 | 表格抽取需专用库——引入新依赖须走 ADR |
| 9 | 大客户感知"服务降级" | 头部客户流失 | tier 驱动 SLA 与直转人工；大客户专属 ACL 文档 |
| 10 | 评估数据集不具代表性 | 门禁通过但线上失败 | 用真实业务语料（含华秋术语与变体）而非合成语料 |

### 实施中发现的两个真实缺陷

**1. 含大写字母的别名永久失效（平台缺陷，已修）。**
`normalize_colloquial` 把查询转小写，却用原样别名匹配，于是 `V割 / EQ / MI / TGZ`
**一条都不会命中**——而这正是 PCB 语料的缩写词汇主体。别名表看起来已配置、实际上从不参与改写，
属于"存在且被测试、但生产路径打不到"的那一族缺陷。修法是对别名同样做 case-fold，
并保持拉丁别名的整词规则不变（新增两条回归测试，含"不得因折叠而放宽整词"的反向断言）。

**2. 变体用例的禁用词无法区分否定与断言（语料缺陷，已修）。**
华秋发票政策原文写"自动开具，**无需**手动申请"，而用例禁止"手动申请"；赔付政策原文写
"**不**承担…（包括 PCBA 停工损失）"，而用例禁止"停工损失"。子串匹配下，忠实答案必然触发禁用词，
用例因与模型行为无关的原因变红。修法：发票按分支拆为两条语料（顺带让"检索选对分支"成为真正被测的能力），
赔付改用原文中不存在的承诺型字符串（"无上限"/"全额赔偿"）。
**并做了变异验证**：反转检索排序后两个变体用例双双失败，证明它们确有鉴别力——
无法观察到失败的守卫不构成证据。

## 附录 B · 阶段2 前置条件核查（2026-09-19）

在着手阶段2（受控写操作与 EQ 流转）之前，核查了智能体的**写路径是否成立**。结论：

**目前不存在智能体可执行的写路径。** 依据（均为 grep `apps/api/src` 实测）：

- `Route.BUSINESS_WRITE` 只由 `intent.py` 产出（`IntentKind.BUSINESS_ACTION →
  Route.BUSINESS_WRITE`），`orchestrator.py` 对 route 的分支只有 `SENSITIVE` /
  `HUMAN_REQUIRED` / `OUT_OF_SCOPE` / `BUSINESS_READ` 四条，**没有 BUSINESS_WRITE 分支**；
- 编排器里唯一的 `gateway.propose(...)` 在 `_attempt_business_read` 内（读路径）；
- 写工具（`jira.create_issue`、`crm.update_account`、`im.send_notification`）在
  `TOOL_CATALOG` 中已定义，且工具网关本身支持 `propose → confirm → execute → verify`，
  但目前只有 HTTP 路由（`tool_gateway/router.py`）能驱动它，**智能体运行时驱动不到**。

**当前行为是安全的**：`BUSINESS_WRITE` 会漏到检索 → QA 路径，而 `qa_path._is_action_request`
会拒绝动作请求并弃权转人工。也就是说"AI 不会擅自写"，但也"AI 什么都做不了"——
客户在对话里说"确认，按建议生产"目前只会得到一次转人工，EQ 确认的价值没有被捕获。

**因此阶段2 的实际工作量被低估了**：它不是"加一个 EQ 工具"，而是要先建
**智能体写执行路径**（propose → 人工确认 → 执行 → 后置校验 → 审计，且受控制租约约束），
再在其上承载 EQ。建议按此拆分立项：

1. **2a 写执行路径**（通用，被 address.update / invoice.apply / EQ 共用）——架构性，需设计决策：
   谁来确认（坐席还是客户二次确认）、确认载体（Chatwoot 还是管理台）、确认超时与租约交互；
2. **2b EQ 业务模型**——`Case.category = eq_confirmation` + `WAITING_CUSTOMER →
   WAITING_INTERNAL` 的状态语义 + `case.eq_confirm` 工具（`human_approval` 风险级）。

`case.read` 已提供会话绑定执行器的范式（读平台自有表、受 RLS 约束），2b 可照此实现。
