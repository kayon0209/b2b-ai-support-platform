# 主流智能客服能力清单 · 逐项比对与缺失项

> 对照片面主流智能客服系统的**十大常见能力域**。
> 判定依据：读本仓库代码 + 查实时库表，不凭文档推断。每条"现状"都指向具体文件。
> 日期：2026-09-22。优先级：**P0** = 一期必须有，**P1** = 二期，**P2** = 优化项。
> 配套：`docs/product-gap-analysis.md`（三界面差距）、`docs/product-shape-and-last-mile.md`（外形与闭环）。

---

## 总览

| # | 能力域 | 判定 | 关键缺失 |
|---|---|---|---|
| 1 | 多渠道接入 | 🟡 有骨架 | 淘宝/电话/QQ群、语音 ASR、渠道配置台、主动营销触达 |
| 2 | 会话分配与转人工 | 🟡 **偏弱** | **无坐席名册、无技能/负载分配、无未指派队列、无认领** |
| 3 | 知识库与语义检索 | ✅ 强 | 复杂表格/图纸解析未验证、"假性覆盖"未独立成类 |
| 4 | 意图识别与多轮对话 | ✅ 强 | 多语言（仅中英） |
| 5 | 自动回复与话术推荐 | 🟡 **偏弱** | **无话术库/快捷回复**、无采纳率统计 |
| 6 | 工单流转与 SLA | 🟡 有骨架 | **SLA 策略写死在代码里**、无自定义字段/模板 |
| 7 | 客户画像与历史会话 | 🟡 数据齐 | **坐席侧无画像面板**、无跨渠道时间线聚合视图 |
| 8 | 数据统计看板 | 🟡 有质量面 | **无坐席绩效**、无渠道维度统计 |
| 9 | 机器人训练与人工干预 | 🟡 有机制 | **无调试/重跑界面**、A/B 无运营入口 |
| 10 | 账号与权限管理 | ✅ 强 | 无坐席技能标签（归入 #2） |

**一句话**：**能力重心偏"AI 侧"，偏弱的是"坐席侧"和"运营配置侧"。**
知识、意图、检索、风控、审计这几块是超配的；而主流产品里最普通的
**话术库、坐席名册与分配、SLA 可配置**这三件，我们**一件都没有**。

## 1. 多渠道接入

**现状**
- ✅ 渠道适配器：`platform_core/channels/{base,email,wechat,outbound,router}.py`，一个渠道 = 一个 `connectors` 行 + 一个适配器（ADR 0013/0014）。
- ✅ 入站去重：`uq_inbox_delivery`，202/200 语义。
- ✅ 跨设备续接：`conversation_contacts`（迁移 0045），按**渠道联系人**续接而非企业账户。
- ✅ 排队位次与预计等待：`agent_runtime/queue_status.py`（真实计数）。
- ✅ 非工作时间兜底：`agent_runtime/hours.py`，明确给出下次服务时间。
- ✅ 富媒体：`support_bridge/inbound_media.py`，只留内容类型。
- ✅ 渠道格式适配：`support_bridge/channel_format.py`（未知渠道保守降级纯文本）。
- ✅ `GET/POST /v1/connectors` 存在。

**缺失**
| 项 | 说明 | 优先级 |
|---|---|---|
| 淘宝/天猫、电话、QQ 群适配器 | 外部协议与签名，扩展点已就绪 | P1 |
| 语音消息转写（ASR） | 需外部模型服务 | P1 |
| **渠道健康与配置台** | 连接器有 API，但没有"这个渠道通不通、最近失败几次"的运营视图；`integrations/health.py` 存在但未接进界面 | P1 |
| 主动触达/营销推送 | B2B 场景需克制，且清单未要求 | P2 |

## 2. 会话分配与转人工 —— **本域最弱**

**现状**
- ✅ 控制权租约：`identity/control_lease.py`（人工接管立即生效，AI 发送前 CAS）。
- ✅ 转人工：`release_to_queue`、`transfer_to_human`；7 类触发齐全（含情绪信号）。
- ✅ 技能组路由：`agent_runtime/routing.py team_for(scene, business_line)`（7.3）；`cases/transfer.py` 映射到真实 `Department.slug`。
- ✅ 升级：`cases/escalation.py`（SLA 违约自动升级）。
- 🟡 `cases.assignee_ref` 是**不透明字符串**，`cases/transfer.py` 明确写着"不做分配给具体的人"。

**缺失**
| 项 | 说明 | 优先级 |
|---|---|---|
| **坐席名册（agent directory）** | 没有"谁是坐席、会什么、现在忙不忙"的表。分配只能靠一个字符串 | **P0** |
| **技能/负载感知的自动分配** | 主流产品的标配：按技能匹配 + 按当前负载 + 上限 | **P0** |
| **未指派队列视图** | 坐席只见 `/workbench/:caseId`，必须先知道案例号 | **P0** |
| **认领 / 退回（claim / release）** | 无 | **P0** |
| 转接给指定坐席（不是组） | 无坐席名册，故不可能 | P1 |
| 分配规则可配置（轮询/最少负载/技能优先） | 无 | P1 |

## 本轮实现

### 批次 1 —— 话术库（P0，已完成）

迁移 0047 `canned_replies` + `cases/{canned_models,canned_service,canned_router}.py`。

- 标题/正文/快捷指令/业务线/团队/语言/使用计数/归档（**归档不删除**：发出去的话术是历史）。
- `shortcut` **可为 NULL 而非默认空串**——UNIQUE 视 NULL 互异，所以"无指令"不冲突，而 `/eta` 只能指一个。
- 作用域过滤**包含未打标的**：筛 `pcb` 会返回 PCB 的 + 通用的，否则通用话术会从最需要它的坐席眼前消失。
- 权限不对称：读/用 = `CASE_READ`，增删改 = `TENANT_ADMIN`（改一条模板等于改所有人说的话）。
- **基础底座**：重复快捷指令此前会以 IntegrityError 冒成 500；现在在边界映射为 409
  `CANNED_SHORTCUT_TAKEN`。空标题/空正文在进库前拒绝。管理类写入落审计事件（`metadata`，因为 `after` 是哈希读不到）。
- 8 个集成测试：归档可恢复、快捷指令带不带斜杠都解析、归档后不解析、作用域包含性、
  使用计数改变排序、重复指令被库拒绝、空标题拒绝、跨租户不可见且不可用。

### 批次 2 —— 坐席名册与分配（P0，已完成）

迁移 0048 `agent_profiles` + `cases/{agent_models,assignment,agent_router,assignment_router}.py`。

- 名册：技能标签、并发上限、在岗状态（`status`，**不删除**——有在手工单的坐席不能消失）。
- `pick_agent`：技能 → 负载比 → 容量。**全员满载返回 None 而不是挑最不忙的**：未分配是可见状态，超载不是。
- `claim_case` / `release_case`：认领会拒绝超容量（志愿者恰恰是最容易绕过上限的路径）；
  退回幂等（连点两次不是错误）。
- `GET /v1/agents/queue`：未指派队列，旧工单先出——坐席终于有了工作入口。
- `user_ref` 用不透明字符串而非外键：与 `cases.assignee_ref` 同形，"谁拥有"和"谁是本尊"之间不需要翻译层。
- **修掉一个真缺陷**：技能匹配最初把"无标签"和"有标签"混在同一候选池里按字母序决胜，
  结果 PCB 问题会派给通用坐席而 PCB 专员闲着。技能匹配必须是**分离键**，无标签只作回退。
- 10 个集成测试：最少负载优先、技能优先、全员满载返回 None、超容量拒绝认领、
  非在岗拒绝认领、退回幂等、队列排序且排除已分配、局部更新不冲掉技能与容量、跨租户隔离。

### 批次 3 —— SLA 策略可配置（P0，已完成）

迁移 0049 `sla_policies` + `cases/{sla_models,sla_service,sla_router}.py`，30 个集成测试。

- 可配置：每个合同等级的**两个目标分钟数** + 可选的优先级系数。
- **不可配置：`running_states`**——沿用原注释的论证：哪些状态暂停时钟是**工作流**属性，不是客户买到的属性。
  按租户开放它会让两个工作流相同的客户在不同点暂停，"这个时钟为什么停了"就没有唯一答案。
- **无 `enabled` 列、无种子行**：没有配置就是代码默认，所以 **DELETE 就是重置**，不存在第二种表达方式。
- 关键不变量（18 个参数化用例）：**未配置时 `resolve_sla_policy` 与原 `sla_policy_for_tier` 逐字段相等**——
  回退是直接调用原函数而非重写其算术，两者无法漂移。
- 层级归一化与默认**同一套规则**：合同非 active → `standard`；未知/缺失 → `standard`。
  查原始 tier 会让暂停合同的客户命中 `strategic` 覆盖，继续享受已无权享有的 15 分钟时钟——
  正是原注释警告的那个失败。
- `priority_multipliers` **按字段回退**：只设了目标分钟的行保留默认 p0/p3 梯度，不会静默变成空表。
- 校验：resolution < first 拒绝（转置的两个数会让每个工单在能被答复之前就违约）、越界拒绝、空 tier 拒绝。
- 端到端：`test_creating_a_case_uses_the_configured_policy` 断言真实工单的 `first_response_due_at`
  等于配置窗口。配置值故意选了默认值**产生不出来**的数（strategic 默认 60×0.25=15，配置用 7）——
  否则拆掉接线测试照样绿，而那正是这条测试存在的理由。

### 批次 4 —— 坐席回复 + 续接落库（P0，已完成）

迁移 0050 `conversation_contacts.external_conversation_key` +
`agent_runtime/{agent_reply,agent_reply_router}.py` + `worker/outbox_relay.py` 的投递处理器，
13 个集成测试。

**做这一批之前先发现了一个更严重的洞**：**工作台没有"回复"这个动词。**
`POST /v1/customer/.../messages` 写的是**客户**的轮次（会顺带排一次 AI run），不是坐席的。
所以坐席能读全部上下文、能看 AI 建议、能看相似工单——**一句话也发不出去**。
话术库（批次 1）也因此悬空：有了模板，没有地方插。

- 新端点 `POST /v1/conversations/{ref}/replies`（`CASE_UPDATE` + 幂等键）。
- **回复即接管**：先 `acquire_or_get` 再 `transfer_to_human`，同一事务内完成，然后才写轮次。
  否则 AI 可能正在同一会话上生成，两条消息都会到客户手里——租约正是防这个的。
  这是 AGENTS.md 规则 8 的另一面：AI 发送前要复查租约，所以人必须**持有**它。
- **文本原样存储**（新增 `append_authored_turn`，不是给 `append_turn` 加布尔开关）。
  `redact_text` 会把 10 位以上数字串打码，等于吃掉坐席正要发的那张单号；
  而且存档会与实际发出的内容不一致，破坏"我们到底跟客户说了什么"这个问题。
- **投递走 outbox 队列，不在 API 进程直接发**：传输层在 worker（熔断与重试计数都在那）。
- 事件载荷只带 `turn_id` 不带正文——轮次是唯一记录，outbox 里再存一份就会有两个版本。
- 处理器**每条读写都显式带 `tenant_id`**：relay 跑在 owner 角色上，RLS 在这条路径不过滤任何东西。

**顺带修掉一个休眠功能**：`link_conversation`（以及它的读取方 `contact_for_conversation`）
**没有任何生产调用方**——只有测试在调。所以 1.5 跨设备续接实际上不工作，
客户在微信问一半再去官网，平台眼里是两个无关会话。现已接进渠道入站路径，
并同时记下出站需要的线程键（`external_conversation_key`）——没有它，每封回复都会开一个新邮件线程。

### 批次 7 —— 修掉一个安全缺陷：`internal_draft` 从未生效（P1，已完成）

2 个集成测试。**这不是新功能，是修 bug。**

`POST /v1/conversations/{ref}/agent-runs` 自写下起就接受 `mode="internal_draft"`，
校验它、存到 run 的 `model_config` 上——**而没有任何东西读它**。

追下去发现比"没人读"更糟：`queue_agent_run` 写 `model_config={"mode": mode}`，
而 `_adopt_or_create_run` 采纳占位行时**用血缘快照整体覆盖 `model_config`**——
**模式在任何执行者能看到它之前就被抹掉了**。坐席要一份草稿来复核，收到的是
**一条已经发给客户的消息**，而唯一能说明这件事的字段已经不存在。

修法：采纳前先读取占位行请求的 mode，再随血缘快照一起写回；执行时从 run 行读取
（模式属于 run，谁执行谁负责，不靠层层传参）。抑制逻辑与影子模式共用——
两者只差"谁要求的"：flag 要求所有会话，mode 只要求这一个。

**测试差点假绿**：第一版没传 `channel_system`，于是 `_dispatch` 走平台面分支、
**任何模式下都不发送**——"没有发送"这个断言会以错误的理由通过，而它存在的目的正是抓住这个缺陷。
补上渠道后，两条用例才真正对立：`internal_draft` 不发送，`customer_reply` 必须发送。

> 后端先行的理由：这几件都是**数据模型先行**的能力，界面可以后调，
> 但"这条话术是什么""谁是坐席""这个 SLA 是多少""这句话是谁说的"必须先有对象才能讨论。
