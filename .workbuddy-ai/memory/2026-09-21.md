## 占位 run 的根因查清了：它不是冗余，**是一个没有被接上的生命周期**

**先量化，再下结论**（配额口径是 `started_at IS NOT NULL`，而占位行**也设了 `started_at`**）：

| 口径 | 数量 |
|---|---|
| 配额实际统计 | **434** |
| 真实 run（`input_hash` 非空） | **171** |
| 占位行 | **263** |
| `admin-demo` 本月 | 占位 **30** / 真实 **12** → **配额读成 42，实际 12** |

→ **租户月配额被虚增到约 3.5 倍**，运营后台"已用 run 数"同样偏高。

**根因不是"多写一行"，而是"同一次逻辑 run 被写了两行"**：
`router.py` / `chat_service.queue_agent_run` 写**占位**（`status=queued`, `input_hash=''`），
`orchestrator.py:674` 又写**真实 run** —— **两行，同一次运行**。
而 `test_m2_http_api.py:1088` 有一条测试**专门钉住占位写入**（注释：`started_at` 要填，
否则 `/v1/quality/metrics` 看不到 run）→ **说明占位是有意设计的**。

**所以真正的架构缺陷是：占位行的消费者从未被实现。** 设计意图显然是"一次 run 一行、
`queued → running → completed` 生命周期"，而**编排器应该 adopt/update 那一行**，却另起了一行。
这解释了为什么会有 `input_hash=''` 这个"孤儿占位"诊断特征（REFERENCE 里那条）。

**两个候选修法**：
- **根治**：让 `orchestrator.py:674` 复用同会话的 queued 占位行（一次 run 一行），
  配额口径不变（配额本意是"请求的 run 数"），同时消灭孤儿行与"同一 run 算两次"。
  代价：动编排器的 run 创建路径 + 更新那条钉住占位的测试。
- **治标**：只改 `usage_snapshot` 的口径（排除 `input_hash=''`）。一行，风险低，
  但孤儿行继续堆、数据模型继续撒谎、诊断陷阱继续存在。

**我倾向根治**，但**没有动手**：这需要改编排器的 run 创建路径，属于深层改动，
我不想在没看完 `orchestrator.py:674` 上下文的情况下盲改。

# 三段：§5-B 相似工单 —— 交接文档这条记错了，真正的问题在别处

**交接文档说"Workbench.tsx 没有相似工单"**。核对后发现：**后端 `related_cases` 和前端渲染
都在**（`/v1/cases/{id}/workbench` 返回 `related_cases`，`Workbench.tsx:187` 渲染它）。
所以 B 真正的问题不是"缺一块"，而是**这块没有相关性可言**：

- 查询是"同 `category` + 最近 5 条"，而 **`category` 默认是 `general`**（实测 admin-demo 23 条里 9 条）；
  端点自己的 docstring 都写着"叫它 similar 会承诺一个查询没算出来的相关性"。
- `basis` 这个 **API 枚举被原样渲染进用户可见标题**（`相似工单 (same_category)`）。

## 修法（要点：先量再设计，量出来的结论推翻了第一版方案）

1. **第一版用 pg_trgm 的 `similarity()` 做门槛** —— 量完发现**彻底不可用**：
   `similarity('能不能加急','加急打样多久') = 0.000`（共享词"加急"是 2 字，
   在两个串里的 3 字窗口分别是"能加急/加急打"，永远对不上）；
   英文同串 0.613 / 弱相关 0.222。**trigram 对产品真实语言是盲的**，
   照第一版上线 = 坐席侧永远显示"没有相关工单"。
2. **换成词项重叠（term overlap）**：拉丁词（≥3 字符）+ **CJK 二元组（bigram）**，
   Dice 系数排序。中文 `能不能加急` vs `加急打样多久` → 共享 `加急`；
   英文 → 共享 `short/circuit/claim`；无关对 → 0。
3. **词频自适应裁剪**：不手写停用词表——"order"对元器件商是每单都有的词、对 payroll 团队罕见，
   手写列表对第二个客户就是错的。改为**文档频率**：窗口内出现在 >50% 工单标题里的词
   不再算共享证据（样本 <30 条时不启用，避免小样本误伤）。
4. **两级信号都保留但如实标注**：`match: subject | category`（每行带 `shared_terms`）；
   **桶匹配封顶 2 条**并排在所有措辞匹配之后——否则主桶里又是"任意最近工单"，
   换个名字回到原缺陷。
5. 前端：标题不再拼 `basis` 枚举；每行 Badge 标注"措辞相近/同类工单" + 共同词；i18n 中英都补了。

**教训（可复用）**：交接文档的"现状"必须核对——这条标了【高】的待办其实已经做了一半；
而做另一半之前，**先对产品真实语言量一次检索信号**，否则会把一个"看着相关"的面板上线。
