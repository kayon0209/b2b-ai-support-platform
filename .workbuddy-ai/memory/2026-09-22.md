## 17:20 用户答渠道问题：**另建邮件和微信适配器**（ADR 0012 的 Option B）

### 先写 ADR 0013（设计），因为规则 1 要求先有决定记录

`docs/adr/0013-inbound-channel-adapters.md`。**设计过程中改过一次方案，因为测量推翻了第一版：**

- 第一版让渠道绑定走 `external_resource_refs`（`system`/`resource_type`/`external_id`）。
  **查库发现该表是 FORCE RLS**（`tenant_id = current_setting('app.tenant_id')`）→ 未绑定租户时 app 角色读**零行**，
  每一条投递都会解析不出租户；而且它没有密钥列。**否决。**
- 第二版（现行）：**一个渠道就是一行 `connectors`**（`provider = "email" | "wechat"`）。
  `resolve_connector_for_webhook`（迁移 0026）**本来就是** SECURITY DEFINER 解析器，`webhook_secret_ref` 本来就是密钥存放处
  → **不需要新迁移，不需要新密钥存储**。ADR 里把"为什么否掉第一版"写了下来，而不是悄悄改掉。

**关键设计：适配器只做"验签 + 翻译"，持久化交给路由。**
路由把客户消息**写成一条 `conversation_turn`**（`append_customer_turn`，先脱敏、顾问锁去重），
再把 `message_id` 设为**该 turn 的 id**、`event_type="message_created"`、`message_type="incoming"` 写进 `InboxEvent`。
于是 worker 的 `_local_turn_text` 就能取到正文 —— **和 `/support` 里打字问问题走的是同一条路**。

## 17:50 Stage B：出站回程（ADR 0014）

### 缺陷是"静默成功"，不是"没实现"

`orchestrator._dispatch` 里：
```python
if not chatwoot_account_id:
    # ... this surface is the delivery channel. This is not a failed send ...
    return ""
```
`""` 的含义是**已投递**。渠道会话没有 Chatwoot account id → **每封邮件/微信的答案都走这个分支、返回成功、然后什么都没发**。
run 完成、答案落库、Workbench 看得到，**客户什么也没收到**。没有异常、没有日志、没有指标 —— 就是 `worker_cannot_send` 那类形状。

### 设计（ADR 0014）

1. **事件带上渠道**：`channel_system` 由渠道路由写入、消费者读出。**不需要新字段表示收件人** ——
   `contact_id` 已经是邮件地址/微信 openid，`conversation_id` 已经是线程键。
2. **分支顺序是承重的**：渠道分支必须在 `sender is None` 之前 —— 因为 `sender` 是 **Chatwoot** 客户端，
   而只走邮件/微信的部署**没有** Chatwoot token。先跑那个 guard 就会返回"已投递"、吞掉每一条渠道答案。
   **变异验证：把渠道分支挂在 `sender` 后面 → 7 条测试红。**
3. **注册表而非 if 链**：`channels/outbound.py` 的 `ChannelSender` 按 system 路由。
4. **未配置的渠道要报出来，不能静默成功**：没有凭据的渠道**不注册**，`_dispatch` 返回 `OUTBOUND_NOT_CONFIGURED`。

**为什么 `OUTBOUND_NOT_CONFIGURED` 不让 run 失败**：agent turn **只为 COMPLETED 的 run 写入**，
失败会连答案**和平台自己的唯一记录**一起丢掉 —— 等于用一个静默不投递换一个静默数据丢失。
所以它和 `SHADOW_MODE` 归为**"扣下不投递"**：run 完成、原因记在 run 上、并打 warning。
失败分类：无传输→`OUTBOUND_NOT_CONFIGURED`（扣下）／有渠道无地址→`OUTBOUND_TARGET_MISSING`（失败）／
抛错→`OUTBOUND_FAILED`（失败）／结果未知→`OUTBOUND_AMBIGUOUS`（可重试失败）。

**邮件闭环**：出站把 `In-Reply-To`/`References` 设为**线程根**，与 `channels.email` 入站推导 `conversation_key` 用的是同一个值
→ 客户回复落回同一个会话。设成"父消息"会让每次往返都分裂线程 —— 就是 ADR 0013 记的那个坑，出站也得避开。

**微信走出客服务消息 API，不走被动回复**：被动回复必须 5 秒内返回，而 run 要 8–68s。

### 顺带必须改的一处

`worker/wiring.py` 的 `require_sender` 原本**没有 Chatwoot token 就拒绝启动** —— 这会让 ADR 0012 的移除**无法进行**
（只走渠道的部署没有 Chatwoot token，且并不是配错了）。改为**只有"一个传输都没有"时才拒绝**，这才是该 guard 本来的用途。
