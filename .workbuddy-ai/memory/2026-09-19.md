**这次真正学到的（可复用的排查套路）**：

- **"假成功"要往 HTTP 状态找，不要往 UI 找。** 三个 router 的 `_xxx_error()` 返回裸 dict，
  FastAPI 渲染成 200；前端 `unwrap()` 只看 `!res.ok`。**判断一个写操作到底成没成，
  直接 `curl -i` 看 status，再看 UI 到底显示了什么** —— 两者不一致就是这类 bug。
- **修这类"旧行为被测试固化"的 bug，先跑定向测试再改断言。** 3 个测试名写着
  "is_not_found_not_500" 却断言 `== 200`；改完断言后新增
  `test_refused_release_actions_are_never_200` 锁住契约（用 `DOMAIN_ERROR_STATUS` 取值，
  不写死数字）。
- **移动端"视口被撑大"的真因往往是 min-content，不是宽度写死。**
  Branding 撑到 449px 不是因为 `width`，而是 `.field` 里「标签 + input」的 min-content
  之和超过屏幕；`min-width:0` 不够，要把 `.field` 改成纵向堆叠才彻底好。
  排查方法：在页面里遍历 `getBoundingClientRect().width > 400` 的元素，看谁最宽。
- **ruff E402/I001 会因为"在 import 之间插了语句"而连锁报错。** 在 main.py 顶部加
  `logger = logging.getLogger(__name__)` 之前没插在 import 中间就没事；插进去后
  后面 28 个 import 全报 E402。logger 定义要放在所有 import 之后。
- **验收复跑必须重启后端才作数。** 前端 Vite 有 HMR，后端没有 —— 我一开始改完 Python
  就跑 journey，结果全是旧行为。用 `APP_API_PORT=8010` 起第二个实例 + Vite
  `VITE_API_TARGET` 指过去，比杀掉别人起的 8000 端口进程安全。

**顺手发现并修掉的 3 个新问题**（原报告没有）：
1. `QuotaIn.monthly_run_quota` 无上界 → 超过 int4 就 DB 溢出 → 500。加 `le=2**31-1`。
2. 未处理异常返回裸文本 `Internal Server Error`，违反 api-contracts 的两形状契约，
   且没有 trace_id。加兜底 handler（细节只进日志，不回显）。
3. 422 走 FastAPI 默认 `{"detail":[...]}`，前端落到 `HTTP 422` 兜底文案；且默认体会
   **回显 input**（可能是 token/prompt）。改成只回"字段: 原因"。

**踩到的坑**：一次失败的测试会把 fixture 租户留在库里，下一轮直接 50 个 setup
`IntegrityError`。清理要用 `begin_nested()` 逐表删（否则一个 FK 违规整事务中止）

## 第四轮：接手 zcode 的华秋落地实现

**断点怎么定位的**：`git status` 找 untracked 里的 `scripts/seed_huaqiu.py`，再跑全量

### 两个失败的根因都是「用例/语料编写缺陷」，不是平台缺陷

oracle 回显整段证据，于是：发票政策原文同时含两个分支 → 禁"手动申请"必炸；
赔付原文写"**不**承担…（包括 PCBA 停工损失）" → 禁"停工损失"必炸。
**子串匹配分不清否定与断言**（与之前 "refund window" 命中 "Are monthly plans
refundable?" 是同一族）。修法：发票按分支拆成两条语料（顺带让"检索选对分支"成为
真正被测的能力），赔付改用原文中不存在的承诺型字符串（无上限/全额赔偿）。
**变异验证**：反转检索排序后两个变体用例双双失败 —— 无法观察到失败的守卫不算证据。

### 顺手挖出一个真平台缺陷

`normalize_colloquial` 把查询转小写、却用**原样别名**匹配 → 含大写字母的别名
（V割 / EQ / MI / TGZ，即 PCB 缩写词汇的全部）**永久不命中**。既有 3 条测试全用
小写别名，所以它活下来了。已修（别名同样 case-fold，拉丁整词规则不变）+ 2 条回归
测试，其中一条是反向断言：不得因折叠而放宽整词规则。

**删之前先对 information_schema 校验整张列表并报出缺失项**。这条校验立刻又抓出 2 个。

## 第四轮：把「客户提问 → AI 回答」整条链路跑通（chatwoot )

结论先说：**平台没有终端用户聊天界面**，提问入口是 Chatwoot（:3000）。
链路：客户在 Chatwoot 发消息 → 签名 webhook → `POST /v1/webhooks/chatwoot`
→ `resolve_chatwoot_tenant(account_id)` → InboxEvent → ai-worker 编排 → 回写。

搭通步骤（下次照做即可）：
1. Chatwoot 首次访问会 302 到 `/installation/onboarding`，表单字段是
   `user[name]/user[company]/user[email]/user[password]`，**密码必须含特殊字符**。
   用 Playwright 自动填即可，不用人工。
2. **account id 从登录后的跳转 URL 拿**（`/app/accounts/3/onboarding` → 3），
   不要用 `Account.first`（库里有遗留的 E2E account id=1，会拿错）。
3. 用户 API token 用 `docker exec <chatwoot-web> bundle exec rails runner
   "User.find_by(email:..).access_token.token"` —— 注意是 `.token`，
   直接 puts `access_token` 得到的是加密对象。`/api/v1/*` 用
   `api_access_token` header，session cookie 会 401。
4. 建收件箱：`Channel::Api.create!(account:, secret:)` + `Inbox.create!(channel:)`
   + `Webhook.create!(url:, subscriptions:['message_created'], secret:)`。
   **secret 必须等于平台的 `APP_CHATWOOT_WEBHOOK_SECRET`**，否则 401。
5. **Chatwoot 在 docker 内，平台在宿主机：webhook URL 必须写
   `http://host.docker.internal:<port>`，写 localhost 会打到自己容器里。**
6. 平台侧插映射：`external_resource_refs(system='chatwoot',
   resource_type='account', external_id=<account_id>, tenant_id=<租户>)`，
   用 `SELECT resolve_chatwoot_tenant('3')` 验证能解析。
7. 起 worker 时把 `APP_CHATWOOT_API_TOKEN` 换成**新账号的** token
   （`.env` 里那个是旧 E2E 账号的，会回写失败）。

验证结果：发 "How do I reset my password?" → 收到
"Let me connect you with a human colleague who can help with that."
（知识库无内容 → 正确弃权转人工，不是故障）。

**顺带修了一个真 bug**：`worker/runner.py` 在 Windows 上根本起不来
（ProactorEventLoop），详见 MEMORY.md。判断方法：worker 打印
`worker_started` 后立刻刷 `worker_cycle_failed` + RuntimeError。

## 阶段 2a 落地：智能体写执行路径（接手 zcode 之后）

按调研报告 附录 B 的拆分建议，完成 **2a 通用写路径**（2b EQ 业务模型仍未做）。

### 核心设计决策

**「智能体可提议、永不批准」**。`integration_service` 原先只有
`{tool.read, tool.write.low}`，而网关在 `propose` 时按 risk class 复核动作，
于是智能体**连提议都被拒** —— AGENTS.md 第 7 条「LLM 可以提议写操作」当时
无法实现，人也永远看不到提议。授予 `tool.write.confirmed`，边界由策略层给出：
唯一能创建 `ActionConfirmation` 的路径是 `POST /v1/tool-proposals/{id}/confirm`，
要求 `case.update`，该角色不持有。`tool.human_approval` 保持不授予。

**风险等级决定行为**（不另立规则）：`low_write` → 提议+执行+校验+回执入证据；
`confirmed_write` → 提议后即止、转人工（`TOOL_CONFIRMATION_PENDING`）；
`human_approval` → 策略拒绝。无候选/无连接器/缺配置/未注册各有 reason code，
**且都不写提议行**。

**一半参数来自租户连接器配置**（`WRITE_ARG_DEFAULTS`：`default_project`
/`default_team`/`default_channel`），未配置则转人工而不是猜 —— 单子开进错误
项目比不开更糟。

**`crm.update_account` 不进选择器**：它要自由格式 `fields` 补丁，从自然语言推导
需要模型，而平台规则是确定性代码决定写入外部系统的内容。列进去只会「每次选中、
每次转人工」，与没上线无法区分。

## 写路径可达性：把分类器改动变成可验证的改动

附录 D 留下的边界（`ACTION_VERBS` 没有 `create`，"请建工单"进不了写路径）本轮处理。
顺序是**先修工具、再改分类器**，因为改分类器的失败模式是"某条问题悄悄换了路由"，
而当时没有任何东西会因此变红。

### 先发现的：`expected_route` 是无人读取的字段

`EvalCase.expected_route` 的**默认值是 `"knowledge_qa"`**，且**全仓库无人读**。
于是 28 条用例里 7 条实际路由是 `sensitive`/`human_required`/`business_read`/
`business_write`，却因默认值"声称"期望知识路径——**审计这份数据集会得出"分类器坏了"的结论**。
（`CaseResult.route` 同样只声明不写入。）

修法是让它变成真的：默认改 `""`（未声明=不检查），`run_case` 比对 `classify()` 路由，
不符则 `ROUTE_MISMATCH` 失败，并写入 `result.route`；给 7 条设计性路由补声明。

**这步是改分类器的前提**——它才是那个"改了会变红"的东西。

### 改分类器：双向覆盖，而不是"论证风险可控"

新增 `create/report/raise/submit/file/open`。全量数据集测量（`measure_action_verbs.py`）
显示六个候选动词**一个都没移动任何用例**——但语料里根本没有这些句式，
所以这只是弱证据。补了**双向守卫**：5 条正向（"Please create a ticket…" → business_write）、
5 条反向（"How do I create a new workspace?" → knowledge_qa）、1 条端到端数据集用例。

**反向守卫立刻抓到真实假阳性**：`Where can I report a bug in the dashboard?` → business_write。
根因：`_has_request_frame` 在句子**任何位置**匹配 `can|could|will|would + I|we + 写动词 + 宾语`，
`report` 一入表就命中。

修法必须窄：该函数存在的理由正是 "Where is my order, **and can I change the delivery address?**"，
所以判据是**相邻性**而非开头词——wh-词紧邻请求框架 → 是疑问句；在后续从句里 → 仍是请求。
另加一条测试锁住后者（否则修假阳性会把真阳性一起修掉）。

该假阳性**早于本次改动就存在**（`where can I change my address?` 同样误触发）。
**教训：写守卫用例 > 论证风险可控。**

## 收尾 2：Cases 页在浏览器里**每次访问都崩**（已修）

管理台能 transition/改优先级/改派，**但不能建工单**——所以包括 `eq_confirmation`
工单在内的所有新工单都只能靠 curl 建。补上「新建工单」面板（标题/描述/优先级/分类/
会话引用/企业账户）后，加浏览器断言，**立刻暴露了一个存在已久的崩溃**：

```
TypeError: Cannot read properties of null (reading 'subject')
  in <CaseDetail>
```

**根因**：详情 loader 在"未选中"分支返回 `{ case: null as unknown as Case }`——
一个**骗过类型系统的谎**（没有那个 cast 根本编译不过）。
渲染处的守卫是 `detail.data ? <CaseDetail c={detail.data.case}/> `，
而 `detail.data` 是个**真值对象**（里面装着 null），于是守卫放行、`CaseDetail`
去读 `null.subject` → 崩。**页面首次加载 resolve 后必崩，也就是每次访问都崩。**

**没有任何测试发现它，因为从来没有测试在浏览器里打开过 `/cases`。**
（新面板恰好是第一个"程序化设置 selected"的东西，但崩溃其实在页面首次加载时就发生。）

**修法**：未选中分支返回 `null`；渲染守卫改成 `detail.data?.case`。

> **可复用的教训：一个为了压住类型错误而写的 `as unknown as X`，
> 就是一个值得去找运行时错误的地方。** 类型系统正好在会抓到它的那一点被关掉了。

### 验收

`.workbuddy-ai/acceptance/approvals.mjs` 现在 **36 项断言全过**，新增 K 段：
面板打开 → 空标题被本地拒（不劳烦服务端）→ 建单成功 → 面板关闭 →
**通过 API 确认工单真的存在且 category 正确**；`Z_page_errors: none`。

## 收尾 3：智能体触发侧 —— 全项目唯一一处"上下文决定路由"

`确认` 没有动词没有宾语，**永远不会被分类成写请求**；脱离上下文它与客套话无异。
但在关联着 `waiting_customer` 的 `eq_confirmation` 工单的会话里，它就是生产在等的答复。
不做 = 客户确认了却什么都没发生。

### 触发条件（四个事实全中）

租户已开写路径开关 + 会话**恰好**关联一张工单（多于一张 → 拒绝）+ 该工单是
`eq_confirmation` 且 `waiting_customer` + 这句话读起来是同意
（`agent_runtime/confirmation.py`：纯词法、**短 / 无否定 / 非疑问**）。

放在编排器而非 `classify`：`classify` 是**文本的纯函数**，这些事实一个都不在文本里。

### 为什么可以接受

**产出有界**：唯一会选中的是 `case.eq_confirm`（`confirmed_write`），
运行停在提议、由人决定；最坏情况是**一条被驳回的提议**。
如果它能**执行**，就需要另一套论证。

**它刻意绕过两道话术级闸门**：`CLARIFY` 降级、`needs_ask` 追问。
两者都是**为话术信号弱而设的补偿**，而上下文正是那个强信号。
对刚回答完平台提问的客户再问"您是说……吗"，正是这两道闸门要避免的循环。

**参数不取自话术**：`case_ref` 来自会话→工单关联。客户不引用工单号，
句子里碰巧出现的数字（"我们要 500 片板子"）绝不能被当成引用。

### 踩坑记录（实现顺序）

1. 先只改 `route` → 仍走 `NEEDS_CLARIFICATION`：**写分支检查的是 `detection.action`**
   （`IntentAction.CLARIFY`），不是 route。
2. 放行写分支的 CLARIFY → 仍失败：**更早还有一道 `needs_ask` 追问闸门**（第 774 行），
   它在写分支之前。两处都要按同一个道理放行。
3. `settings` 在 `run()` 里定义在路由块**之后**，早用会 `used-before-def`；
   用 `self._settings()`（与文件里其他 3 处一致）。

### 验证

- 21 条单测（16 正 + 5 反：长度 / 否定 / 疑问）；**80 字符阈值被测试当场推翻**——

- 5 条集成测试（正常路径真的产出提议且参数为工单 id；无关联 / 非 waiting /
  非 EQ 类 / 否定句 → 均不提议）；
- **变异验证**：上下文查询恒返回 `None` → 正常路径立刻失败；
- 连跑两遍 0 失败、0 残留（夹具按"子表先删"补了 `case_conversations`/`cases`）。

## 收尾 4：给"智能体提议、人批准"这条主控制补上**开的那一侧**

审查时发现：工具网关的**人机分工**是整套设计最关键的控件，但测试只覆盖了它的**关的一侧**

## ⚠️ 事故与恢复：`.git` 被 `git stash` 中断导致仓库不可用（20:00）

**触发**：我为验证一个 flaky 测试是否与我的改动有关，跑了
`git stash push -u -m "..." -- apps/.../intent.py`。该命令被 **SIGTERM 打断**（沙箱超时），
恰好在 git 做 pack 维护的窗口内。

**后果（严重）**：
- `.git/refs/` 整个目录消失 → `git` 报 `fatal: not a git repository`；
- `.git/objects/pack/pack-80b70c8b...pack` **丢失**（只剩 `.idx` 与 `multi-pack-index`）→ HEAD commit 对象不在库中；
- `.git/HEAD` 仍指向 `refs/heads/master`（已不存在）→ 连锁失效。

**幸运之处**：**工作区完全完好**（所有源码、我的全部改动都在）。丢的只是 git 元数据。

**恢复步骤（可复用）**：
1. **不要慌、不要 `git init`**（会毁掉残留对象）——先确认工作区文件完好；
2. 从 `.git/logs/HEAD` / `.git/logs/refs/heads/master` 末行取回**权威 HEAD SHA**
   （本例 `1059ad8bada4db814c38aceb2d2e29fd7e71de60`），并从
   `.git/logs/refs/remotes/origin/master` 末行**交叉验证**同一 SHA → 双侧一致才可信；
3. `mkdir -p .git/refs/heads .git/refs/tags .git/refs/remotes/origin` 重建 refs 目录；
4. `git --git-dir=.git --work-tree=. fetch origin master` —— **从远端拉回全部对象**
   （远端 HEAD 与第 2 步 SHA 完全一致，证明没有丢提交）；
5. `echo <SHA> > .git/refs/heads/master` 和 `.../remotes/origin/master`；
6. 把指向已丢失 pack 的陈旧 `pack-*.idx` **移走**（本例备份到 `/tmp/dead_pack.idx`），
   删掉 `multi-pack-index` 后 `git multi-pack-index write` 重建；
7. 清掉 reflog 里指向丢失 commit 的无效行（`grep -v <lost_sha>` 覆写 `logs/HEAD`
   与 `logs/refs/heads/master`）；
8. `git fsck --no-progress` **输出为空 = 完全干净**。

**核实结果**：`git fsck` 空输出；`git log` 历史正确（HEAD = `1059ad8` "Stop swallowing the
local turn read error in the worker"）；`git rev-parse HEAD` == `origin/master`；
`git status` 正常列出 60 个改动文件；`intent.py` 的 196 行改动完好。

**教训（写给未来的自己）**：
- **在这个环境下不要用 `git stash`**。它的 pack 维护窗口一旦被打断，代价是仓库级损坏。

   播 5 陈旧 + 13 新 → `claim(10)` 返回 **5 陈旧 + 5 新**，新的 5~12 全被排除。
5. 真实运行时插桩：`claimable=13`（全是本次运行的同一租户），但 `claim(10)` 只返回 **9 行**，
   且**最老的那行 `refund-policy-v3` 不在其中** → 典型的 `FOR UPDATE SKIP LOCKED` 被锁跳过特征。

**结论**：`batch=10 < 13`，且循环"每条目只 drain 一次"，只要队列头部有其它可认领行
（上一次中断运行留下的、或并发 worker 正在处理的），目标行在本轮就永远轮不到，
随后断言失败。这是**测量脚本与全局 FIFO 队列的容量不匹配**，属预存缺陷。

**修法建议（未实施，需你定）**：把循环改成"drain 到本条目 `ready` 为止"（带上限次数
防死循环），或把 `batch` 提到 ≥ 队列水位并在断言前 drain 到空。
**不擅自改**的理由：该文件属评测基础设施，且另一会话可能正在动它。

## 结论
FIFO 饥饿已修完并端到端验证；但修的过程中暴露出**更深的未解缺陷**：

## 更正 + 重大环境发现：outbox 有活的消费者（2026-09-19 晚）

### 先更正上一条结论
上一条说 `test_run_once_without_commit_does_not_persist` "单独跑就确定性失败""根因同夹具 uuid 债"。
**两处都不准确**，实测更正：
- 该测试**现在单跑通过**（`1 passed in 1.58s`），`test_billing_ledger.py` 整文件 **3 连跑 12 passed**。
- 那次失败是**我自己的诊断脚本污染**（我插的残留 `queued` 行被 relay 先领走，导致断言的那一行没被处理）。
  也就是说：**它依赖"表里只有它自己那一行"这一前提**，任何并发消费者/残留行都会让它假失败。

### 真正的原因：数据库有一个持续在跑的 outbox 消费者
实测证据链（全部可复现）：
1. `test_outbox_relay.py` 整个文件 **8 个用例全 skip**，理由是它自己的守卫 `_assert_no_live_relay`：
   *"a live worker/relay is consuming outbox rows; `docker compose stop ai-worker-interactive
   ai-worker-outbox` before running this suite"*。
2. `docker ps` **没有** `ai-worker-outbox` 容器（只有 ai-postgres / ai-redis / chatwoot 等 9 个），
   → 守卫告警不是"本地 compose worker"造成的，但**判定是真的**。
3. 最小复现（**纯 SQL、无任何 relay 代码**）：`psycopg autocommit` 直插一行 `status='queued'`，
   t+0.5s 读回已是 **`('sent', 1)`**。即：**插入后不到半秒就被别人处理掉了**。
4. `_assert_no_live_relay` 里同样的探针（v7 id、tenants `...d6`）→ `remaining: 1 | status: sent`。
5. 排除项：`outbox_events` **无触发器**（`pg_trigger` 非 internal 为空）、**无 rewrite rule**
   （`pg_rules` = 0）、列默认值是 `'queued'`/`0`（不是 sent）。
6. `pg_stat_activity` 只看到 9 个 `idle`/`COMMIT` 的池化连接（`platform`/`platform_app`），
   采样 40 次×0.25s 也没抓到活跃的 claim 查询 → 消费者**连接是短暂/间歇的**，或不在本机 DB 上出现。

**结论**：有一处**外部**（非本地 docker、非本会话 Python 进程）的 relay 在消费 `platform` 库的
outbox。这会**污染所有断言"outbox 里只有我这一行"的测试**。

### 对我这轮改动的影响（重要）
- `test_billing_ledger.py` 的 `uuid7()` 改动**本身是干净且正确的**（3 连跑全绿）。
- 但 `test_outbox_relay.py` 的 id 改动**无法在本环境验证** —— 8 个用例被守卫 skip，
  守卫判定"有活消费者"是**真的**，不是误报。
- 因此我把该文件的 `gen_random_uuid()`→`uuid7()` 改动视为**正确但未验证**（unverified），
  必须等消费者停掉后重跑才能确认。
- **遗留风险**：`test_billing_ledger` 这类测试会继续与那个外部消费者**竞态**，
  表现为间歇性 `RelayStats(claimed=0)`。这不是代码 bug，是环境问题。

### 给下一个人的操作建议（按序）
1. 先找出并停掉那个外部消费者（不在 `docker ps` 里；查本机其它进程 / 另一个 IDE 会话 /
   另一个 worktree 的 `python -m worker` / 远程 compose）。
2. 停掉后重跑 `test_outbox_relay.py`（应从 8 skip 变成真跑）与 `test_billing_ledger.py`。
3. 若短期停不掉：给这类测试加**租户隔离**或**行级过滤**（只处理自己租户/自己 id 的行），
   而不是依赖"表里只有我一行"。`_assert_no_live_relay` 已是对的防御范式，可推广。
