完整修复记录见 `docs/acceptance-defects-2026-09-19.md` 的"修复记录（同日第二轮）"一节。

**这次真正学到的（可复用的排查套路）**：

- **"假成功"要往 HTTP 状态找，不要往 UI 找。** 三个 router 的 `_xxx_error()` 返回裸 dict，
  FastAPI 渲染成 200；前端 `unwrap()` 只看 `!res.ok`。**判断一个写操作到底成没成，
  直接 `curl -i` 看 status，再看 UI 到底显示了什么** —— 两者不一致就是这类 bug。
- **修这类"旧行为被测试固化"的 bug，先跑定向测试再改断言。** 3 个测试名写着
  "is_not_found_not_500" 却断言 `== 200`；改完断言后新增
  `test_refused_release_actions_are_never_200` 锁住契约（用 `DOMAIN_ERROR_STATUS` 取值，
  不写死数字）。
- **移动端"视口被撑大"的真因往往是 min-content，不是宽度写死。**
  Branding 撑到 449px 不是因为 `width`，而是 `.field` 里「标签 + input」的 min-content
  之和超过屏幕；`min-width:0` 不够，要把 `.field` 改成纵向堆叠才彻底好。
  排查方法：在页面里遍历 `getBoundingClientRect().width > 400` 的元素，看谁最宽。
- **ruff E402/I001 会因为"在 import 之间插了语句"而连锁报错。** 在 main.py 顶部加
  `logger = logging.getLogger(__name__)` 之前没插在 import 中间就没事；插进去后
  后面 28 个 import 全报 E402。logger 定义要放在所有 import 之后。
- **验收复跑必须重启后端才作数。** 前端 Vite 有 HMR，后端没有 —— 我一开始改完 Python
  就跑 journey，结果全是旧行为。用 `APP_API_PORT=8010` 起第二个实例 + Vite
  `VITE_API_TARGET` 指过去，比杀掉别人起的 8000 端口进程安全。

**顺手发现并修掉的 3 个新问题**（原报告没有）：
1. `QuotaIn.monthly_run_quota` 无上界 → 超过 int4 就 DB 溢出 → 500。加 `le=2**31-1`。
2. 未处理异常返回裸文本 `Internal Server Error`，违反 api-contracts 的两形状契约，
   且没有 trace_id。加兜底 handler（细节只进日志，不回显）。
3. 422 走 FastAPI 默认 `{"detail":[...]}`，前端落到 `HTTP 422` 兜底文案；且默认体会
   **回显 input**（可能是 token/prompt）。改成只回"字段: 原因"。

**踩到的坑**：一次失败的测试会把 fixture 租户留在库里，下一轮直接 50 个 setup
`IntegrityError`。清理要用 `begin_nested()` 逐表删（否则一个 FK 违规整事务中止）
+ 多轮 sweep（子表先删）。删除前确认只删 `slug <> 'admin-demo'` 的确定性 fixture。

**已知未修**：工单页无"新建"入口（产品决策）；fixture 清理应改用事务回滚而非手动扫库。

## 第四轮：接手 zcode 的华秋落地实现

**断点怎么定位的**：`git status` 找 untracked 里的 `scripts/seed_huaqiu.py`，再跑全量
套件看谁红。结论：zcode 停在"加了 5 条华秋 eval 用例、其中 2 条失败、门禁红"。

### 两个失败的根因都是「用例/语料编写缺陷」，不是平台缺陷

oracle 回显整段证据，于是：发票政策原文同时含两个分支 → 禁"手动申请"必炸；
赔付原文写"**不**承担…（包括 PCBA 停工损失）" → 禁"停工损失"必炸。
**子串匹配分不清否定与断言**（与之前 "refund window" 命中 "Are monthly plans
refundable?" 是同一族）。修法：发票按分支拆成两条语料（顺带让"检索选对分支"成为
真正被测的能力），赔付改用原文中不存在的承诺型字符串（无上限/全额赔偿）。
**变异验证**：反转检索排序后两个变体用例双双失败 —— 无法观察到失败的守卫不算证据。

### 顺手挖出一个真平台缺陷

`normalize_colloquial` 把查询转小写、却用**原样别名**匹配 → 含大写字母的别名
（V割 / EQ / MI / TGZ，即 PCB 缩写词汇的全部）**永久不命中**。既有 3 条测试全用
小写别名，所以它活下来了。已修（别名同样 case-fold，拉丁整词规则不变）+ 2 条回归
测试，其中一条是反向断言：不得因折叠而放宽整词规则。

### `--purge` 从来没真正删过东西

PURGE_TABLES 里 3 个表名不存在（knowledge_gap_drafts / case_events / tenant_branding），
DELETE 抛错 → 整个事务回滚 → 什么都没删却看起来"吵闹地失败了"。修法：删幻影名 +
**删之前先对 information_schema 校验整张列表并报出缺失项**。这条校验立刻又抓出 2 个。

### 环境提醒

- `release_check --evidence-only` 要 PYTHONPATH，而 Git Bash 的 `$(pwd)` 给 POSIX 路径、

## 第四轮：把「客户提问 → AI 回答」整条链路跑通（chatwoot )

结论先说：**平台没有终端用户聊天界面**，提问入口是 Chatwoot（:3000）。
链路：客户在 Chatwoot 发消息 → 签名 webhook → `POST /v1/webhooks/chatwoot`
→ `resolve_chatwoot_tenant(account_id)` → InboxEvent → ai-worker 编排 → 回写。

搭通步骤（下次照做即可）：
1. Chatwoot 首次访问会 302 到 `/installation/onboarding`，表单字段是
   `user[name]/user[company]/user[email]/user[password]`，**密码必须含特殊字符**。
   用 Playwright 自动填即可，不用人工。
2. **account id 从登录后的跳转 URL 拿**（`/app/accounts/3/onboarding` → 3），
   不要用 `Account.first`（库里有遗留的 E2E account id=1，会拿错）。
3. 用户 API token 用 `docker exec <chatwoot-web> bundle exec rails runner
   "User.find_by(email:..).access_token.token"` —— 注意是 `.token`，
   直接 puts `access_token` 得到的是加密对象。`/api/v1/*` 用
   `api_access_token` header，session cookie 会 401。
4. 建收件箱：`Channel::Api.create!(account:, secret:)` + `Inbox.create!(channel:)`
   + `Webhook.create!(url:, subscriptions:['message_created'], secret:)`。
   **secret 必须等于平台的 `APP_CHATWOOT_WEBHOOK_SECRET`**，否则 401。
5. **Chatwoot 在 docker 内，平台在宿主机：webhook URL 必须写
   `http://host.docker.internal:<port>`，写 localhost 会打到自己容器里。**
6. 平台侧插映射：`external_resource_refs(system='chatwoot',
   resource_type='account', external_id=<account_id>, tenant_id=<租户>)`，
   用 `SELECT resolve_chatwoot_tenant('3')` 验证能解析。
7. 起 worker 时把 `APP_CHATWOOT_API_TOKEN` 换成**新账号的** token
   （`.env` 里那个是旧 E2E 账号的，会回写失败）。

验证结果：发 "How do I reset my password?" → 收到
"Let me connect you with a human colleague who can help with that."
（知识库无内容 → 正确弃权转人工，不是故障）。

**顺带修了一个真 bug**：`worker/runner.py` 在 Windows 上根本起不来
（ProactorEventLoop），详见 MEMORY.md。判断方法：worker 打印
`worker_started` 后立刻刷 `worker_cycle_failed` + RuntimeError。
