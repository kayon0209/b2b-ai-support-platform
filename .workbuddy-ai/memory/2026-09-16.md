# 2026-09-16（续 3）— 工具执行器注册：connecting connectors → executors

## 背景：一个"接口齐备但永远执行不了"的缺口

`ToolGateway.__init__(session, executors)` 从设计上就要求外部注入
`dict[str, ToolExecutor]`（为了授权/确认/幂等可脱离网络测试），
但**从来没有任何代码提供这个 dict** —— 三个调用点全部传 `{}`。
后果：确认式写入（confirmed_write）永远停在 `TOOL_EXECUTOR_MISSING`，
工具网关的整套确认流程实际上无法触达任何适配器。

## 新增 `tool_gateway/registry.py`

解析粒度是**每租户、每请求**：

- 适配器从**调用方租户自己的 `connectors` 行**构建。若做进程级
  "tool name → adapter" 全局缓存，会让 A 租户的凭据服务 B 租户的写入。
  故 resolver 用租户 session 构造，缓存生命周期 = 一个请求。
- 连接器必须**声明该工具所需的 capability**。为读而连的 Jira
  不会变成创建 issue 的通道（这是网关已保证的同一性质在连接器层的另一半）。
- 只有 `status='active'` 的连接器可解析 —— 已知损坏的连接上执行写入
  只会产生需要人工追查的模糊结果。
- 缺适配器降级为 `TOOL_EXECUTOR_MISSING` 而非 500，
  这样"尚未接入的后端系统"其确认流程仍可被检视。
- 凭据只传引用（`credential_ref`），本模块绝不解读密钥。

## 写这个模块时发现的真实缺陷（本次最有价值产出）

**`CrmReadAdapter` 不满足 `ToolExecutor` 协议。** 它继承基类
`ConnectorAdapter.execute(command, parameters, idempotency_key) -> ExecutionResult`
与 `verify_postcondition(execution: ExecutionResult) -> bool`，
而协议要求
`execute(tool_name, parameters, idempotency_key) -> dict | None`
与 `verify_postcondition(tool_name, parameters, output) -> bool | None`。
**签名完全不同** → 一旦注册，首次执行就会 `TypeError`。

只有 `JiraAdapter`（jira.py:129/140）自己重写了这两个方法，真正符合协议。

# 2026-09-16（续 4）— Outbox relay：从"只写不读"到真正投递

## 缺口性质

`cases/router.py` 在**业务状态变更的同一事务内**写入 `case.created` /
`case.updated` outbox 行 —— 这正是文档要求的模式。但**没有任何代码读取它们**：

- 事件永远堆在表里；
- 审计轨迹暗示"下游已收到通知"，而实际上从未离开进程；
- 事务性 outbox 只做到一半就停住了。

`outbox_service` 早已备好 `claim_pending`（SKIP LOCKED）/`mark_sent`/`mark_failed`，
缺的只是调用者。

## 新增 `apps/worker/src/worker/outbox_relay.py`

刻意的语义选择（**改动前请先读这里的理由**）：

- **至少一次投递（at-least-once）**。先 publish 后 `mark_sent`，
  崩溃会导致重发。反过来（先标 sent 再 publish）会**静默丢事件**——
  对客服系统而言，重复远好于丢失。消费者用稳定的 `event_id` 去重，
  这也是 `event_id` 独立于主键存在的原因。
- **有界重试后"停靠"（parked）**。处理失败时记录 `last_error` 并**保持
  `queued`**，使该行始终可见、可人工重排。超过 `MAX_ATTEMPTS` 后不再消耗
  轮询周期，但**绝不标记为 `failed`** —— 那会掩盖一个从未送达的事件。
- **失败按事件隔离**。一个毒丸 payload 不会中断或回滚整批。
- **无 handler 视为已投递**。没人消费的事件类型标记 sent，而不是对着
  不存在的消费方无限重试（否则 `pending_count` 会失去运维意义）。

## compose

新增 `ai-worker-outbox` 服务，**刻意不与 interactive worker 合容器**：
投递业务事件不依赖 AI 链路，故该 relay **无需 LLM key** 即可运行。
`python -m worker.runner --outbox-only` 可单独启动它。
（`main()` 默认 `asyncio.gather` 同时跑 inbox worker 与 relay。）

## worker 静默空转修复 + 首个真实端到端验证（提交 47d548f 及后续）

### 修复：worker 组装了 4 个 None 的 OrchestratorDeps

`runner.main()` 原来构造 `OrchestratorDeps(embedder=None, generator=None,
sender=None)`。orchestrator 把「没有 generator」当作 abstain、把「没有 sender」
当作「没发出去，但不是失败」（`_dispatch` 里 `if self._deps.sender is None:
return ""`），于是 worker 会领走真实客户消息、把 inbox 行标成 COMPLETED、
**一个回复都不发，而且全程不报错**——日志和监控里看全是成功。

新增 `apps/worker/src/worker/wiring.py` 作为唯一组装点：
- 缺 LLM key 直接 fail closed（`WorkerConfigurationError(SystemExit)`，
  容器非 0 退出 + 可读信息，而不是 traceback）
- `--outbox-only` 保留给确实不要 AI 链路的部署
- sender 和 reader 是**同一个 ChatwootClient**（共享连接配置和熔断器），
  否则收发对「Chatwoot 是否挂了」会有两个不同判断
- `audit_wiring` 的 `has_chat` 取自 **generator**（orchestrator 真正查的东西），
  不是 bundle——有 bundle 没 generator 恰好就是「每次都 abstain」的状态
- **空 token 视为无 token**：compose 写的是 `${APP_CHATWOOT_API_TOKEN:-}`，
  变量永远「已设置」（常常是空串），只判 `is not None` 会绑一个每次都 401 的
  client

测试 240 → 247。7 个 wiring 测试 + 1 个空 token 测试。

### 首个真实 Chatwoot 端到端验证（关键）

用 `rails runner` 取到了真实 token（account 1 "E2E Tenant"，API Inbox 1，
contact 1 "E2E Customer"），并发真实客户消息。结果：

- ✅ **收 → 生成 → 发 全链路打通**：worker 日志
  `run_completed route=knowledge_qa status=completed chunk_count=1
  latency_ms=15039`，Chatwoot 会话里出现了真实 AI 回复
- ✅ require 的 wiring 审计日志 / NO_CHATWOOT_TOKEN 警告按设计工作
- ✅ **发现并修复一个无限回复循环**（见下）

### 🐞 重大缺陷：AI 回复自己的回复（无限循环）

Chatwoot 对 **outbound 消息同样发 `message_created` webhook**，而
`inbox_consumer` 只检查 `event_type == "message_created"`，**从不检查消息方向**。
于是 AI 的回复又变成新的 inbox 事件 → AI 再答 → 无限循环。

实测证据：**一条**客户提问（"What is the refund window for annual enterprise
plans?"）导致 agent_runs 一路写到 message id **17**；`message_type` 字段明明
是 `outgoing`、`sender_type=user`，但消费者完全没看。
已 `docker compose stop ai-worker-interactive` 止血并把残留行标 completed。

修复（`inbox_consumer.py`）：
- 新增 `CUSTOMER_MESSAGE_TYPES = {"incoming"}` 和 `is_customer_message()`
- `process_event` 在 `event_type` 检查之后再过一道方向检查，非客户消息
  → 记 `event_skipped_not_customer` 日志 → ack 不答
- 默认方向是**不对称**的：只有显式 `incoming` 才答，缺失/未知一律不答。
  理由：漏答可由人工补救，回复循环不可挽回
- 新增 8 个回归测试（`test_self_reply_guard.py`），含 `0`/`1` 整数
  message_type（Chatwoot REST 用整数、webhook 用字符串，两种形状都不能漏）

### 踩坑（可复用）

- **`FOR UPDATE SKIP LOCKED` 返回 0 行不一定是查询写错了**：先查
  `pg_stat_activity` 里有没有 `idle in transaction` 的会话占着行锁。
  本次就是被一个泄漏事务挡住，误判成 claim 逻辑 bug。
  排查 SQL：`select pid,state,xact_start,now()-xact_start from
  pg_stat_activity where datname='platform' and state like '%transaction%'`
- **compose 的 `.env` 默认在 compose 文件同目录**，不在项目根。项目根有
  `.env` 时必须显式 `--env-file .env`，否则 `${APP_...:-}` 全部取到空默认值。
  表现是容器里 `KEY_LEN=0`。
- 取 Chatwoot token：
  `docker compose exec chatwoot-web bundle exec rails runner "puts
  User.first.access_token.token"`
- 本机 `PYTHONPATH` 环境变量被外部预设（WorkBuddy shim），
  `export PYTHONPATH=$(pwd)/...` 里的 `$(pwd)` 会展开成含中文的路径且
  整个变量被覆盖；用**字面量绝对路径**赋值才可靠。
