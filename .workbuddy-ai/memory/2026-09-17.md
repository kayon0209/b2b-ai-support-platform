## Backend: five real defects, found by making auth actually run

The frontend work forced the API to be exercised for real, which is what
surfaced these. All five are in `AGENTS.md` security-checklist territory.

1. **Auth resolution returned `role=None` for everyone** (most severe).
   `bootstrap_token_resolver` synthesised a tenant id with
   `uuid5(namespace, f"tenant:{slug}")` and pointed at a
   `resolve_membership` function that did not exist. Result: **every**
   authenticated endpoint returned 403 for **every** user, including
   `tenant_owner`. Tests missed it because the unit test only asserted
   `actor_id` round-trips and the integration tests fabricate roles via
   `_RoleResolver`.

2. **ORM enum storage contract mismatch.** `Tenant.status` / `Membership.role`
   were bare `Enum(...)`, which persists member *names* (`ACTIVE`), over
   migrations that create plain `String` columns holding lowercase *values*.
   Every ORM read raised `LookupError`.

3. **RLS binding order.** `memberships` is FORCE RLS; an unbound read matches
   the predicate against NULL and returns zero rows — indistinguishable from
   "no membership". Resolution had to become two steps (read `tenants`, bind,
   then read `memberships`).

4. **Missing app-role grants / RLS bootstrap problem.** Resolving a token needs
   a membership row readable *before* any tenant is known, which RLS forbids by
   construction. See the design note below.

5. **`psycopg.InterfaceError: cannot use ProactorEventLoop`** — a deployment-level
   blocker on Windows. uvicorn hardcodes a Proactor loop and builds it before
   importing the app, so nothing in `main.py` at import time can fix it. Fixed by
   a `ensure_async_db_loop()` guard (loud error instead of a silent 401 storm)
   plus a `python -m platform_core.main` entrypoint that passes
   `loop=asyncio.SelectorEventLoop`.

6. **Intermittent `test_outbox_relay` failure — a real test-isolation defect.**
   `test_queued_event_is_delivered_and_marked_sent` asserted `stats.claimed == 1`,
   but `claim_pending` scans the outbox **globally** (correct in production: one
   relay drains everything). Another suite committing a real `case.created`
   event, or a run interrupted before cleanup, leaves queued rows that get
   claimed in the same batch → `claimed == 2`.
   Diagnosed by A/B: injected a stray queued row, confirmed the old code fails
   and the fix passes. Fixed by having the module's `_cleanup` also delete
   `status = 'queued'` rows (sent rows are inert), which makes the suite
   hermetic so the strict batch assertions stay meaningful.
   Lesson recorded: this failure looks exactly like a code bug in the relay and
   is ordering-dependent, so "it passed just now" proves nothing.

Also: `except Exception` in the middleware was swallowing everything with no
log line, which is precisely why #5 took so long. Now logs path + exception type
(never the token). That log is what finally located the Proactor problem.

## RLS bootstrap: the design decision worth recording

Adding a policy exception (`app.tenant_id IS NULL OR ...`) would have granted
table-wide cross-tenant reads. Instead: migration `0015_membership_bootstrap`
adds `resolve_active_membership(slug, user_id)`, a `SECURITY DEFINER`
read-only function with a pinned `search_path`, granting EXECUTE but not SELECT.

Verified by attempting to falsify it (probe run then deleted):
- wildcard/metacharacter slugs (`%`, `_`, `' OR '1'='1`) → 0 rows;
- LATERAL composition into a table scan → 0 rows (base table still RLS'd);
- direct `SELECT` on `memberships` → still 0 rows;
- `DROP FUNCTION` as the app role → blocked;
- `prosecdef = true`, `search_path` pinned, owner is not the app role.

These are now executable assertions in `test_membership_resolution.py`.

# Session 2 — ingestion pipeline built end to end

## What was added

  chunk / embed / index / advance. Idempotent (delete-then-insert chunks).
  Failures split by recoverability: dependency fault → release claim back to
  `uploaded`; document defect → terminal `failed`.
- Migrations `0017` (timestamp columns + triggers + partial claim index),
  `0018` (`claim_ingestion_versions()`), `0019` (`reclaim_stale_ingestions()`).
- `apps/worker/src/worker/runner.py` — `APP_WORKER_QUEUE` selects the role
  (interactive / ingestion / outbox); one image, three deployments.
- `tests/e2e/e2e_ingestion_minio.py` — the real path against real MinIO.

## The four defects (all found by running, none by reading)

1. **`document_versions` had no `created_at` and no `updated_at`.** The claim
   orders by `created_at` and stale-recovery compares `updated_at`; both were
   imaginary. `DocumentVersion` does not use `orm_base.TimestampMixin`, and
   reading the model file agreed with the wrong schema — so the model was
   wrong too, not just the migration.

2. **RLS silently no-ops an UPDATE for an unbound app role.** Measured, not
   inferred:
   ```
   unbound UPDATE document_versions ... WHERE id = <known id>  → rowcount 0
   bound   UPDATE document_versions ... WHERE id = <known id>  → rowcount 1
   SELECT count(*) FROM document_versions: platform → N rows, platform_app → 0
   ```
   No error, no exception. The claim reported `claimed=1` and persisted
   nothing, which would have caused the same document to be ingested
   repeatedly by different workers. Fixed by binding the tenant per row
   (the tenant comes from the row itself — not an escalation) and by moving
   the cross-tenant scan into a `SECURITY DEFINER` function (0018).

3. **`reclaim_stale_ingestions(0)` reclaimed nothing.** Both `updated_at` and
   `now()` are whole seconds, so a row touched this second has
   `updated_at == now`; `<` never fires. Semantics are "at least this stale",
   so the cutoff must be `<=`.

4. **An explicit NULL from the ORM overrides a column DEFAULT.** After 0017
   added the NOT NULL timestamps, every upload returned HTTP 503
   `IntegrityError: null value in column "updated_at"` — SQLAlchemy emitted
   `updated_at = NULL` explicitly because the ORM metadata had no
   `server_default`, and an explicit NULL wins over the table's `DEFAULT`.
   The trigger cannot help: it runs after the row reaches the table, by which
   point the value is already NULL.
   The `server_default` must be a **dialect-neutral literal** (`0`), not
   `EXTRACT(EPOCH FROM now())`. Unit tests build the schema with
   `Base.metadata.create_all` on SQLite, which cannot parse `EXTRACT(...)` —
   that broke all 13 `tool_gateway` tests with a DDL error. On Postgres the
   trigger overwrites the placeholder, so the honest value always wins.

## Test isolation: two lessons re-confirmed

- The claim function is tenant-agnostic **by design** (one bulk worker serves
  all tenants), so any leftover `uploaded` row anywhere enters every test's
  batch. A manual probe of mine leaked one row into a *seeded* tenant and
  `test_ingestion_produces_chunks_and_marks_ready` failed with
  `IngestStats(claimed=2, ready=2)` — a message that reads exactly like a
  pipeline bug. Fixed properly: an autouse fixture now moves claimable rows
  **outside this suite's two tenants** to `expired` (not deleted — it is
  someone else's row, and deleting data to make a test pass is the wrong
  trade). This mirrors the `test_outbox_relay` incident from session 1.
- Deleted every throwaway `scripts/_probe_*.py` before committing. The probe
  that caused the leak above is precisely why: ad-hoc scripts that write to
  the real database are the leak source, so they must not outlive their use.

## Gotchas worth keeping

- `FOR UPDATE` requires `VOLATILE`; PostgreSQL rejects it in a non-volatile
  function at creation time.
- `PARSING → UPLOADED` is not in `knowledge/ingest.py:_TRANSITIONS`, so
  releasing a claim must assign the state directly, not via `transition()`.
- The worker needs `embed(texts) -> EmbeddingResult` (batch), while
  `hybrid_search` needs `Embedder.embed_query(query)` (single). Two different
  interfaces on purpose. A stub implementing only one of them will look like
  a passing test while the other path is never exercised.
- `drain_ingestion_once` does **not** commit, same contract as
  `inbox_consumer.drain_once` — the caller owns the unit of work.
- `EXPECTED_MIGRATIONS` in `test_migration_and_performance.py` is a deliberate
  speed bump: bump it when adding a revision. 16 → 19.

# Session 4 — CRM write adapter + idempotency enforcement

Two more tracked gaps closed, both from the "still open" list.

## CRM write adapter (commit 97b6eea)

Only `jira.create_issue` had an adapter; `crm.update_account` had been removed
because `CrmReadAdapter` did not satisfy `ToolExecutor` (its inherited
`execute` took an `ExecutionResult`). Added `CrmWriteAdapter(CrmReadAdapter)`:

- closed writable set (`tier`, `contract_status`); an unknown field is refused,
  not forwarded, so a prompt injection cannot rewrite arbitrary account state;
- postcondition verified by re-reading the account with the read cache
  invalidated first (otherwise it compares against the pre-update projection
  and reports a false failure); an ambiguous transport outcome verifies to
  None (UNKNOWN), not False;
- registered in `TOOL_CAPABILITY` / `TOOL_PROVIDER` / `default_factories`. The
  capability gate means a lookup-only CRM connector never becomes a write
  path (gateway reports `TOOL_EXECUTOR_MISSING`).
- `ToolExecutor` is now `@runtime_checkable`.
Tests: 9 adapter unit, 2 registry, 2 HTTP end-to-end. Docs updated.

## Idempotency on every write command (commit dc04519)

AGENTS.md requires an Idempotency-Key on every write command; only
cases/commands, identity, tool-gateway and agent-runs enforced it. Prompt
release, feature flags, knowledge gaps, knowledge upload/ready and case
creation accepted writes without one — a retry after a timeout then looks
like a new command (duplicate drafts / documents / tickets).

- `api.py`: `require_write_idempotency(request, action)` + a `READ_ACTIONS`
  set. Expressed as the read set so a new write action is covered by default.
- Enforced inside the single `_gate` of the prompt/flag/gap/knowledge routers
  (17 write endpoints in one place), and in `cases` create.
- Note: the fresh-app test harness copies only `app.router.routes`, NOT
  middleware or exception handlers — so a router-level dependency or a custom
  exception handler would not exist under `TestClient(fresh_app)`. Enforcing
  inside the handler/gate is what the harness supports.

# Session 6c — third reverse-audit find: retention policy never ran

Same technique, third hit. `evaluation/pii.py::sweep_expired_data` implements
the per-tenant retention policy (superseded versions -> expired after 30d,
resolved dead letters pruned after 14d, completed inbox events pruned after
90d). It is even covered by `test_retention_sweep.py`, which calls it
directly. But **no application code called it**, so nothing ever expired.

That is the inverse of the usual "untested code" problem: the function was
tested and correct, and the missing piece was the caller. A direct-call test
cannot detect a missing caller — only a test that drives the *production
path* can.

Fix (`51f27cd`):
- `worker/retention_consumer.py::drain_retention_once()` lists active tenants
  (`tenants` is global reference data, so the app role can read it before any
  context exists) and sweeps each in its **own** RLS-bound transaction, so one
  tenant's failure cannot roll back another's completed sweep.
- `runner.py` gains a `retention` role on a long interval (policy is measured
  in days; the sweep is idempotent).
- `infra/compose/docker-compose.yml`: `ai-worker-retention`.
- Tests cover the **wiring** (every tenant swept, counts aggregated, failure
  propagates) and that the role is selectable.

Also dead in the same module: `minimize_payload` and `classify_field` (0
callers). Left alone for now — `minimize_payload` is the "minimize before a
boundary crossing" helper; the inbox path minimizes via
`support_bridge.minimize` instead, so wiring it would be a separate call.

**Reverse-audit score: 3 defects, 0 false alarms.** All three were
"implementation complete, invocation missing":
1. `AgentRun.started_at` — never written (dashboard blind).
2. `AgentRun.token_usage` — never written (no metering).
3. `sweep_expired_data` — never called (no retention).

## The real find: `credential_ref` was never dereferenced (754cfa3)

`registry.ConnectorExecutorResolver` built every `ConnectorContext` with
`credentials={}`, so **every adapter sent an empty Authorization header**:
the tool gateway could not authenticate to a real Jira or CRM at all. The
registry's own comment said "the reference is passed through, not
dereferenced here" — but it was not passed through either, just dropped.

Fix: `integrations/credentials.py::resolve_credentials()` implements the
pilot `env://VAR` scheme (JSON object -> credentials mapping; bare value ->
`api_token`). Any other scheme (including the `vault://` refs in tests)
resolves to **nothing** — fail closed, so a call fails loudly instead of
looking like a real attempt. The resolver is *injected* into the executor
resolver, preserving the registry's "never read a secret here" invariant.
Production swaps this one function for a secret-manager client.

**Reverse-audit score: 4 defects, 0 false alarms.** The 4th is the first
one that is not a missing *writer* but a missing *dereference* — same
family (a value stored and never consumed).

## Open, needs a decision (not a code fix)

A production secret store (Vault / cloud SM / sealed secret) needs an ADR
per AGENTS.md rule 9. Until then: connectors with `vault://` refs are
configurable but cannot authenticate; connector health checks cannot run
(they would need credentials, and probing without them would mark healthy
connectors DEGRADED, which is worse than not probing).
