## The design decision worth recording

`ConnectorAdapter.health_check()` in the pilot adapters calls
`GET {base}/health` **with no Authorization header** (`crm.py:98`). So:

> a successful probe is **not** evidence that the credential works.

Two consequences, both now encoded in `integrations/health.py`:

1. **A probe may never clear `NEEDS_REAUTH`.** If reachability could lift it,
   an expired credential would be silently re-armed, and the next thing the
   platform does with an `active` connector is execute a **write** through it.
2. `NEEDS_REAUTH` is only cleared by an explicit operator action that also
   demonstrates the credential now **resolves** (`can_clear_reauth` requires
   both reachable *and* `credential_is_present`). The second condition catches
   "operator repointed the reference at a variable they forgot to set" - the
   failure that would otherwise leave the API reporting `active` for a
   connector that still cannot authenticate.

Also: `{"api_token": ""}` counts as **absent**. It produces
`Authorization: Bearer ` (empty), which is not a credential and would make a
connector look configured while every call 401s.

## What landed

- `integrations/health.py` - pure transitions (`status_after_probe`,
  `status_after_auth_failure`, `can_clear_reauth`) plus the async recorders.
  **Pure by design**: the rule that decides whether a connector may execute
  writes is then verifiable without Postgres.
- `tool_gateway/registry.AuthReportingExecutor` - adapters report a rejected
  credential by *returning* `CONNECTOR_AUTH_EXPIRED` in a dict, not by
  raising, so nothing in the tool path observed it. The wrapper is applied at
  build time (it needs the `Connector` row) and delegates
  `verify_postcondition` unchanged.
- `integrations/router.py` - `GET /v1/connectors`,
  `POST .../health-check`, `POST .../reactivate`, `PUT .../credential-ref`.
- `EventType.CONNECTOR_NEEDS_REAUTH` + payload schema (emitted only on the
  *transition* into NEEDS_REAUTH, so a repeatedly-failing connector notifies
  once).
- `Action.CONNECTOR_READ` / `CONNECTOR_ADMIN`: intentionally separate from the
  tool vocabulary. `support_admin` reads health (their tools broke);
  rotating a credential is `tenant_owner` only.

## Test seam choice

`probe_connector` is monkeypatched in the reactivation *success* test only.
Standing up an HTTP server to answer `/health` would test `httpx`, not the
gate. The unreachable paths use `http://127.0.0.1:9` (discard port) so a

# Session — dead letters, and a P1 ingestion regression the e2e caught

Docker Desktop came up. Started `ai-postgres`/`ai-redis` via compose; `minio`
could not be pulled (`minio/minio:latest` -> "pull access denied"), so the e2e

`tests/e2e/e2e_ingestion_minio.py` expects anyway.

## The regression: every API-uploaded document failed to ingest

Running the e2e (not the suite) surfaced it:

```
IngestionError: unsupported content type for parsing: "text/markdown"
```

Note the **quotes around the value**. `parse_document` matches exact content
types, so `"text/markdown"` - with quotes - matches nothing.

Root cause, proved against the live database before touching anything:

```sql
'{"content_type": "text/markdown"}'::jsonb ->  'content_type'  ::text  => "text/markdown"
'{"content_type": "text/markdown"}'::jsonb ->> 'content_type'         => text/markdown
```

`->` returns a **JSON** value, and casting a JSON *string* to `text` keeps its
surrounding double quotes. Migration `0024_claim_content_type` used `->`;
migration `0025_fix_claim_content_type` uses `->>`. The function body was
verified by reading `pg_proc.prosrc` after the upgrade.

**Why the suite stayed green.** `_make_version` in `test_ingestion_worker.py`
seeded versions with **no** `content_type` in metadata. `->` on a missing key
yields SQL NULL from either operator, the worker falls back to markdown, and
everything passed. Only the real upload path - the one the API writes
`metadata.content_type` for - failed. That is the shape of coverage gap worth
remembering: the fixture did not reproduce the production row.

Fixed by:
- migration `0025` (`->>`), `EXPECTED_MIGRATIONS` 24 -> 25;
- `_make_version(..., content_type=...)` so the fixture can seed the way the
  API does;
- `test_the_claim_returns_an_unquoted_content_type` - asserts the **exact**
  string, because `in` would have accepted the buggy value;
- `test_an_api_style_upload_with_a_content_type_ingests_to_ready` - the e2e
  path pinned in the suite, so this cannot regress back to e2e-only detection.

Related trap hit while writing the fixture: `document_versions.metadata` is
NOT NULL with a `'{}'::jsonb` default, and passing an explicit NULL in the
INSERT **overrides** that default -> `NotNullViolation`. Same family as the ORM
`server_default` note already in `MEMORY.md`.

## Dead letters: from "model with no producer" to visible work

`DeadLetterItem` had a model and a retention sweep and **no producer**, so a
connector operation that exhausted its bounded retries left nothing behind but
a failed `ToolExecution` row nothing listed.

- `integrations/dead_letter.py`: `operation_digest` = `"{tool}:{sha256(params)[:32]}"`.
  The **payload is never stored** - it can be customer-derived and this row is
  read by an operational endpoint and copied into backups. The digest still
  answers "is this the same operation failing 40 times?".
  `sort_keys=True` is load-bearing: without it a different insertion order
  produces a different digest and that grouping silently stops working.
- `AuthReportingExecutor` renamed to **`ConnectorOutcomeExecutor`** - after it
  also produced dead letters the old name was actively misleading, which is
  the exact defect class this repo audits.
- Classification: auth rejections are **excluded** (they have NEEDS_REAUTH,
  and duplicating them would fill the queue with rows whose fix is "rotate the
  credential"), everything else - including `ambiguous` transport failures -
  is recorded. Ambiguity outranks the error code; the row says
  `AMBIGUOUS_OUTCOME` because the operator's first question is "did it land?",
  which the error code cannot answer.
- **No replay endpoint, deliberately.** The payload is not here by design, and
  an ambiguous row cannot be safely retried until someone establishes whether
  the first attempt landed - an operator decision, not a loop.
- `GET /v1/dead-letters`, `POST /v1/dead-letters/{id}/resolve` (idempotent:
  a second resolve writes no second audit event).

# Session — resumable connector sync, then connector webhooks

## Sync: two "never consumed" defects, and the bug the caller exposed

`SyncCursor` was referenced by **nothing**; `ConnectorAdapter.fetch` had
**zero callers**. Together that meant a connector could only be read one named
record at a time (`get_account`, `search_issues`) - there was no way to walk a
resource, and therefore nothing that needed a position.

Writing the caller exposed a defect invisible to tests while nothing called it:

```python
jql = cursor or f"project = {self._project} ORDER BY updated ASC"
```

A supplied `cursor` **replaced the JQL**. Page 1 ran the default query; page 2
sent page 1's opaque `nextPageToken` as a *query-language expression*. Jira
answers that with 200 and an empty result set, so it would have read as "no
more records" rather than an error: pagination could never work, silently.

Now the query comes from configuration (`jql`, default `ORDER BY updated ASC`
- a resumable position needs a stable page boundary) and the cursor travels as
`nextPageToken`. `http_request` gained `params`, because a GET with a JSON
body has no defined semantics and proxies drop it.

`integrations/sync_service.py` (`load_cursor` / `advance_cursor` /
`reset_cursor` / `sync_once`) + `POST /v1/connectors/{id}/sync`.

**The cursor is stored verbatim and never parsed.** Its meaning belongs to the
provider; the moment the platform interprets it, a provider-side change
becomes data loss here. `watermark` answers "how stale is this position?"
without understanding the token.

**The position advances only on success** - a failed page that moved the
cursor would skip that page forever while the sync kept reporting success.

`reset` is not a convenience: a cursor is only valid for the query that
produced it, so after a `jql` change the old token addresses a different result
set and resuming from it skips rows without any error.

## Webhooks: the third RLS bootstrap, plus a prefix exemption

Last uncovered Phase 3 epic ("Webhook verification and replay protection").
Only Chatwoot had a signed inbound endpoint, so no other provider could notify
the platform at all.

Migration `0026` adds `connectors.webhook_secret_ref` **and**
`resolve_connector_for_webhook(uuid)`. Two things, because the second is
unusable without the first:

- The inbound signing secret is a **different** secret from `credential_ref`
  (outbound auth). They rotate independently, so overloading one column means
  rotating either breaks the other.
- The bootstrap: a webhook has no bearer token, so the tenant must come from
  the connector id - but `connectors` is FORCE-RLS'd on the binding being
  discovered. Same shape as 0015/0016/0018/0019; **fifth instance**, so this is
  the standing pattern. The function returns tenant/provider/inbound-secret-ref/
  status and deliberately **not** `configuration` or `credential_ref`: a
  webhook verifier has no business reading the outbound credential.

Endpoint `POST /v1/webhooks/connectors/{connector_id}` reuses
`support_bridge.webhook_security.verify_webhook` rather than implementing a
second HMAC path. Refusals: unknown connector 404 (no detail - distinguishing
"no such connector" from "bad signature" would let a caller enumerate ids),
`disabled` 409, no resolvable secret 503, bad signature 401, missing delivery
id 400, malformed payload 400.

**Middleware change worth noting**: `EXEMPT_PATHS` was exact-match only, and a
webhook path ends in a connector id. Added `EXEMPT_PREFIXES = ("/v1/webhooks/",)`
plus `is_exempt(path)`. The prefix is a deliberate grant, so the module says so
rather than leaving the next person to inherit it silently.

`test_the_webhook_is_reachable_without_a_bearer_token` drives the **real app**
(`TestClient(platform_core.main.app)`), not a freshly-mounted router: a router
-only test passes even when the path is missing from the exempt list, which
would make the endpoint unreachable in production.

**What an accepted event does, stated rather than implied**: it is persisted in
`inbox_events` and the worker marks it processed without acting on it, because
the existing consumer only runs the answer path for `message_created`. Deciding
what a provider event should change (which Case does a Jira transition belong
to?) needs a link the domain model does not have. Persisting first is the
documented rule and it makes the decision reversible.

# Session — Phase 4: rate limiting, a restore drill, and the first flag consumer

## Rate limiting: a token bucket in Redis, and why not a fixed window

`platform_core/rate_limit.py`. A fixed window permits twice the intended rate
across a boundary (1000 at 12:00:59 plus 1000 at 12:01:00 are both accepted),
and it cannot compute a meaningful `Retry-After`. A token bucket refills
continuously and can say exactly how long until one token exists.

Three decisions worth keeping:

- **Redis holds the counters, and that is not the durable queue.** ADR 0002
  said `APP_REDIS_URL` was read by no code *on purpose*, because durable work
  lives in Postgres tables. A rate-limit bucket is the opposite kind of state:
  ephemeral, loss-tolerant, worthless after a restart. The ADR has been updated
  with that distinction - the rule is not "Redis is banned" but "Redis never
  holds state whose loss changes the outcome of a request".
- **Redis unreachable degrades to per-process buckets, it does not fail open.**
  Failing open removes all protection exactly when a shared dependency is
  degraded, which is when abuse is most likely to go unnoticed. The fallback is
  weaker (N replicas allow N× the rate) and the module says so.
- **`/healthz` and `/metrics` are never limited.** Limiting `/metrics` blinds
  monitoring during an incident; a 429 on `/healthz` makes an orchestrator kill
  a healthy container.

Middleware order, which is load-bearing and now commented in `main.py`:
`HttpMetrics -> TenantContext -> RateLimit -> routing`. RateLimit must be
*inside* TenantContext because a tenant-keyed bucket is what stops one noisy
tenant consuming another's budget, and it cannot key on an unresolved tenant.

Keys are separate scopes per audience (`api` / `webhook`) because provider
deliveries arrive in bursts and must not be throttled into data loss. Webhook
traffic keys by client address, which behind a proxy means every caller shares
one bucket - stated in the docstring rather than hidden, and honoured
`X-Forwarded-For` would let any caller pick its own bucket, which is worse.

## Backup/restore drill: `scripts/backup_restore_drill.py`

`docs/deployment-and-operations.md` promised quarterly drills; there was no
script, so the promise was untestable. The drill dumps, restores into a scratch
database it creates and drops, and asserts each property.

**First run reported seven confident failures that were a false alarm**, and
fixing that was the most valuable part:

> the regression suite was mid-flight, and `test_dead_letters`' cleanup deleted
> its own tenant *during* the dump. The drill compared a restored copy against
> a source that had moved, and reported "missing tenant" - i.e. data loss.

A drill that reports a concurrent fixture as data loss teaches people to ignore
it. It now snapshots the source **before and after** the dump and exits with
code **2** ("source was not quiescent") instead of reporting failure.

Its checks, and why each is the right assertion:

| Check | Why |
|---|---|
| row count, every table | a silently dropped table is invisible in "did it finish" |
| per-tenant distribution, 14 tables | totals can match while rows moved *between* tenants |
| audit count **and** min/max timestamp | losing only the newest events still leaves a plausible minimum |
| outbox status distribution | `sent` vs `queued` decides whether the relay re-sends |
| resume-guard constraints present | `uq_inbox_delivery` etc. are what stop a resumed job duplicating a side effect |
| no dangling `external_resource_refs` | reported **separately** from the restore, so it is clear whether to fix the backup or the database |

It also found a real one: one dangling `external_resource_refs` row pointing at
a deleted tenant. Note that **tenant-owned tables have no FK on `tenant_id`**
(the platform enforces isolation with RLS, not constraints), so orphans are
structurally possible - worth knowing.

RPO is deliberately *not* measured: a logical dump contains everything
committed before it started, so its RPO is 0 by construction and reporting that
as a measurement would be theatre. The drill measures RTO and says so.

## The first consumer of a feature flag

`flag_service.evaluate` had **zero callers** outside its own module, so flags
could be defined, audited and previewed while gating nothing - a canary was not
executable. Wiring the reranker closed that.

The reranker was the right thing to gate first, and finding it was the same
audit again: `Reranker` existed, was tested, and was reachable from exactly one
place (the retrieval diagnostics endpoint), so **the production answer path
never reranked**. `wiring.py` even carried the comment "Reranking is likewise
optional" above code that built no reranker.

- Applied **after** fusion and after the ACL pre-filter, which is the only safe
  order: reranking reorders what survived authorization, it never decides what
  is visible.
- Default **False**: an undefined flag is never a silent opt-in to a change
  whose blast radius is every customer-visible answer.
- Degradation is the reranker's own contract and is surfaced
  (`retrieval_degraded_total`), not swallowed.

**The rollout scope is narrower than it looks, and that is a real finding.**
Flags are tenant-owned and RLS-scoped, and the gate evaluates inside the
running tenant's session, so the flag a run sees is that tenant's own.
`target_tenant` refuses self-targeting by design, leaving the kill switch and
the rollout percentage. So **a central canary across tenants is not expressible
today**: a tenant can roll the reranker out to itself, the platform cannot do
it on their behalf because under RLS the platform's flag is invisible in the
tenant's session. Making it work needs a platform-owned flag read through a
narrow SECURITY DEFINER resolver - the same pattern as the tenant bootstrap -
which deserves its own decision rather than being smuggled in.

# Session — Phase 5: custom domains, and two bugs the new tests caught

`0022` stored branding and deferred Host -> tenant routing, on the grounds that
storing a domain with nothing reading it would be dead configuration. This is
the routing half: migration `0027` (`tenant_domains` + `resolve_domain_tenant`,
the **sixth** RLS bootstrap), `identity/domains.py`, `identity/domain_router.py`.

## The security decisions, because Host is caller-controlled

- **Host never selects the tenant for an authenticated request.** That would be
  "tenant id from the request", which every layer here exists to prevent. What
  Host is allowed to do is narrower: pick which tenant's *public branding* to
  render. `resolve_tenant_for_host` is called from exactly one place, the
  public endpoint, and no API route takes a tenant from it.
- **Unverified domains do not resolve.** Anyone can send any Host header, so
  serving an unverified claim would let a tenant publish their branding on a
  domain they do not own. `resolve_domain_tenant` filters
  `verified_at IS NOT NULL`, and the API cannot mark a claim verified by
  itself.
- **Domain uniqueness is global, not per tenant.** Two tenants owning one host
  would make resolution depend on row order. `UNIQUE (domain)` makes it
  unrepresentable.
- `CHECK (domain = lower(domain))` is structural: normalising only in the
  application would let a raw insert create a second row for the same host.
- **Verification is an operator attestation, not a DNS check.** Reading a TXT
  record needs a resolver dependency and its own failure-mode decisions. The
  docstring says so rather than letting a `verified_at` column imply an
  automated check that never ran.

## Bug 1: the migration created the table and forgot the grant

`permission denied for table tenant_domains`, on the *first request*. Every
other tenant-owned table migration ends with
`GRANT SELECT, INSERT, UPDATE, DELETE ... TO platform_app`; `0027` did not.

The failure shape is nasty: the migration applies cleanly, RLS is configured,
unit tests pass, and only a real request fails - and only on a *fresh* database,
because an established one may hold the privilege out of band. **Exactly the
`users` grant added in migration 0021.** So this is the second occurrence, which
is why `test_schema_privileges.py` now exists and checks all 34 tables.

That test also pins the mirror image, which is just as important: `audit_events`
has SELECT + INSERT and **no** UPDATE/DELETE. Append-only is a security
property, and the way it would break is a migration copying the usual
four-privilege grant. The exception is asserted, not tolerated.

## Bug 2: RLS defeats an application-level uniqueness check

`claim_domain` checked for an existing row and got `None` for another tenant's
domain - because RLS hides it - then inserted and hit the unique constraint.
That surfaced as a **500**, not a 409:

```
PendingRollbackError: This Session's transaction has been rolled back due to a
previous exception during flush. Original exception was UniqueViolation
```

The constraint is the correct authority (uniqueness is a database property, and
two concurrent claims race past any application check); the bug was not turning
its violation into a clean error. `begin_nested()` did **not** help - the
session still came out unusable - so the fix is a plain flush, `await
session.rollback()` on `IntegrityError`, then a `DomainError`. Safe here
because the claim is the first write in the request and the audit event comes
after.

Useful corollary: the RLS-scoped pre-check *is* still worth having, because it
is the only way to tell "you already claimed this" from "someone else did"
without a second cross-tenant function.

## Bug 3: a fixture that could not set the value it asserted on

The tenant seed used `ON CONFLICT (slug) DO NOTHING`, so a tenant left by an
earlier run kept its old branding and the assertion compared against a value
the fixture never wrote. Loaded as an endpoint bug; was a fixture bug. Now
`DO UPDATE SET ...`.
