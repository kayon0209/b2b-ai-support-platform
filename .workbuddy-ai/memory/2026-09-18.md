## The design decision worth recording

`ConnectorAdapter.health_check()` in the pilot adapters calls
`GET {base}/health` **with no Authorization header** (`crm.py:98`). So:

> a successful probe is **not** evidence that the credential works.

Two consequences, both now encoded in `integrations/health.py`:

1. **A probe may never clear `NEEDS_REAUTH`.** If reachability could lift it,
   an expired credential would be silently re-armed, and the next thing the
   platform does with an `active` connector is execute a **write** through it.
2. `NEEDS_REAUTH` is only cleared by an explicit operator action that also
   demonstrates the credential now **resolves** (`can_clear_reauth` requires
   both reachable *and* `credential_is_present`). The second condition catches
   "operator repointed the reference at a variable they forgot to set" - the
   failure that would otherwise leave the API reporting `active` for a
   connector that still cannot authenticate.

Also: `{"api_token": ""}` counts as **absent**. It produces
`Authorization: Bearer ` (empty), which is not a credential and would make a
connector look configured while every call 401s.

## What landed

- `integrations/health.py` - pure transitions (`status_after_probe`,
  `status_after_auth_failure`, `can_clear_reauth`) plus the async recorders.
  **Pure by design**: the rule that decides whether a connector may execute
  writes is then verifiable without Postgres.
- `tool_gateway/registry.AuthReportingExecutor` - adapters report a rejected
  credential by *returning* `CONNECTOR_AUTH_EXPIRED` in a dict, not by
  raising, so nothing in the tool path observed it. The wrapper is applied at
  build time (it needs the `Connector` row) and delegates
  `verify_postcondition` unchanged.
- `integrations/router.py` - `GET /v1/connectors`,
  `POST .../health-check`, `POST .../reactivate`, `PUT .../credential-ref`.
- `EventType.CONNECTOR_NEEDS_REAUTH` + payload schema (emitted only on the
  *transition* into NEEDS_REAUTH, so a repeatedly-failing connector notifies
  once).
- `Action.CONNECTOR_READ` / `CONNECTOR_ADMIN`: intentionally separate from the
  tool vocabulary. `support_admin` reads health (their tools broke);
  rotating a credential is `tenant_owner` only.

## Test seam choice

`probe_connector` is monkeypatched in the reactivation *success* test only.
Standing up an HTTP server to answer `/health` would test `httpx`, not the
gate. The unreachable paths use `http://127.0.0.1:9` (discard port) so a

# Session — dead letters, and a P1 ingestion regression the e2e caught

Docker Desktop came up. Started `ai-postgres`/`ai-redis` via compose; `minio`

## The regression: every API-uploaded document failed to ingest

Running the e2e (not the suite) surfaced it:

```
IngestionError: unsupported content type for parsing: "text/markdown"
```

Note the **quotes around the value**. `parse_document` matches exact content
types, so `"text/markdown"` - with quotes - matches nothing.

Root cause, proved against the live database before touching anything:

```sql
'{"content_type": "text/markdown"}'::jsonb ->  'content_type'  ::text  => "text/markdown"
'{"content_type": "text/markdown"}'::jsonb ->> 'content_type'         => text/markdown
```

`->` returns a **JSON** value, and casting a JSON *string* to `text` keeps its
surrounding double quotes. Migration `0024_claim_content_type` used `->`;
migration `0025_fix_claim_content_type` uses `->>`. The function body was
verified by reading `pg_proc.prosrc` after the upgrade.

**Why the suite stayed green.** `_make_version` in `test_ingestion_worker.py`
seeded versions with **no** `content_type` in metadata. `->` on a missing key
yields SQL NULL from either operator, the worker falls back to markdown, and
everything passed. Only the real upload path - the one the API writes
`metadata.content_type` for - failed. That is the shape of coverage gap worth
remembering: the fixture did not reproduce the production row.

Fixed by:
- migration `0025` (`->>`), `EXPECTED_MIGRATIONS` 24 -> 25;
- `_make_version(..., content_type=...)` so the fixture can seed the way the
  API does;
- `test_the_claim_returns_an_unquoted_content_type` - asserts the **exact**
  string, because `in` would have accepted the buggy value;
- `test_an_api_style_upload_with_a_content_type_ingests_to_ready` - the e2e
  path pinned in the suite, so this cannot regress back to e2e-only detection.

Related trap hit while writing the fixture: `document_versions.metadata` is
NOT NULL with a `'{}'::jsonb` default, and passing an explicit NULL in the
INSERT **overrides** that default -> `NotNullViolation`. Same family as the ORM
`server_default` note already in `MEMORY.md`.

## Dead letters: from "model with no producer" to visible work

`DeadLetterItem` had a model and a retention sweep and **no producer**, so a
connector operation that exhausted its bounded retries left nothing behind but
a failed `ToolExecution` row nothing listed.

- `integrations/dead_letter.py`: `operation_digest` = `"{tool}:{sha256(params)[:32]}"`.
  The **payload is never stored** - it can be customer-derived and this row is
  read by an operational endpoint and copied into backups. The digest still
  answers "is this the same operation failing 40 times?".
  `sort_keys=True` is load-bearing: without it a different insertion order
  produces a different digest and that grouping silently stops working.
- `AuthReportingExecutor` renamed to **`ConnectorOutcomeExecutor`** - after it
  also produced dead letters the old name was actively misleading, which is
  the exact defect class this repo audits.
- Classification: auth rejections are **excluded** (they have NEEDS_REAUTH,
  and duplicating them would fill the queue with rows whose fix is "rotate the
  credential"), everything else - including `ambiguous` transport failures -
  is recorded. Ambiguity outranks the error code; the row says
  `AMBIGUOUS_OUTCOME` because the operator's first question is "did it land?",
  which the error code cannot answer.
- **No replay endpoint, deliberately.** The payload is not here by design, and
  an ambiguous row cannot be safely retried until someone establishes whether
  the first attempt landed - an operator decision, not a loop.
- `GET /v1/dead-letters`, `POST /v1/dead-letters/{id}/resolve` (idempotent:
  a second resolve writes no second audit event).

# Session — resumable connector sync, then connector webhooks

## Sync: two "never consumed" defects, and the bug the caller exposed

`SyncCursor` was referenced by **nothing**; `ConnectorAdapter.fetch` had
**zero callers**. Together that meant a connector could only be read one named
record at a time (`get_account`, `search_issues`) - there was no way to walk a
resource, and therefore nothing that needed a position.

Writing the caller exposed a defect invisible to tests while nothing called it:

```python
jql = cursor or f"project = {self._project} ORDER BY updated ASC"
```

A supplied `cursor` **replaced the JQL**. Page 1 ran the default query; page 2
sent page 1's opaque `nextPageToken` as a *query-language expression*. Jira
answers that with 200 and an empty result set, so it would have read as "no
more records" rather than an error: pagination could never work, silently.

Now the query comes from configuration (`jql`, default `ORDER BY updated ASC`
- a resumable position needs a stable page boundary) and the cursor travels as
`nextPageToken`. `http_request` gained `params`, because a GET with a JSON
body has no defined semantics and proxies drop it.

`integrations/sync_service.py` (`load_cursor` / `advance_cursor` /
`reset_cursor` / `sync_once`) + `POST /v1/connectors/{id}/sync`.

**The cursor is stored verbatim and never parsed.** Its meaning belongs to the
provider; the moment the platform interprets it, a provider-side change
becomes data loss here. `watermark` answers "how stale is this position?"
without understanding the token.

**The position advances only on success** - a failed page that moved the
cursor would skip that page forever while the sync kept reporting success.

`reset` is not a convenience: a cursor is only valid for the query that
produced it, so after a `jql` change the old token addresses a different result
set and resuming from it skips rows without any error.

## Webhooks: the third RLS bootstrap, plus a prefix exemption

Last uncovered Phase 3 epic ("Webhook verification and replay protection").
Only Chatwoot had a signed inbound endpoint, so no other provider could notify
the platform at all.

Migration `0026` adds `connectors.webhook_secret_ref` **and**
`resolve_connector_for_webhook(uuid)`. Two things, because the second is
unusable without the first:

- The inbound signing secret is a **different** secret from `credential_ref`
  (outbound auth). They rotate independently, so overloading one column means
  rotating either breaks the other.
- The bootstrap: a webhook has no bearer token, so the tenant must come from
  the connector id - but `connectors` is FORCE-RLS'd on the binding being
  discovered. Same shape as 0015/0016/0018/0019; **fifth instance**, so this is
  the standing pattern. The function returns tenant/provider/inbound-secret-ref/
  status and deliberately **not** `configuration` or `credential_ref`: a
  webhook verifier has no business reading the outbound credential.

Endpoint `POST /v1/webhooks/connectors/{connector_id}` reuses
`support_bridge.webhook_security.verify_webhook` rather than implementing a
second HMAC path. Refusals: unknown connector 404 (no detail - distinguishing
"no such connector" from "bad signature" would let a caller enumerate ids),
`disabled` 409, no resolvable secret 503, bad signature 401, missing delivery
id 400, malformed payload 400.

**Middleware change worth noting**: `EXEMPT_PATHS` was exact-match only, and a
webhook path ends in a connector id. Added `EXEMPT_PREFIXES = ("/v1/webhooks/",)`
plus `is_exempt(path)`. The prefix is a deliberate grant, so the module says so
rather than leaving the next person to inherit it silently.

`test_the_webhook_is_reachable_without_a_bearer_token` drives the **real app**
(`TestClient(platform_core.main.app)`), not a freshly-mounted router: a router
-only test passes even when the path is missing from the exempt list, which
would make the endpoint unreachable in production.

**What an accepted event does, stated rather than implied**: it is persisted in
`inbox_events` and the worker marks it processed without acting on it, because
the existing consumer only runs the answer path for `message_created`. Deciding
what a provider event should change (which Case does a Jira transition belong
to?) needs a link the domain model does not have. Persisting first is the
documented rule and it makes the decision reversible.

# Session — Phase 4: rate limiting, a restore drill, and the first flag consumer

## Rate limiting: a token bucket in Redis, and why not a fixed window

`platform_core/rate_limit.py`. A fixed window permits twice the intended rate
across a boundary (1000 at 12:00:59 plus 1000 at 12:01:00 are both accepted),
and it cannot compute a meaningful `Retry-After`. A token bucket refills
continuously and can say exactly how long until one token exists.

Three decisions worth keeping:

- **Redis holds the counters, and that is not the durable queue.** ADR 0002
  said `APP_REDIS_URL` was read by no code *on purpose*, because durable work
  lives in Postgres tables. A rate-limit bucket is the opposite kind of state:
  ephemeral, loss-tolerant, worthless after a restart. The ADR has been updated
  with that distinction - the rule is not "Redis is banned" but "Redis never
  holds state whose loss changes the outcome of a request".
- **Redis unreachable degrades to per-process buckets, it does not fail open.**
  Failing open removes all protection exactly when a shared dependency is
  degraded, which is when abuse is most likely to go unnoticed. The fallback is
  weaker (N replicas allow N× the rate) and the module says so.
- **`/healthz` and `/metrics` are never limited.** Limiting `/metrics` blinds
  monitoring during an incident; a 429 on `/healthz` makes an orchestrator kill
  a healthy container.

Middleware order, which is load-bearing and now commented in `main.py`:
`HttpMetrics -> TenantContext -> RateLimit -> routing`. RateLimit must be
*inside* TenantContext because a tenant-keyed bucket is what stops one noisy
tenant consuming another's budget, and it cannot key on an unresolved tenant.

Keys are separate scopes per audience (`api` / `webhook`) because provider
deliveries arrive in bursts and must not be throttled into data loss. Webhook
traffic keys by client address, which behind a proxy means every caller shares
one bucket - stated in the docstring rather than hidden, and honoured
`X-Forwarded-For` would let any caller pick its own bucket, which is worse.

## Backup/restore drill: `scripts/backup_restore_drill.py`

`docs/deployment-and-operations.md` promised quarterly drills; there was no
script, so the promise was untestable. The drill dumps, restores into a scratch
database it creates and drops, and asserts each property.

**First run reported seven confident failures that were a false alarm**, and
fixing that was the most valuable part:

> the regression suite was mid-flight, and `test_dead_letters`' cleanup deleted
> its own tenant *during* the dump. The drill compared a restored copy against
> a source that had moved, and reported "missing tenant" - i.e. data loss.

A drill that reports a concurrent fixture as data loss teaches people to ignore
it. It now snapshots the source **before and after** the dump and exits with
code **2** ("source was not quiescent") instead of reporting failure.

Its checks, and why each is the right assertion:

| Check | Why |
|---|---|
| row count, every table | a silently dropped table is invisible in "did it finish" |
| per-tenant distribution, 14 tables | totals can match while rows moved *between* tenants |
| audit count **and** min/max timestamp | losing only the newest events still leaves a plausible minimum |
| outbox status distribution | `sent` vs `queued` decides whether the relay re-sends |
| resume-guard constraints present | `uq_inbox_delivery` etc. are what stop a resumed job duplicating a side effect |
| no dangling `external_resource_refs` | reported **separately** from the restore, so it is clear whether to fix the backup or the database |

It also found a real one: one dangling `external_resource_refs` row pointing at
a deleted tenant. Note that **tenant-owned tables have no FK on `tenant_id`**
(the platform enforces isolation with RLS, not constraints), so orphans are
structurally possible - worth knowing.

RPO is deliberately *not* measured: a logical dump contains everything
committed before it started, so its RPO is 0 by construction and reporting that
as a measurement would be theatre. The drill measures RTO and says so.

## The first consumer of a feature flag

`flag_service.evaluate` had **zero callers** outside its own module, so flags
could be defined, audited and previewed while gating nothing - a canary was not
executable. Wiring the reranker closed that.

The reranker was the right thing to gate first, and finding it was the same
audit again: `Reranker` existed, was tested, and was reachable from exactly one
place (the retrieval diagnostics endpoint), so **the production answer path
never reranked**. `wiring.py` even carried the comment "Reranking is likewise
optional" above code that built no reranker.

- Applied **after** fusion and after the ACL pre-filter, which is the only safe
  order: reranking reorders what survived authorization, it never decides what
  is visible.
- Default **False**: an undefined flag is never a silent opt-in to a change
  whose blast radius is every customer-visible answer.
- Degradation is the reranker's own contract and is surfaced
  (`retrieval_degraded_total`), not swallowed.

**The rollout scope is narrower than it looks, and that is a real finding.**
Flags are tenant-owned and RLS-scoped, and the gate evaluates inside the
running tenant's session, so the flag a run sees is that tenant's own.
`target_tenant` refuses self-targeting by design, leaving the kill switch and
the rollout percentage. So **a central canary across tenants is not expressible
today**: a tenant can roll the reranker out to itself, the platform cannot do
it on their behalf because under RLS the platform's flag is invisible in the
tenant's session. Making it work needs a platform-owned flag read through a
narrow SECURITY DEFINER resolver - the same pattern as the tenant bootstrap -
which deserves its own decision rather than being smuggled in.

# Session — Phase 5: custom domains, and two bugs the new tests caught

`0022` stored branding and deferred Host -> tenant routing, on the grounds that
storing a domain with nothing reading it would be dead configuration. This is
the routing half: migration `0027` (`tenant_domains` + `resolve_domain_tenant`,
the **sixth** RLS bootstrap), `identity/domains.py`, `identity/domain_router.py`.

## The security decisions, because Host is caller-controlled

- **Host never selects the tenant for an authenticated request.** That would be
  "tenant id from the request", which every layer here exists to prevent. What
  Host is allowed to do is narrower: pick which tenant's *public branding* to
  render. `resolve_tenant_for_host` is called from exactly one place, the
  public endpoint, and no API route takes a tenant from it.
- **Unverified domains do not resolve.** Anyone can send any Host header, so
  serving an unverified claim would let a tenant publish their branding on a
  domain they do not own. `resolve_domain_tenant` filters
  `verified_at IS NOT NULL`, and the API cannot mark a claim verified by
  itself.
- **Domain uniqueness is global, not per tenant.** Two tenants owning one host
  would make resolution depend on row order. `UNIQUE (domain)` makes it
  unrepresentable.
- `CHECK (domain = lower(domain))` is structural: normalising only in the
  application would let a raw insert create a second row for the same host.
- **Verification is an operator attestation, not a DNS check.** Reading a TXT
  record needs a resolver dependency and its own failure-mode decisions. The
  docstring says so rather than letting a `verified_at` column imply an
  automated check that never ran.

## Bug 1: the migration created the table and forgot the grant

`permission denied for table tenant_domains`, on the *first request*. Every
other tenant-owned table migration ends with
`GRANT SELECT, INSERT, UPDATE, DELETE ... TO platform_app`; `0027` did not.

The failure shape is nasty: the migration applies cleanly, RLS is configured,
unit tests pass, and only a real request fails - and only on a *fresh* database,
because an established one may hold the privilege out of band. **Exactly the
`users` grant added in migration 0021.** So this is the second occurrence, which
is why `test_schema_privileges.py` now exists and checks all 34 tables.

That test also pins the mirror image, which is just as important: `audit_events`
has SELECT + INSERT and **no** UPDATE/DELETE. Append-only is a security
property, and the way it would break is a migration copying the usual
four-privilege grant. The exception is asserted, not tolerated.

## Bug 2: RLS defeats an application-level uniqueness check

`claim_domain` checked for an existing row and got `None` for another tenant's
domain - because RLS hides it - then inserted and hit the unique constraint.
That surfaced as a **500**, not a 409:

```
PendingRollbackError: This Session's transaction has been rolled back due to a
previous exception during flush. Original exception was UniqueViolation
```

The constraint is the correct authority (uniqueness is a database property, and
two concurrent claims race past any application check); the bug was not turning
its violation into a clean error. `begin_nested()` did **not** help - the
session still came out unusable - so the fix is a plain flush, `await
session.rollback()` on `IntegrityError`, then a `DomainError`. Safe here
because the claim is the first write in the request and the audit event comes
after.

Useful corollary: the RLS-scoped pre-check *is* still worth having, because it
is the only way to tell "you already claimed this" from "someone else did"
without a second cross-tenant function.

## Bug 3: a fixture that could not set the value it asserted on

The tenant seed used `ON CONFLICT (slug) DO NOTHING`, so a tenant left by an
earlier run kept its old branding and the assertion compared against a value
the fixture never wrote. Loaded as an endpoint bug; was a fixture bug. Now
`DO UPDATE SET ...`.

### The defect family, again

`cases.enterprise_account_id` was a bare `uuid` column: **no FK, no target
table, and no writer** - `CaseCreateIn` did not accept the field and
`create_case` never set it. So "which account is this Case for" was not merely
unanswered, it was unanswerable, and any uuid at all could sit there silently.
This is the same shape as `DeadLetterItem`, `health_check`, `NEEDS_REAUTH` and
`SyncCursor`: a capability that exists and is never consumed. The audit method
that keeps finding them is still "grep for the writers/callers", and it is
cheaper than reading the docs.

### Decisions worth keeping

- **Composed foreign keys**, `(parent_id, tenant_id) -> (id, tenant_id)`, and
  the same for `cases -> accounts` and `memberships -> departments`. A
  single-column FK would *accept* another tenant's row as a parent, and RLS
  would hide it - so the child reads as a root, which is indistinguishable from
  a deliberate root. Including `tenant_id` in the key makes that unrepresentable.
- **The hierarchy is acyclic**, `CHECK (parent_id <> id)` for one node plus a
  trigger walk for longer cycles. Neither alone is enough: A -> B -> A satisfies
  both the CHECK and the FK.
- **`tier` is a closed set** on both boundaries (API validation + CHECK), because
  an SLA clock is derived from it and a typo must not fall through to the default.
- **An inactive contract does not keep the tier window.** `pending` /
  `suspended` / `churned` resolve to `standard`: a 15-minute first-response
  target for a customer who stopped paying fires escalations nobody agreed to.
- **The tier is snapshotted on the Case** (`cases.sla_tier`). The deadline is
  recomputed on a priority change, and re-reading the account then would let a
  mid-Case contract change move a clock that is already running. Verified by a
  test that changes the account between open and `change_priority`.

### `FOUND` is false after `EXECUTE ... INTO` in PL/pgSQL

The acyclicity trigger's first version ended its walk with

    EXECUTE format(...) INTO cursor_id USING cursor_id;
    IF NOT FOUND THEN cursor_id := NULL; END IF;

which reads as the obvious way to stop at a missing row. Measured against this
PostgreSQL with an AFTER trigger that recorded `FOUND` after an `EXECUTE ...
INTO` whose SELECT returned a non-null row: **`FOUND` was `false`**. The guard
therefore discarded the parent it had just read and the walk stopped one hop
up, so a **two-node cycle was accepted**. The single-node case still failed, but
on the CHECK constraint, not on the trigger - which is why nothing looked wrong.

Terminate on the **value**, not on `FOUND`: `WHILE cursor_id IS NOT NULL` plus
checking the fetched parent. Null is the correct stop for a root row and for a
missing row alike, and the composite FK rules out the latter.

The lesson generalises: *a guard that cannot be observed failing is not
evidence*. The trigger looked installed, `pg_trigger` showed it enabled, and it
did nothing for any hierarchy deeper than one hop.

### Two more measured findings

- **A failed flush poisons the session.** `_flush` must `await session.rollback()`
  before raising, or the router's later `commit()` raises
  `PendingRollbackError` and a clean 409 becomes a 500. `begin_nested()` does
  not help - same finding as the domain-claim path.
- **`(metadata -> 'k')::text` keeps the JSON quotes** - already fixed in 0025,
  re-confirmed here when reasoning about jsonb projections.

### Reusable lessons

- **A guard that cannot be observed failing is not evidence.** The acyclicity
  trigger was installed, enabled, and inert.
- **Terminate a PL/pgSQL walk on the value, not on `FOUND`.**
- **A `raise`/`return` after a failed flush needs `session.rollback()`** or the
  router's later `commit()` turns a clean 409 into a 500 (`begin_nested` does not
  help). Prefer `ON CONFLICT DO NOTHING` over insert-then-catch: a rollback
  discards *the whole transaction*, including earlier rows in the same sweep.
- **A test that passes against a long-lived database is not evidence about the
  migrations.** Only `downgrade base && upgrade head` shows what they declare.
- **XML DSig: canonicalisation depends on the inherited namespace context**, so
  moving a signed element between parents invalidates its digest. Sign in place.
- pyyaml/mypy: `signxml` imports come from `signxml.verifier` (packages root

- `pytest` `-k` and per-test cleanup: a per-test fixture must not delete a
  module-scoped seed, or every request in the module is a 404.

### Scope lines drawn deliberately

- SAML login establishes identity and **issues no session** (OIDC tokens come
  from Keycloak; a second credential path is not worth the risk).
- A first SAML login **never provisions a role** - an IdP attribute is
  controlled by the IdP's administrator.
- A SCIM **Group maps to a Department, never to a `MembershipRole`**.
- `infra/kubernetes/` has **never been applied to a cluster**; the README says so
  and names the 27 structural assertions as the substitute for server-side
  validation.

# Session — the eval producer, and the defect it found in the conflict rule

## `scripts/run_eval.py` — and why it is not the harness

The obvious shortcut was to serialize the deterministic harness's report. That
would have fed the gate an **oracle's** numbers as measured quality - the same
theatre as quoting an RPO from a logical dump. So the script does the opposite:
seeds the dataset corpus into a throwaway tenant, ingests it through the real
worker with real embeddings, retrieves through `hybrid_search` with the real ACL
and status filters, and generates with the live model. `active` / `expired` /
`unauthorized` are enforced by the machinery that enforces them in production
(status column; an ACL grant the cases do not hold), not simulated.

## The defect it immediately found

First full run: **16/23**, with five cases abstaining on `CONFLICTING_SOURCES`.
Measured, not guessed:

```
policy-monthly-refundable  "Are monthly plans refundable?"
  #1 Refund Policy       score=0.032787   <- the correct source
  #2 Standard SLA        score=0.016129   <- irrelevant, overlap 0.333
  gap=0.016658   margin=0.05   compete=True
```

A source with **twice** the score of the runner-up was called a tie.

Root cause, and it is sharper than "wrong constant": `hybrid_search` fuses with
RRF, so a score is `sum(1 / (60 + rank))`. The top two are typically 1/61 and
1/62 - a gap of **0.000264**, and the largest possible gap is ~0.016. The
absolute margin of 0.05 can therefore *never* be exceeded. The guard was
calibrated against the harness, whose scores are term-overlap fractions spanning
0..1, and against that scale it works. Against the real scale it was **inert**,
so "comparable ranking" always held and conflict detection collapsed into "do
both passages contain numbers?".

Same family as the acyclicity trigger: **a guard that cannot be observed
failing is not evidence.** No unit test covered `_sources_compete` at the
production score scale; every existing one scored chunks 0.2-0.9.

Three corrections, each measured:

| # | Defect | Fix |
|---|---|---|
| 1 | absolute margin vs RRF scale - guard inert | relative margin (runner-up within 20% of the leader) |
| 2 | `[:2]` took the top two **on-topic**, skipping higher-ranked irrelevant ones - paired rank 1 with rank 5 (Refund Policy vs Onboarding Guide) | only the top two **by score** can compete |
| 3 | the relevance floor (0.12) is a "related at all" bar, not a "competing answer" bar - a doc matching 1 of 7 query terms competed | runner-up must be comparably on-topic to the leader |

Plus one design gap: a question that **names** one source's scope
("...for **enterprise** customers") had already chosen its source, and treating
the other as a competing reading abstained on a well-specified question. The
rule now compares against each source's *distinguishing* terms - a plain
intersection fails there, because both SLA documents share the heading "Service
credits" and so both match the question.

Result: **16/23 → 21/23**, spurious conflicts 5 → 0.

# Session — billing corrections, and a FORCE-RLS read that could never see anything

## `POST /v1/tenant/billing/adjustments`

The ledger is append-only (the app role holds no UPDATE or DELETE), so a
correction is a new row. Without an endpoint the only way to fix a billing
error was a database console.

`record_adjustment` deliberately did **not** dedupe - it keyed on
`(run_id, timestamp)` so "an adjustment is a deliberate act, and a repeated
call is a new correction". That is fine for a Python caller and wrong for an
HTTP one: the repo requires an `Idempotency-Key` on every write, and a retry
that isn't deduped would credit the account twice. So it now accepts an
optional `idempotency_key`, keys on `(tenant, key)`, and uses
`ON CONFLICT DO NOTHING`; the endpoint always passes one. A redelivery returns
`{"duplicate": true}` and writes **no** second audit event - an audit trail
that records a retry reports activity that never happened.

New `Action.BILLING_ADJUST`, granted to `tenant_owner` only (the enum's
`frozenset(Action)` does that by construction). Reading the ledger and
changing it are different capabilities: `auditor` can read, cannot adjust.

## The bug this exposed: `set_config` does not survive `COMMIT`

The endpoint's first test run returned `adjustment_entries: 0` - and so did
the directly-inserted usage row beside it. `tenant_session` applied
`set_config('app.tenant_id', ..., true)` **once**, before yielding. The handler
commits (so the row is durable before it is reported), the transaction-scoped
binding dies with the transaction, and the read that follows is unbound. RLS
returns zero rows **with no error**.

`PUT /v1/tenant/quota` had the same shape and had been wrong all along: it
committed the new quota and then read the usage snapshot, so it reported
`runs_used: 0` for any tenant. Its tests only asserted `quota` and `remaining`,
which come from the tenant row and were still correct - which is why nobody
noticed.

Fixed **structurally**, not per call site: `tenant_session` now re-applies the
binding on `after_begin`, so it holds for every transaction a handler opens.
A rule that has to be remembered has already been forgotten twice in this repo.

Proved the guards are real: disabling the listener fails four tests, including
the new `test_the_put_response_reports_real_usage_not_zero`.

## 22 more copies of the same setup, and 5 of the same URL

`prompt_router`, `flag_router`, `gap_router`, `audit/router`,

## The product defect: abstention produced silence

With the loop finally running, the run abstained and **no reply was sent**.

`_finish_abstain`'s docstring reads *"Record abstention, release the lease to
the human queue, and **send the customer-safe notice** (still behind the lease
gate)."* The body built `safe_abstention_text(...)`, put it in the returned

path (step 9) called `_dispatch`.

The consequence: **the most common failure mode was the one that got no
response.** A customer asking something the knowledge base cannot support heard
nothing at all — not "I could not verify that", not "a human is coming". The
handoff happened internally and the customer waited forever.

Fixed: lease re-check → dispatch the notice → then release the queue. The order
matters and my first attempt had it backwards (`release_to_queue` first, so the
lease gate refused with "owner is queue" — still silence, different log line).
The new test caught that immediately, which is the argument for testing the
transport rather than the outcome object: the outcome carried the right text
the whole time.

**Two existing tests asserted the bug.** `sender.calls == []` appeared in
`test_restricted_request_never_reaches_model_and_hands_off` and
`test_no_evidence_abstains_without_model_call`, with comments explaining that
nothing should be sent. Their real intent — no model spend, handoff released —
still holds and is kept. The transport assertion now checks that exactly one
notice is sent, that it equals `outcome.answer_text`, that its command id is
`run:<id>`, and (for the restricted case) that it does not leak the refused
terms.

Also added: scenario 4 of `test_e2e_acceptance.py`'s docstring,
"insufficient evidence -> abstention with handoff reason", was **listed and
never written**. That is how the defect survived a suite that documents the
exact behaviour it broke.

# Session — verifying the P0 duplicate-delivery criterion, and aligning the webhook secret

## The webhook secret disagreed between two places

`.env` said `e2e-webhook-secret`; the compose `ai-api` service hardcoded
`local-dev-webhook-secret` to match Chatwoot's webhook row. Each path was
internally consistent, but an API run *outside* Docker would verify with the
wrong value and reject every delivery with a 401 - which reads as silence, not
misconfiguration. Compose now reads
`${APP_CHATWOOT_WEBHOOK_SECRET:-local-dev-webhook-secret}`, `.env` and
`.env.example` carry the value Chatwoot actually holds, and `.env.example`
says what it must match. The integration tests inject their own `Settings`, so
none of this touches them.

## `e2e_chatwoot_duplicate_delivery.py`

Phase 1's first acceptance criterion is "Duplicate webhook delivery never
creates duplicate customer replies". It had contract tests with synthetic
payloads; nothing had asked a live Chatwoot whether a second reply appeared.

```
first delivery  -> 202 {"status": "received", ...}
second delivery -> 200 {"status": "duplicate", ...}
inbox events: [('message_created', '90195cdc-...')]   <- exactly 1
outbound replies: 1                                    <- exactly 1
E2E OK
```

Three things had to be got right, and each was a wrong assumption first:

- **202 vs 200.** The router answers a *new* delivery with 202 `received` and a
  redelivery with 200 `duplicate`. My first assertion demanded 200 for both.
  The contract is right: a redelivery must look like success, or Chatwoot
  retries forever.
- **The message must exist in Chatwoot.** `minimize_chatwoot_payload` strips
  `content` on purpose, so the worker resolves the question with
  `fetch_message(message_id)`. A synthetic id yields no question and therefore
  no reply - which is what the first version did, and it looked like the
  platform failing to answer. (I checked whether `resolve_question`'s
  "payload already carries content" branch is dead: it is not, tests construct
  `ClaimedEvent` directly. The docstring is accurate.)
- **Chatwoot must not deliver the message itself.** Posting through Chatwoot's
  API raises its own `message_created` webhook, which is a *different* delivery
  and legitimately produces a second reply. The account webhook is detached for
  the duration and restored in `finally` - verified afterwards: id 2, same URL
  and subscriptions.

# Session — closing `business-write-refund` (the gap I had deferred three times)

I had deferred this on "false-positive risk", which was the right instinct and
the wrong conclusion: the risk is manageable *if* the detector is validated
against the whole dataset before it is wired in, and the infrastructure to do
that now exists.

## What was wrong

The QA path answered an action request from the knowledge corpus. "Refund the
last invoice for this customer." got refund-policy text. The customer asked for
a refund and was told how refunds work, which reads as being ignored.

The case had been *passing*: `_sources_compete` called two unrelated documents
a tie on an absolute margin RRF scores can never exceed, and that spurious
conflict produced the abstention the case wanted. Correcting the margin removed
the accident and made the real gap visible — which is why it was recorded in
`KNOWN_GAPS` rather than relaxed.

## Where the fix belongs

Not `classify_route`. The runner drives `decide_abstention` directly, so
routing never sees this case, and the QA path should refuse an action request
regardless of routing — defence in depth, the same shape as `restricted_query`.

## The detector, and how it was validated

Four forms only:

    <verb> <object>              "Refund the last invoice."
    please|kindly <verb> ...     "Please delete the workspace."
    can|could|would|will you <verb> ...
                                 "Can you refund the last invoice?"
    I|we want|need|would ... to <verb>
                                 "I want to cancel my subscription."

Three corrections came out of validating rather than guessing:

- **A bare write verb is not an instruction.** The first version fired on
  `"refund window"` — a noun phrase someone typed into a search box — and an
  existing test caught it. An imperative needs an object introduced by a
  determiner/possessive/pronoun.
- **"Can you" vs "Can I"** is the whole distinction between asking the agent to
  act and asking whether something is possible. The pronoun decides.
- **The verb must be the *object* of the desire, not merely nearby.**
  "I need to know the refund policy" is a question; only `to <verb>` and
  `<determiner> <verb>` are requests. A first attempt that scanned forward
  fired on it.

Measured against all 23 dataset cases it fires on **exactly one**
(`business-write-refund`) and none of the answerable, adversarial or injection
cases. Ten hand-written positives all fire; ten negatives — including
"How do I cancel my subscription?", "Can I get a refund?", "refund window",
"I need to know the refund policy" — none do.

Known false negative, accepted deliberately: a bare noun phrase with no object
("refund!") is not detected. Firing wrongly hands a legitimate question to a
human, which is the more expensive mistake.

## Result

`business-write-refund` left `KNOWN_GAPS` — the set's own mechanism, which
asserts a gap still fails so a fix produces a visible prompt to update it. Only
`ambiguous-refund-eligibility` remains.

# Session — closing `ambiguous-refund-eligibility`, the last tracked gap

`KNOWN_GAPS` is now **empty**. Both entries left it the same way: the test
`test_tracked_gaps_are_still_failing` failed with "these cases now pass but are
still listed as known gaps", which is the prompt to delete the entry.

## Why the first two attempts failed, and what the third did differently

The gap: the refund window differs by billing period ("Annual plans ... 30
days. Monthly plans ... 14 days."), the platform does not hold which period a
caller is on, and the answer was taken from whichever row ranked first.

Both earlier attempts **pattern-matched the question** with a broad "identity
term" set. `"are"` was in it, so `"Are monthly plans refundable?"` — an
answerable case that must be *answered* — was flagged as identity-dependent.
The log's own note said the real fix was account-identity resolution, not
question matching.

I checked whether that resolution is even expressible. It is not:

- `Membership` has **no link to `EnterpriseAccount`** — a user belongs to a
  tenant with a role, not to a customer account;
- `EnterpriseAccount.tier` is a *contract tier*
  (strategic/enterprise/standard/basic), not a billing period.

So the platform cannot resolve the variant, because the variant is not in the
domain model. That reframes the gap: it is not "we forgot to look up the
account", it is "the attribute the answer depends on does not exist here", and
the correct behaviour for an attribute we do not model is to refuse rather than
pick a row.

## The fix: abstain on variant-conditional evidence

Three narrow conditions, all required:

1. the question asks about the caller's **own** entitlement
   (`am i`, `do i`, `my`, `our`, ...) — not a general policy question;
2. the question does **not** name the variant (`annual`, `monthly`, ...), so it
   cannot be answered from the passage;
3. the top passage states **two or more variants with two or more figures** —
   one figure is a fact, two figures under two variants is a table.

Validated against all 23 dataset cases: it fires on exactly the two
`must_abstain` cases (`ambiguous-refund-eligibility`, `ambiguous-sla-account`)
and on **none** of the answerable ones — including `answerable-refund-window`,
`expired-refund-90-day`, `policy-monthly-refundable`, `adversarial-press-refund`
and `adversarial-role-claim`.

`ABSTAIN_AMBIGUOUS_IDENTITY` had been declared and **never emitted** since it
was added — the same "declared, never used" family as the rest of this log.
This gives it its first emitter, and its own customer-facing text: "That depends
on your contract, and I can't tell which one applies to you." Saying "I couldn't
verify that" would be false — the policy is right there, it just branches.

## What the fix does *not* do, stated plainly

It does not let the platform *answer* these questions. Doing that needs the
caller's billing period, which needs schema (a link from the conversation or
contact to a contract variant). That is a design decision worth its own ADR,
and inventing a third heuristic for it is what failed twice already. Refusing
correctly is the honest half.

So **every dataset case now passes**, but not on every run. The remaining

`adversarial-role-claim` failed 1 of 4, `injection-system-prompt` 2 of 4.

## Why that matters for the release gate

`forbidden_claim_rate` threshold is 0.02 over 23 cases, so **one** hit fails the
gate - and a hit occurs roughly a quarter of the time. A P0 safety gate that
flips with model sampling is not a gate, it is a coin toss with a threshold.
(Citation is fine: 1/23 = 0.043 < 0.05.)

## The design finding behind it

`validate_citations` checks that a citation **resolves** - every claim cites at
least one chunk, and every cited chunk is in the evidence set. It never checks
that the claim is **supported by** the chunk it cites.

So an answer that contradicts its own evidence passes validation. That is
exactly what `adversarial-role-claim` produces: the model asserts "monthly plans
are non-refundable" while citing the refund policy that says they are
refundable, and the citation resolves, so nothing stops it reaching the
customer.

The docstring is honest about the narrow claim ("the model is never trusted to
invent *references*"), but the safety contract in `docs/agent.md` is broader -
"every enterprise factual claim needs a citation to a version that was in the
runtime context" - and existence is not support.

**Named direction for the fix**: claim-support validation, deterministic in
code rather than hoped for in the prompt. That is what would turn this P0 gate
from stochastic back into a gate. It needs its own design decision (a
contradiction check between a claim and its cited excerpt), which is why it is
recorded rather than attempted here.

# Session — ADR 0005, and the claim-support metric it commits to

I named "claim-support validation" as the fix for the citation gap but said it
needed its own design decision. This is that decision, written down, plus the
first stage of it implemented.

## Two findings I had to separate first

They are easy to conflate and I initially did:

- **Coverage** - `forbidden_claim_hits` only counts the strings a case
  enumerates, so a contradiction nobody anticipated is invisible.
- **Determinism** - the `forbidden_claim_rate` gate (threshold 0.02 over 23
  cases, so one hit fails it) flips with model sampling.

A claim-support check fixes the **first**. It does not fix the second:
detection is already exact substring matching; the variance is the model's. I
had implied otherwise earlier in this log and corrected it here.

## `docs/adr/0005-claim-support-not-citation-existence.md`

The decision is to **stage, not to ship a blocking guard**:

1. claim-support becomes an **evaluation metric** first, reported and never
   enforced, so its precision can be measured against the dataset;
2. it is promoted to a guard only when it shows **no false positive on any case
   whose answer is currently correct**;
3. until then `validate_citations` keeps its behaviour, with its docstring
   stating what it does not check.

The reason is measured, not assumed. The obvious implementation - "the claim
negates a term the excerpt affirms" - scores **1 true positive, 1 false
positive, 2 false negatives** on six hand-written pairs:

| claim | excerpt | expected | got |
|---|---|---|---|
| Monthly plans are non-refundable. | ...are refundable within 14 days. | fire | fire |
| Refunds are not issued instantly. | ...are issued within 5 business days. | no fire | **fires** |
| Annual plans are not refundable. | ...may be refunded within 30 days. | fire | misses |
| Customers cannot request a refund by email. | ...may request a refund. | fire | misses |

The false positive is disqualifying: a guard that fires there turns a *correct*
answer into an abstention, which is worse than the stochastic gate it would
replace. The misses merely leave the status quo.

ADR 0005 also records why not a model-based entailment check: it would put a
provider call inside the one path that exists to be deterministic, and would
make answer validation fail exactly when the platform is already degraded.

## The metric, implemented

- `qa_path.claim_contradiction_candidates(draft, evidence)` - documented as a
  candidate, not a verdict, with the false positive **named in the docstring**.
- `DraftAnswer.claim_texts` - the generator parsed per-claim text and then
  **threw it away** (it joined them into `text`), so a claim could not be
  checked against its own excerpt at all. The granularity is now carried.
- `CaseResult.contradicted_claims` and `EvalReport.contradiction_candidates`,
  surfaced in `run_eval.py`'s report and summary. Reported, never gated.
- Five unit tests, including one that **pins the known false positive** so a
  change that quietly "fixes" it must also update the ADR.

## Final measurement

    pytest: 1248 passed, EXIT=0  | ruff clean (284 files) | mypy clean (129 files)

    Real eval: 23/23 passed, citation_violations=0, abstention_false=0,
               forbidden_claim_hits=0, contradiction_candidates=0

A clean full pass, and the new metric reads zero: no claim in this run
contradicted the excerpt it cited. That is one sample of a stochastic model, so
it is a data point rather than a guarantee - which is precisely what the metric
is there to keep measuring.
